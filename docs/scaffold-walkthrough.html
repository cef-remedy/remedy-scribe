Orientation

The whole thing in one paragraph

A doctor's phone records a consultation and uploads it. A FastAPI server stores the audio, hands it to a speech-to-text vendor, hands the transcript to a language model, and saves the result as a structured note that the doctor edits and signs. Postgres holds the records, Redis carries the background jobs, S3-compatible storage holds the audio. What exists today is that skeleton with every joint articulated and two joints — the actual ASR and note-generation calls — left as sockets with the shape declared but nothing plugged in.

The rest of this document explains why each part sits where it does. If you read only one section, read the six patterns — that's where the transferable ideas are.

Verified

Everything described here was executed, not just written. Migrations ran against a real Postgres in Docker; the append-only trigger was tested by hand in psql; the server was started and driven through login → patient match → encounter → consent with curl; the Expo app type-checks and bundles. Where something is not proven, this document says so.

Where to start

Read the code in this order

Codebases are not meant to be read alphabetically. This order follows dependency: each file only relies on ones above it, so nothing is a forward reference.

  1. app/core/config.pyEvery other module reads settings from here. Start with what's configurable and you learn what the system considers a knob versus a fact.
  2. app/models/*.pyThe data model is the real specification. Read all seven; the docstrings map each table back to a PRD requirement.
  3. app/core/security.pyPassword hashing, JWT, TOTP, and the encryption wrapper — one file, four separable ideas.
  4. app/api/deps.pyShort, and it explains how every route gets a database session and an authenticated user without asking for one.
  5. app/services/note_lifecycle.pyThe clearest example of the service-layer pattern: 59 lines that own one field.
  6. app/api/routes/notes.pyNow you can see a route as what it is — a thin translator between HTTP and a service call.
  7. app/tasks/pipeline.pyThe async half. Read it last, because it depends on nearly everything else.

Part one

The layer cake, and what each layer is forbidden from doing

The folder structure isn't decoration — it encodes a rule about which direction dependencies flow. Layers only ever import downward. A model never imports a route; a service never imports FastAPI. That single constraint is what makes the code testable, because you can exercise a service without an HTTP request and a model without a service.

LayerIts one jobWhat it must never do
core/Settings and cryptography primitivesKnow about HTTP or the database schema
db/Engine, session factory, declarative baseContain business rules
models/Table definitions — the shape of stored truthEnforce workflow rules or call services
schemas/Validate what crosses the API boundaryBe reused as ORM models
services/Business rules, the interesting logicImport FastAPI or raise HTTPException
api/routes/Translate HTTP ↔ service callsContain business rules worth testing
tasks/Long-running work, off the request pathAssume a web request exists
Why it matters

Notice the "must never" column for services/: no HTTPException. That's why note_lifecycle.py defines its own InvalidTransitionError and SigningRequiresLicenseError, and the route translates those into 409 and 422. It costs a few extra lines — and it means the state machine could be driven by a CLI tool, a background job, or a test with no HTTP concept at all. Every time a service raises an HTTP error directly, that portability quietly dies.

Models versus schemas: two shapes for the same noun

There's a Patient model and a PatientOut schema, and beginners reasonably ask why both exist. They answer different questions. The model answers "what does the database store?" The schema answers "what am I willing to show the outside world, and what will I accept from it?"

They diverge the moment those answers differ — which is immediately. The Clinician model has hashed_password and mfa_secret; ClinicianOut has neither, so no route can leak them even by accident. That's not duplication, it's a boundary.

Part two

Six patterns worth taking with you

These are the ideas in the scaffold that generalize past this project. Each one is small; each one buys something specific.

1 · A settings object built once per process

Two things are happening. BaseSettings turns environment variables into a validated, typed object — so AUDIO_RETENTION_DAYS=ninety fails at startup with a clear error instead of at 3 a.m. inside a date calculation. And Literal["luna", "haiku"] means an invalid provider name is impossible to configure at all.

The @lru_cache is the subtle part: it makes get_settings() return the same instance every call, so reading config never re-parses the environment.

The catch

That cache is why tests/conftest.py sets environment variables at the very top of the file, before importing anything from app. The first call to get_settings() anywhere in the process freezes the values. Import the app first and your test database URL is ignored — silently, with tests running against your development database. The # noqa: E402 comments on those later imports exist to tell the linter this ordering is deliberate, not sloppy.

2 · Mixins for columns every table shares

Worth noticing why the primary key is a string rather than Postgres's native UUID type: the test suite runs on SQLite, which has no UUID type. Choosing String(36) means the same model definition works on both. That's a small tax on Postgres for a large gain in test speed.

Also notice UUIDs rather than auto-incrementing integers. Sequential integers leak information — a competitor can read /patients/1834 and infer your patient count, and a client can guess neighbouring IDs. The client also can't generate an integer ID offline, which matters for a phone that creates records without a network.

3 · Transparent column encryption via TypeDecorator

This is my favourite pattern in the scaffold, because of how little it asks of the rest of the code. Declare a column as EncryptedString(512) instead of String(512) and it is encrypted at rest — forever, everywhere, with no call site changed. Look at how Patient uses it:

Service code writes Patient(full_name="Juan Dela Cruz", ...) and reads patient.full_name as an ordinary string. The ciphertext exists only between the driver and the disk. Note also that the method raises if PHI_ENCRYPTION_KEY is unset rather than falling back to plaintext — a security control should fail loudly, never degrade quietly.

The catch

Encrypted columns cannot be searched by the database. Ciphertext isn't comparable, so WHERE full_name = 'Juan' can never match. That's the entire reason match_patient filters on birthdate first — an indexed plaintext column — and only then compares names in Python. This one line of model code shapes the whole patient-search feature, which is a good illustration of how far a storage decision can reach.

4 · Dependency injection, and why it makes tests trivial

Any route that writes clinician: Clinician = Depends(get_current_clinician) is now authenticated, and its signature documents that fact. Compare it to a decorator that stuffs a user onto a magic request object: here the requirement is visible in the type signature, and the route body receives a real Clinician.

The payoff shows up in the test suite, in three lines:

Every route in every module now uses the test session. No mocking library, no patching of import paths, no conditional code inside the app that asks "am I in a test?" That last point is the real prize: the application has no idea it is being tested.

Why it matters

get_db is a generator — it yields a session and closes it in a finally. FastAPI runs the code after the yield once the response is sent. That's how a session is guaranteed to close even when a route raises, and it's the same mechanism as a Python with block, applied across the request lifecycle.

5 · One service owns one field

The note lifecycle is the sharpest example. PRD requirement P0-5 says four states with none skippable. That rule is expressed as a dictionary:

Three properties are worth naming. The rule lives in data, not scattered if statements, so it can be read at a glance and printed in an error message. SIGNED is absent as a key, which makes it terminal — a signed note cannot transition anywhere, and that falls out of the structure rather than needing its own check. And the signature captures identity, licence, and timestamp in the same operation as the status change, so a signed note without a signer is not a state the code can produce.

The module docstring states the contract plainly: this is "the only code path allowed to change Note.status." That is a convention, not something Python enforces — but it's a convention with one obvious home, which is the most you can ask of a convention.

6 · A provider interface is what turns a rewrite into a config change

The PRD says GPT-5.6 Luna generates notes, with Claude Haiku 4.5 "available as a configured fallback." The roadmap leans on that: since the vendor bake-off was cancelled, a swap has to be cheap. Here is what "cheap" required structurally.

Why it matters

The same pattern appears for speech-to-text in services/asr/, and for the same reason — the roadmap names Speechmatics as the fallback if ElevenLabs' data-processing agreement doesn't cover the Scribe API. Both are cases where a business risk (a vendor may not work out) was answered with a structural choice (never name the vendor at the call site). That translation from commercial risk to code shape is worth learning to do deliberately.

Part three

One request, traced all the way down

Take the request that signs a note — POST /api/v1/notes/{id}/transition with {"to_status": "signed", "prc_license_number": "PRC-000111"}. Here is every layer it touches, in order.

  1. FastAPI matches the route and sees the parameter payload: NoteTransitionRequest. The JSON body is parsed and validated against that Pydantic model. A misspelled status is rejected here with a 422, before any of my code runs.
  2. Dependencies resolve. get_db opens a session. get_current_clinician pulls the bearer token, verifies its signature and expiry, loads the Clinician, and checks is_active. Either can abort the request before the route body starts.
  3. The route body runs — and it is deliberately dull. Fetch the note or 404, call transition(...), translate two domain exceptions into 409 and 422, record an audit entry, return.
  4. The service enforces the rules. Is this transition legal from the current state? If signing, is a licence number present? It sets the signature fields and commits.
  5. SQLAlchemy writes. Every EncryptedString column passes through process_bind_param on the way out, so the four note sections are encrypted before the driver sees them.
  6. The response is serialized through NoteOut. Only fields declared there are emitted — a new internal column added to the model tomorrow will not silently start appearing in API responses.

Step six is a quiet but real security property. Because the route declares response_model=NoteOut, the schema acts as an allow-list on the way out, not just a validator on the way in.

The login request, and what MFA actually checks

All five failure modes produce the same 401 with the same text. That's intentional: distinct messages for "no such user," "wrong password," and "wrong code" hand an attacker a way to enumerate valid accounts and to learn that a password was correct before brute-forcing the second factor.

The TOTP check itself is worth understanding, because it isn't a stored comparison. Both server and phone hold the same shared secret, and both compute the same function of (secret, current 30-second window). Nothing is transmitted or looked up. The valid_window=1 argument accepts the adjacent windows too, which covers ordinary clock drift — a real necessity, and also a reminder that the code is only as fresh as ±30 seconds.

Part four

The async half: why any of this is a queue

Transcribing twenty minutes of audio and generating a note takes far longer than an HTTP request should live. So the upload-confirmation route does the minimum — records the audio key, sets the retention clock, enqueues work — and returns immediately. The slow part happens in a Celery worker.

The pipe means "run the first, then pass its return value as the first argument to the second." So transcribe_encounter returning encounter_id is not incidental — it's how the second task learns what to work on.

Why the tasks check whether they've already run

The Celery config sets task_acks_late=True, which means a job is only acknowledged after it finishes. Kill a worker mid-task and the job returns to the queue and runs again — good for reliability, and it means every task must tolerate being executed twice. Hence:

Without this, a redelivered message means a second call to a paid transcription API and possibly a second note on the same encounter. The two protections operate at different levels and you want both: the unique constraint stops duplicate work being requested, the in-task check stops duplicate work being performed.

Known gap

Read transcribe_encounter closely and you'll find _ = segments — the transcript is computed and thrown away. generate_note then calls the model with transcript=[]. Both are marked TODO. The plumbing is real and the shape is right; nothing flows through it yet. Transcript persistence is the first thing to build here, and the checklist covers what that choice involves.

Part five

Migrations, and pushing guarantees into the database

Two migrations exist. The first creates all seven tables. The second does something more interesting: it makes the consent ledger physically append-only.

My first attempt used REVOKE UPDATE, DELETE ON consent_ledger_entries FROM PUBLIC, which looks equivalent and isn't. In Postgres, the owner of a table bypasses its own grants — and the application's role owns the table it created, so the revoke would have protected against everyone except the one account an attacker would actually have. A trigger applies to the owner too. That distinction is the difference between a real control and a decorative one.

Proven

I tested this by hand: inserted a ledger row, then attempted UPDATE and DELETE. Both raised consent_ledger_entries is append-only (P0-1). It works — but see the gap below, because "it works" and "it's protected from regression" are different claims.

Known gap

The test suite builds its schema with Base.metadata.create_all(), which reads model definitions — not migrations. So the trigger never exists during tests, and nothing in the suite exercises it. Every guarantee written in SQL rather than Python is currently invisible to CI. This is worth internalizing as a general lesson: your tests only cover the parts of your stack they actually construct.

The autogenerate hook, and a bug it exists to fix

Alembic can compare your models to the live database and write the migration for you. It did — and the generated file failed immediately with NameError: name 'app' is not defined, because it rendered the column type as app.core.security.EncryptedString(length=512) without importing app.core.security. Alembic knows how to import SQLAlchemy's own types; it cannot guess where a custom one lives.

Two things generalize from this. First, the fix belongs in the generator, not the generated file — patching one migration by hand leaves the trap armed for the next person. Second, env.py reads the database URL from application settings rather than from alembic.ini, so migrations and the app can never disagree about which database they mean.

Part six

The tests, and what they deliberately don't cover

Nine tests, four files. They're chosen to cover logic that could plausibly be wrong, not to chase a coverage number.

FileWhat it pins down
test_health.pyThe app starts and routes resolve. A smoke test.
test_patient_matching.pyExact match, near match, and — importantly — that the same name with a different birthdate does not match.
test_note_lifecycle.pyStates can't be skipped; signing without a licence fails; a full run captures the signature.
test_auth_flow.pyWrong credentials are refused; a real TOTP code yields a token that opens a protected route.

The third patient-matching test is the one I'd point at. It asserts a negative: that matching does not happen when it shouldn't. P0-6 says dedup uses name and birthdate together, and the failure mode that requirement guards against — two different patients merged into one record — is a clinical-safety problem, not a data-tidiness one. Tests that assert something correctly refuses are often more valuable than tests that assert it works.

Dropping and recreating per test is brutal and, on SQLite, fast enough not to matter. What it buys is complete independence: no test can be affected by another's leftover rows, and there is no ordering dependency to debug later. On Postgres you'd reach for a transaction rolled back after each test instead.

What the suite does not cover, stated plainly: the Postgres trigger (as above), the Celery tasks, the stubbed vendor calls, and any route not exercised by the two auth tests. That's an honest MVP test suite — thin, and thin in known places rather than unknown ones.

Part seven

The mobile side and the local infrastructure

What's actually in apps/mobile

Honestly: a scaffold and four dependency choices. There's no application code — one placeholder screen. But the dependency choices encode real decisions, so they're worth reading.

PackageWhy it's there
expo-dev-clientThe pivotal one. Background audio needs native modules that Expo Go can't load, so the project needs a custom development build. This package is what makes that possible while keeping Expo's tooling.
expo-audioRecording. Replaces expo-av, which I installed first and then found deprecated.
expo-secure-storeKeychain / Keystore access — where the auth token and the audio encryption key belong.
expo-sqliteThe durable upload queue. Must survive the app being killed, so it can't live in memory.
Why it matters

This is the single most consequential decision in the whole stack, and it's worth being able to argue it: a web app cannot satisfy P0-2. Mobile browsers suspend microphone capture when the screen locks or the tab backgrounds. No amount of clever JavaScript changes that, because it's an OS-level policy. The requirement "recording survives interruption" is therefore what forces a native app — not preference, not performance.

I verified the scaffold genuinely builds rather than trusting that it would: tsc --noEmit passes, and expo export --platform android bundles 580 modules into a 1.4 MB Hermes bytecode file. That's a real Metro build, headless, with no emulator — a useful check to keep running as the app grows.

The compose file, and why the ports look wrong

infra/docker-compose.yml runs Postgres, Redis, MinIO, the API, and a Celery worker. Two details are non-obvious.

First, host ports are shifted: Postgres on 5433, Redis on 6380, MinIO on 9002/9003. This isn't stylistic. A native Postgres install on the development machine already held 5432, and Docker's published port silently lost the race — connections reached the wrong server and failed authentication with a message that looked like a credentials bug. Inside the compose network the services still use standard ports; only the host mapping moved.

Second, every service declares a healthcheck, and the API depends on them with condition: service_healthy. Without that, the API starts before Postgres finishes initializing and crashes on first connection — the classic docker-compose race. A container being started and being ready are different states, and only healthchecks let you wait for the second.

Part eight

Five things that broke, and how each was diagnosed

This is the part I'd most want you to read, because the errors were the useful bit. Each one has a diagnostic move worth reusing.

1 · psycopg2-binary wouldn't install

The error asked for Microsoft Visual C++ 14.0. The real cause: no prebuilt wheel exists for psycopg2-binary on Python 3.13 for Windows, so pip fell back to compiling from source and needed a C toolchain. Fix: use psycopg[binary], the version-3 driver with current wheels, and change the SQLAlchemy URL prefix from postgresql+psycopg2 to postgresql+psycopg.

The generalizable move: when installation demands a compiler, you're usually missing a wheel, not a compiler. Check what your Python version and platform actually have available before installing build tools.

2 · bcrypt raised on a 72-byte password nobody typed

Tests failed inside passlib's own startup self-check, with an error about a password longer than 72 bytes — on a password of about 12 characters. Reading the traceback showed the string was passlib's internal probe, not mine: it deliberately hashes a long value to detect a historical bcrypt bug, and modern bcrypt now rejects over-length input instead of truncating. Fix: pin bcrypt==4.0.1.

The generalizable move: read the traceback for whose code is running. The password in the error wasn't mine, and noticing that pointed straight at a library-compatibility problem rather than a bug in my hashing.

3 · Postgres rejected the right password

psql inside the container worked; connecting from the host with identical credentials failed. Since credentials can't be simultaneously right and wrong, the connection must have been reaching a different server — confirmed with netstat -ano | grep 5432, which showed two processes listening. Fix: shift the host port.

The generalizable move: when the same credentials work in one place and fail in another, stop debugging the credentials and start questioning what you're connected to.

4 · Alembic generated a migration that couldn't run

Covered above — the missing import for the custom column type. The signal was that the failure was a NameError at module import, not a database error, which located the problem in code generation rather than in SQL.

5 · The versions directory didn't exist

Alembic printed its full plan, then died with FileNotFoundError writing the file, because I'd created alembic/ and alembic/versions/ was never made. Trivial, and included because it's representative: a tool can do all its real work and still fail on filesystem plumbing. The fix took a second once I read the last line of the traceback instead of the first.

Worth noticing

Four of these five were environment problems, not logic problems — and that ratio is normal. Most of the time lost on a new project goes to dependency resolution, platform differences, and port conflicts, and almost none of it is in the code you set out to write. Recognizing an environment failure quickly is a distinct skill from debugging your own logic, and it's the one that saves whole afternoons.
