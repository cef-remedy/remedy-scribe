# Phase 1.5 — Pipeline failure handling

**Status:** done · **Date:** 2026-08-25
**Related decisions:** [0023](../decisions/0023-pipeline-failure-handling-design.md)
(two failure states not three; dead-letter vs. stuck-sweep as separate mechanisms; `/retry` scope — implementation)

This closes Phase 1 — 1.1 through 1.5 are all done.

## What changed

- **`EncounterPipelineStatus`** (`app/models/encounter.py`) gains two
  terminal members: `TRANSCRIPTION_FAILED`, `GENERATION_FAILED`.
  Deliberately not a third `UPLOAD_FAILED` — see decision 0023.
- **Three new columns on `Encounter`:**
  - `retry_count: int` — already existed as a column nobody wrote to;
    now actually incremented on every failed attempt and reset to `0`
    the moment a stage succeeds.
  - `last_pipeline_error: str | None` — the last exception's message,
    cleared on success. Always an infrastructure/vendor error string
    (HTTP status, missing API key, "not found"); never anything built
    from transcript or note content, so it can't leak PHI.
  - `pipeline_updated_at: datetime` — stamped on every real
    `pipeline_status` transition, not a generic `onupdate=now()` (see
    decision 0023 for why that distinction matters).
- **Migration `c9d0e1f2a3b4`** — adds the two columns, backfills
  `pipeline_updated_at` from `created_at` for existing rows, and
  drop-and-recreates the `encounterpipelinestatus` CHECK constraint with
  the two new values (CHECK constraints can't be `ALTER`ed in place).
- **`app/tasks/pipeline.py`** — the real logic:
  - `_mark_stage_failure()`, shared by both tasks' `except` blocks:
    records the attempt (`retry_count`, `last_pipeline_error`,
    `pipeline_updated_at`) every time, and additionally flips
    `pipeline_status` to the stage's `*_FAILED` member once
    `self.request.retries >= self.max_retries` — the one call before
    Celery's own `self.retry()` would raise `MaxRetriesExceededError`
    instead of scheduling another attempt.
  - Both tasks reset `retry_count = 0` and `last_pipeline_error = None`
    on their own success path, so neither lingers as stale history once
    a stage that previously failed goes on to succeed.
  - `run_note_generation(encounter_id)` — a new sibling to `run_pipeline`
    that re-enqueues only `generate_note`. Used by `/retry` and the
    stuck-sweep when re-transcribing would be wasted, real money.
  - `sweep_stuck_encounters()` — a new Celery task, scheduled via Celery
    Beat (see below): finds encounters sitting in `UPLOADED` or
    `TRANSCRIBED` past `settings.pipeline_stuck_threshold_minutes` and
    re-kicks the appropriate next stage. This is the failure mode
    dead-lettering structurally cannot catch — a task that never ran at
    all never reaches an `except` block to record anything.
- **`app/tasks/celery_app.py`** — `beat_schedule` added: runs
  `sweep_stuck_encounters` every 5 minutes.
- **`infra/docker-compose.yml`** — new `beat` service
  (`celery -A app.tasks.celery_app beat`). Beat only schedules; the
  `worker` service (already Redis/Postgres-configured) is what actually
  executes the swept tasks.
- **`app/core/config.py`** — `pipeline_stuck_threshold_minutes: int = 30`,
  plus `.env`/`.env.example` entries.
- **`app/schemas/encounter.py`** — `EncounterOut` now includes
  `retry_count` and `last_pipeline_error`, so a future doctor-facing
  client has real data to render a specific, actionable message per
  failure mode rather than just a bare status name.
- **`app/api/routes/encounters.py`** — two new routes:
  - `GET /encounters/failed` — every encounter in a `*_FAILED` state,
    same shape as the existing `/loose` worklist. The dead-letter
    surfacing the checklist asks for, in the form that exists before
    Phase 2's mobile client does.
  - `POST /encounters/{id}/retry` — the "regenerate note" action,
    generalized to both failure stages rather than just note generation:
    404 if the encounter doesn't exist, 409 if it isn't actually in a
    failed state, otherwise resets `retry_count`/`last_pipeline_error`,
    rewinds `pipeline_status` to the stage before the one that failed,
    and re-kicks exactly that stage (`run_pipeline` from
    `TRANSCRIPTION_FAILED`, `run_note_generation` from
    `GENERATION_FAILED`).
- **Tests:** new `tests/test_pipeline_failure_handling.py` (13 tests) —
  dead-lettering after exhausted retries for both tasks (via Celery's
  `.apply()`, the only way to exercise a real eager retry loop without a
  live worker), recovery from a transient failure that resets
  `retry_count`/`last_pipeline_error` on success, `/failed` listing,
  `/retry`'s 404/409/success paths for both failure stages, and
  `sweep_stuck_encounters` — re-kicking a genuinely stuck encounter,
  leaving a recent one alone, and never touching a terminal status no
  matter how old. One new RBAC regression added to `tests/test_rbac.py`
  for `/retry`.

## How the pieces connect

```
transcribe_encounter / generate_note
        │
        ├─ succeeds → pipeline_status advances; retry_count = 0,
        │             last_pipeline_error = None, pipeline_updated_at = now
        │
        └─ raises  → _mark_stage_failure(db, encounter_id, self, exc, FAILED_status)
                        │
                        ├─ retries remain → retry_count += 1, last_pipeline_error
                        │                   set, self.retry(...) schedules another
                        │                   attempt (same as before this phase)
                        │
                        └─ retries exhausted → pipeline_status = *_FAILED,
                                                exception re-raised (Celery
                                                marks the task FAILURE too)

GET /encounters/failed  ──────────► every *_FAILED encounter, doctor-facing worklist

POST /encounters/{id}/retry
        │
        ├─ TRANSCRIPTION_FAILED → pipeline_status = UPLOADED → run_pipeline()
        │                          (no transcript existed; re-run the whole chain)
        │
        └─ GENERATION_FAILED    → pipeline_status = TRANSCRIBED → run_note_generation()
                                   (transcript already real; don't re-pay for ASR)

Celery Beat, every 5 min
        │
        ▼
sweep_stuck_encounters()
        │  finds: pipeline_status in (UPLOADED, TRANSCRIBED)
        │         AND pipeline_updated_at < now - stuck_threshold_minutes
        │
        ├─ UPLOADED    → run_pipeline(encounter_id)
        └─ TRANSCRIBED → run_note_generation(encounter_id)
              (both are no-ops if the work already happened — safe to
               re-kick something that was just slow, not actually stuck)
```

Dead-lettering and the stuck-sweep are deliberately two separate code
paths reacting to two separate signals — an exception, versus a stale
timestamp — because they catch two different failure classes. See
decision 0023 for the full reasoning.

## Tests

13 new tests in `tests/test_pipeline_failure_handling.py`; 1 new RBAC
regression in `tests/test_rbac.py`. Full suite: **121 passing** (up from
107), `ruff` and `mypy` both clean. Migration `c9d0e1f2a3b4` applied
cleanly against a real Postgres container as part of the full run.

## Notable bugs caught

- **A real bug found while writing the `sweep_stuck_encounters` tests,
  not by reading:** the first version dispatched via a dict built at
  module load time (`{UPLOADED: run_pipeline, TRANSCRIBED:
  run_note_generation}`). That dict captures the two functions'
  *identities* once, at import time — a test's
  `monkeypatch.setattr("app.tasks.pipeline.run_pipeline", ...)`, which
  replaces the *module attribute*, has no effect on a reference already
  stored in the dict. The test's fake never ran; the real `run_pipeline`
  did, which tries to open a real connection to Redis and hung the test
  run. Fixed by dispatching on a plain `if`/`else` referencing the bare
  names inside the function body, which resolves them from the module's
  current global namespace at call time — the same mechanism that makes
  `monkeypatch.setattr` on a module-level function work at all. Recorded
  as a comment on `sweep_stuck_encounters` itself, since the same trap
  is waiting for the next person who reaches for a dispatch dict here.

## Open follow-ups

- **No load-bearing test runs `celery beat` for real** — `beat_schedule`
  and the new `docker-compose` `beat` service are real configuration,
  but `sweep_stuck_encounters` itself is only ever invoked directly in
  tests (`sweep_stuck_encounters()`), never through an actual running
  Beat process on a real interval. Worth a smoke check once Phase 5's
  deployment work stands up a real environment.
- **`pipeline_stuck_threshold_minutes` (30) and the sweep interval (5
  minutes, hardcoded in `beat_schedule`) are both first-guess numbers,**
  not validated against how long a real transcription/generation call
  actually takes end to end with retries. Once alpha produces real
  timing data, both are worth revisiting — a threshold shorter than a
  single legitimate slow attempt would re-kick work that wasn't actually
  stuck.
- **Phase 1 is now fully closed** (1.1 through 1.5). The suggested
  sequencing table's next step is Phase 2.1–2.2 (mobile app foundation +
  recording), already flagged as the longest-lead, highest-risk work
  remaining.
