5.3 reads as four chores. Three of them are the same question asked in
three places, and the fourth describes a product that was retired two
phases ago.

The question is **what a passing build is evidence of**. Phase 4.3 built
this repo's first CI and was careful about it — but its test suite builds
its schema with `Base.metadata.create_all()` against SQLite, so the suite
is *structurally incapable* of noticing that a model has no migration. Add
a column: 385 tests pass, `ruff` passes, `mypy` passes, `alembic upgrade
head` succeeds at deploy because there is nothing to apply, and the first
query touching the column raises `UndefinedColumn` at a clinic.

Green, green, green, outage. So the rule for this phase:

> **A gate must be able to fail, must have been seen failing, and must not
> be able to pass by not running.**

## 1. Migration safety — and yes, it was watched failing

`scripts/check_migrations.py` brings a database to `head` and asks
Alembic's autogenerate what it would write next.

**Observed failing.** A column added to `Patient`, no revision:

```
OK: single migration head, a0b1c2d3e4f5
FAIL: 1 unrecorded difference(s) between the models and the schema at head:
  - add_column: patients.TEMPORARY_DRIFT_PROBE (VARCHAR(24))
```

...while `pytest` on the same tree stayed green — the two halves of the
failure, side by side, on one machine. Then reverted, byte-identical
(`md5sum` before and after, `git diff` on `app/models/` empty). Done twice:
once during the initial build and once again on the current tree.

Decision 0034 named the principle. A control nobody has watched fail is
the same hope with a nicer name.

**It runs on Postgres and refuses a SQLite URL**, because a SQLite version
would be green in exactly the cases that matter. SQLite compiles
`DateTime(timezone=True)` and a naive `DateTime` to the same `DATETIME` —
and every timestamp in this schema is tz-aware: the retention clock, the
audit log's expiry, the signing timestamp.

There is a correction worth recording. The first draft of that argument
used `String(64)` vs `String(128)` as its example. **That is false** —
SQLite renders and reflects declared lengths faithfully, it just never
enforces them. A test written to pin the claim caught it in about four
seconds. The wrong version is kept as a comment in
`test_sqlite_would_not_have_caught_this`, because it passed review by
sounding right, and that is the more useful artifact.

**Two paths to the same assertion, one of which cannot skip.** The `api`
job runs the pytest version via testcontainers; the new `migrations` job
runs the script against a GitHub `services:` Postgres container, which
either comes up or fails the job. `REMEDY_REQUIRE_POSTGRES=1` additionally
turns `test_migration_safety.py`'s Docker-unavailable skip into a hard
failure — that file only (see §5).

### It ran red on the first try, and the four findings are real

| Finding | Cause |
|---|---|
| `remove_constraint: transcripts_encounter_id_key` | `f6a7b8c9d0e1` writes `sa.UniqueConstraint('encounter_id')` **and** a unique index on the same column; the model declares only the index. A duplicate B-tree maintained on every insert |
| `remove_constraint: refresh_tokens_token_hash_key` | Same pattern in `c3d4e5f6a7b8` |
| `modify_type: consent_ledger_entries.event` | `String(16)` initially, `Enum(native_enum=False)` since 0.4, no `ALTER`. Deployed column is 7 chars wider than the model |
| `modify_type: encounters.pipeline_status` | Same. `VARCHAR(32)` deployed, longest member is 20 |

Every one is a genuine difference between a schema built by migrations and
one built by `create_all()`. **None is dangerous — which is exactly why
they survived four phases.** Nothing mechanical was looking. That is the
argument for the gate in one sentence.

Fixing them needs an Alembic revision, which this phase does not own, so
they are recorded in `KNOWN_DIVERGENCES` — and the shape of that record is
a decision, not bookkeeping:

**It is a snapshot assertion, not an ignore list.** The gate fails when a
recorded divergence *disappears* as well as when a new one appears. An
ignore list only grows; a snapshot has to be edited down when someone
fixes something, so it shrinks toward empty on its own and every surviving
entry is one a human looked at recently. Each key is the fully rendered
diff line, so adding an `EncounterPipelineStatus` member changes the key
and fails the gate on purpose — the moment to check the column still fits.

A test asserts every entry carries a real explanation, because a baseline
entry without one *is* an ignore-list entry.

## 2. Staging with synthetic data — a PHI control, not a convenience

The reason this bullet is in a checklist at all is behavioural: when
staging is three lorem-ipsum rows and someone needs to reproduce a bug,
`pg_dump production | psql staging` is the obvious next command. Under the
Data Privacy Act that is an unlogged bulk disclosure of every patient in
the clinic.

You do not police that with a policy. You **remove the motive** by making
staging fuller than production feels — the same shape of argument as
decision 0031's published dev secrets.

So "realistic" was treated as a specification:

- **14 patients built to break the matcher**, not to fill a table. A
  compound surname; a `Ma.` abbreviation; a Jr./father pair distinguished
  *only* by birthdate; an unaccented `Pena` a doctor will dictate as
  `Peña`; two people with an identical name and different birthdates;
  Chinese-Filipino short surnames; a legal name for someone called "Jun".
  Each row records which behaviour it exists to exercise. Verified against
  the live directory: "Maria Dela Cruz" → 0.73, "Jun Aquino" → 0.67 (above
  the 0.55 search threshold, below the 0.82 dedup threshold — the band
  where having two thresholds is what makes the flow work), dictated "Peña"
  → 0.96 near-match, same name + wrong birthdate → `none`, + right
  birthdate → `exact`. And one honest negative: "Maria Bautista" does
  **not** return `Ma. Cristina Reyes-Bautista`, because they share no
  token. That is the current matcher's real recall limit, left visible
  rather than designed around.
- **4 Taglish consultations** with word timings and deliberately
  low-confidence words on clinically load-bearing tokens (a dose
  frequency, a lab name, an episode count), so P0-4's `[INAUDIBLE]`
  suppression appears in staging rather than only in unit tests.
- **11 encounters covering every state the UI renders**, including both of
  decision 0030's grounding flags disagreeing, all three audio rungs
  (`available` / `expired` / `withdrawn` / `never_recorded`), a declined
  consent, a loose unlinked session, and both terminal pipeline failures.
- **Notes built by the production span builder**, `build_sections`, not a
  copy of its convention. `apps/web/smoke/seed_pipeline.py` duplicates it
  deliberately and for a smoke test that is right — the duplicate is a
  canary. For a dataset trusted for weeks it is wrong: change the
  separator and a copy silently produces notes whose grounding never lines
  up, and staging becomes *worse* than empty because it looks fine.
- **Statuses driven through `note_lifecycle.transition`**, never by
  assigning `Note.status`.
- **Verified, not asserted.** Every note is read back through
  `resolve_grounding`; a note with a live transcript resolving zero cited
  segments fails the run.

### What it actually produced

Executed 2026-08-29 against local Postgres 16 and MinIO, fresh database at
head `a0b1c2d3e4f5`, real audio uploaded over the presigned-multipart path:

```
clinicians 3 · patients 14 · encounters 11 · consent_entries 12
transcripts 8 · notes 8 · revisions 2 · audio_objects 7
```

All 8 notes resolve citations through the grounding path — 5 or 6 cited
segments each plus 2–3 context neighbours, except the consent-withdrawn
one, which correctly resolves 0 because its transcript is gone. Both
decision-0030 states landed: one note has `plan` **edited and still
fitting** (same-length substitution), another has `assessment` **edited
and no longer fitting** (insertion). All 7 audio objects resolve via
`head_object` (896,044-byte WAVs). All 14 names decrypt; the raw column
holds Fernet ciphertext. Full output in
[the runbook](../runbooks/staging.md) §6.

### Pointing at production is structurally hard

Six locks, checked before a single `INSERT`: `is_production`; an
`ENVIRONMENT` allow-list that **fails closed** (`prod-eu` is refused, not
shrugged at); an opt-in env var absent from every `.env` in the repo; a
schema-at-head check; a typed confirmation; and the one that does not
depend on any configuration being correct — **every `clinicians` row must
be on `@staging.remedy.invalid`**. Production has real accounts, so the
script refuses before writing. `.invalid` is RFC 2606-reserved and can
never resolve.

All six were exercised, not just written. Each refusal was observed,
including the genuinely-production-configured case (freshly generated
secrets, `REFRESH_COOKIE_SECURE=true`, a real CORS origin) where lock 1
fires rather than the config validator, and a database holding one
ordinary `maria.reyes@remedy.ph` account where lock 4 fires.

It also **only ever INSERTs, and has no `--reset`** — the consent ledger's
append-only trigger means a mis-seed cannot be cleaned up row by row by
anyone, and giving this script `DROP DATABASE` privileges would hand the
largest available capability to the exact code path whose guards just
failed.

### The bug the seed manufactured

Rehearsing the CI job caught the seed doing the thing Phase 3 already
fixed once.

Under `--no-audio` the first version still wrote an `audio_object_key` for
bytes it never uploaded. `grounding._audio_state` treats "row claims a
key, storage says 404" as proof the lifecycle rule expired the object and
stamps `audio_deleted_at` — correct in production, and precisely the
verification Phase 3 added *because the database's belief about audio is
not evidence* (decision 0030 §2). Handed a key for an upload that never
happened, it recorded a **retention expiry that never occurred**.

Found by running it, not by reading it: the read-back reported
`audio=expired` where `never_recorded` was expected. Fixed by making those
encounters honestly never-recorded — no key, no bytes, no claim. Confirmed
on the live database: `audio_object_key` set on exactly 9 rows (7 uploaded
+ the expired and withdrawn scenarios), `audio_deleted_at` on exactly 2.

This is the **second time this system has produced a row asserting bytes
that were never there**, and both times the row looked completely
ordinary. Worth carrying forward as a shape to watch for rather than an
incident that was closed.

## 3. The mobile release pipeline is obsolete

> ~~Mobile release pipeline (EAS Build, internal distribution for pilot
> doctors).~~ — and "build the mobile bundle" in the first bullet.

**Decision 0024 re-platformed the client from an Expo mobile app to a
browser app on a clinic laptop, and there is no app store in the plan.**
No EAS project, no `eas.json`, no native bundle, no TestFlight or Play
track. Implementing this would mean inventing a delivery mechanism for a
product that does not exist — a green CI job that ships nothing.

Deleting it silently is no better: six weeks from now that is
indistinguishable from having forgotten it.

**What replaces it** is deliberately small, because the honest answer is
small: `npm run build` produces a static `dist/`, and CI uploads it as
`web-client-dist-<sha>` (14 days, `if-no-files-found: error`). The one
part that is a decision rather than plumbing is *uploading* rather than
rebuilding at deploy time — Vite inlines `VITE_` variables at build time,
so a bundle rebuilt on the deploy host is a different artifact from the
one CI tested, and "we shipped what we tested" only holds if the bytes are
carried forward.

`docs/implementation-checklist.md` is outside this phase's lease, so the
bullet is not edited there. This document, decision 0038 §3, and
[ci-cd.md](../runbooks/ci-cd.md) §5 are where it is stated.

## 4. Playwright: a documented manual gate

`apps/web/smoke/*.cjs` need Postgres, Redis, MinIO, the API, a Celery
worker, Vite, a browser, and either real vendor keys or `SEED_PIPELINE`.

**They stay out of CI**, for a reason that is not "it is hard": a
six-process browser suite is the flakiest thing in any pipeline, and a
gate that goes red for reasons unrelated to the change is one people learn
to re-run rather than read. That habit does not stay contained on the job
that taught it — it gets applied to the migration gate.

The cost is stated rather than hidden: **no full end-to-end path is
verified automatically today.** CI covers each seam separately — real
Postgres migrations and the append-only triggers, real MinIO presigned
multipart, the route layer on SQLite, the client's unit tests. The seam
nothing covers is a browser talking to a running API. The procedure is in
[ci-cd.md](../runbooks/ci-cd.md) §6, and the right fix is a **nightly**
run against 5.1's staging deploy once one exists — not per-PR.

### And what that verification does **not** cover

- **Nothing has run on a GitHub runner.** No remote exists. The first push
  is the first real run, and this is the third phase in a row that has had
  to write that sentence.
- **`actionlint` is not available here**, so action *input names* and the
  runner API were never schema-checked. A typo in a `with:` key would not
  have been caught. Most likely first failures: the `services:` block's
  `options:` health-check syntax and `actions/upload-artifact@v4` inputs.
- **The Postgres service container's health-check timing is unrehearsed.**
  Locally the database was already up. On a runner, if `alembic upgrade
  head` races the health check, the `migrations` job fails on connection
  rather than on drift — that is the fix, not a retry loop around the gate.
- **`test_postgres_specific.py` and `test_storage_specific.py` can still
  skip silently** (§5 below).

## 5. Known gap: the skip that is still silent

`REMEDY_REQUIRE_POSTGRES` covers `test_migration_safety.py` only. The two
older testcontainers suites still skip rather than fail when Docker is
unreachable, which means the consent ledger's append-only trigger and
0.4's CHECK constraints could go unexercised on a runner without anything
going red.

Extending the switch needs `tests/conftest.py`, which this phase does not
own. Until then: **on the first real run, check the `api` job's summary
for skips.** If they are there, those assertions are not running.

## Hand-offs

**1. An Alembic revision for the four known divergences.** Owned by
whoever next touches `alembic/`. Two `op.drop_constraint` and two
`op.alter_column`; the exact names and reasoning are in
`KNOWN_DIVERGENCES` and in [ci-cd.md](../runbooks/ci-cd.md) §3. Delete
each entry as its fix lands — the gate fails on a stale entry, which is
the mechanism that keeps the list shrinking.

**2. Phase 5.1 consumes `web-client-dist-<sha>`.** Two things it needs to
know: the build currently uses Vite's defaults because **no staging API
URL exists yet**, so whatever 5.1 settles on must be present at build time
(and if 5.1 rebuilds instead, this artifact is a convenience, not the
release); and the bundle contains a **service worker**, so the deploy must
replace the whole directory atomically or it will pin users to a mix of
old and new.

## Open follow-ups

- **A staging `PHI_ENCRYPTION_KEY` distinct from the published dev key**,
  before staging is reachable from anywhere but a laptop. The seed prints
  the key fingerprint on every run precisely so this is checkable.
- **Nightly Playwright against staging**, once 5.1's deploy exists. The
  expensive half of running them in CI is standing the stack up.
- **Extend `REMEDY_REQUIRE_POSTGRES` to the older suites** (needs
  `conftest.py`).
- **Object-storage cleanup on re-seed.** Dropping the database orphans the
  audio objects; harmless but they accumulate.
- **Pin Actions to commit SHAs**, inherited from 4.3 and still open. Not
  done because the SHAs could not be verified from this environment, and a
  pin nobody checked is worse than an honest tag.
- **`ruff format` is still not run and still should not be.** 44 of 98
  files would be rewritten at 120 columns. It is a mechanical commit of
  its own, and adding `--check` to CI before that lands would either fail
  the build or bury a real change.
- **No job timeouts.** A hang runs to GitHub's 6-hour default.
- **Index entries are not written.** `docs/decisions/README.md`,
  `docs/progress/README.md` and `docs/implementation-checklist.md` are
  outside this phase's lease, so decision 0038, this document, and the two
  new runbooks are unlisted in them.
