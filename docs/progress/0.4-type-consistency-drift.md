# Phase 0.4 — Fix the type and consistency drift

**Status:** done · **Date:** 2026-08-25
**Related decisions:** [0010](../decisions/0010-enum-check-constraints-needed-explicit-flags.md)
(bug found empirically), [0011](../decisions/0011-encounter-pipeline-status-enum-membership.md)

## Why this was next

Three places where the codebase's own claims about itself were false or
unenforced: `Encounter.pipeline_status` was a free-form `String(32)` the
codebase wrote five different values into across two files with nothing
checking any of them; `confirm_upload` took a PHI-adjacent value
(`audio_object_key`) as a query parameter, which lands in access logs and
proxy logs; `ConsentLedgerEntry.event` had only a Python comment
documenting its allowed values.

## What changed

- **`app/models/encounter.py`** — new `EncounterPipelineStatus(str, enum.Enum)`
  with exactly the 5 values already in use (`recording`, `uploaded`,
  `transcribed`, `note_generated`, `blocked_no_consent` — see decision 0011
  for why not more). Column changed from `String(32)` to
  `Enum(EncounterPipelineStatus, native_enum=False, create_constraint=True,
  values_callable=...)`.
- **`app/models/consent.py`** — new `ConsentEventType(str, enum.Enum)`
  (`given` / `declined` / `withdrawn`), same `Enum(...)` treatment,
  replacing `event`'s old `String(16)`.
- **`app/models/note.py`** — `Note.status`'s existing `Enum(NoteStatus,
  native_enum=False)` gained `create_constraint=True` and
  `values_callable=...` — see "Notable bugs caught" below; this column
  was not new, but its DB-level enforcement effectively was.
- **`app/schemas/encounter.py`** — new `ConfirmUploadRequest` (one field:
  `audio_object_key: str`); `EncounterOut.pipeline_status` retyped from
  `str` to `EncounterPipelineStatus` (matches how `NoteOut.status` was
  already typed as `NoteStatus`, not `str`).
- **`app/schemas/consent.py`** — `ConsentEntryCreate.event` retyped from
  `Literal["given", "declined", "withdrawn"]` to `ConsentEventType`.
- **`app/api/routes/encounters.py`** — `confirm_upload` now takes
  `payload: ConfirmUploadRequest` (JSON body) instead of a bare
  `audio_object_key: str` parameter (which FastAPI resolved as a query
  param). All `pipeline_status` assignments now use enum members instead
  of string literals.
- **`app/tasks/pipeline.py`** — same: enum members instead of string
  literals at all four `pipeline_status` write/compare sites.
- **Alembic migration** `d4e5f6a7b8c9_type_consistency_check_constraints.py`
  — adds the three `CHECK` constraints directly (hand-written, not
  autogenerated — see why in "Notable bugs caught").
- **`tests/test_schema_constraints.py`** — 5 new tests: raw-SQL (bypassing
  the ORM entirely) attempts to write an invalid value into all three
  columns, each expected to raise `IntegrityError`; one test confirming
  every legitimate value is still accepted; one test locking in the
  `confirm_upload` contract change (old query-param style now gets `422`).
- **`tests/test_consent_gate.py`** — the two `confirm_upload` tests updated
  from `params={...}` to `json={...}`.

## How the pieces connect

```
Python: EncounterPipelineStatus / ConsentEventType / NoteStatus
  (str, enum.Enum — members compare equal to their plain-string values,
   so existing string comparisons elsewhere needed no changes)
        │
        ▼
SQLAlchemy Enum(..., native_enum=False,
                create_constraint=True,      ← makes the DB enforce it
                values_callable=...)         ← makes the constraint use
        │                                       .value, not .name
        ▼
CHECK (column IN ('value1', 'value2', ...))   ← enforced by SQLite AND
                                                  Postgres, at the DB
                                                  layer, independent of
                                                  which code path writes
```

The chain that matters: a Python enum by itself only constrains what the
*application's own code* can assign to an attribute (and even that's
weak — Python doesn't enforce type hints at runtime). Getting to "the
database physically cannot hold an invalid value" needs both
`create_constraint=True` (turn the constraint on at all) and
`values_callable` (make it check the right strings) — this phase is the
one place in this codebase that had to get all three enum-like columns to
actually make that stronger claim, not just the Python-typed one.

## Tests

5 new tests in `tests/test_schema_constraints.py`; 2 tests modified in
`tests/test_consent_gate.py`; full suite (45 tests at this point) passing
on SQLite — including, notably, the raw-SQL constraint-violation tests,
which SQLite honors identically to Postgres for plain `CHECK` constraints
(unlike the Postgres-only trigger behind the consent ledger's append-only
guarantee).

## Notable bugs caught (both found by testing, not by reading)

1. **`Note.status` had no DB-level constraint at all**, despite its own
   docstring claiming otherwise. Compiling the table's DDL and reading it
   showed a plain `VARCHAR` with no `CHECK`. Root cause: SQLAlchemy 2.0
   changed `Enum.create_constraint`'s default to `False`. This had been
   true since the very first migration — nothing in this phase introduced
   it, this phase just found and fixed it.
2. **Turning the constraint on then exposed a second bug**: SQLAlchemy's
   default `CHECK` rendering uses each enum member's *name*
   (`'RECORDING'`) rather than its *value* (`'recording'`) — while the
   column stores `.value` strings. Enabling `create_constraint=True`
   without also passing `values_callable` would have shipped a constraint
   that rejects every legitimate write. Caught by
   `test_db_accepts_every_valid_pipeline_status`, which failed on its very
   first iteration (the *default* status, "recording") before the fix.

## Notable follow-ups

- Decision 0011: `EncounterPipelineStatus` intentionally does not yet
  include Phase 1.5's future failure-mode states — extend it when that
  phase defines its actual taxonomy, not before.
- Decision 0010 flags that this pattern (`create_constraint=True` +
  `values_callable`) now has to be remembered by hand for any *future*
  enum column; worth a shared helper if a fourth one is ever added without
  copying this pattern correctly.
