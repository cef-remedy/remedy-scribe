## The 🧠, split into the half that was decided and the half that was not

The checklist asks two questions and they are not the same question.

**"In which jurisdiction?" is Legal's, and it is genuinely blocking.** Data
residency for Philippine health data may eliminate providers before any
technical criterion applies, so every recommendation that names a *vendor* is
conditional. Decision 0036 opens with the four questions Legal has to answer,
ordered by how quickly each eliminates options — the sharpest being whether
PHI at rest must stay physically in the Philippines, because a "yes" removes
most of the managed-Postgres market and changes the argument for buying it at
all. It also flags, in the same breath, that **Remedy still has no designated
DPO and no breach response team**, both legally required, and that the breach
runbook's legal section has never been reviewed by counsel.

**"Where does this run?" was decided, at implementation level**, against the
checklist's own principle — *the least infrastructure that meets the
compliance bar* — and this pilot's real scale: one clinic, a handful of
doctors, laptops.

## What was decided

**One Linux VM running Docker Compose.** Kubernetes is rejected for the
reason the checklist gives first: the compliance bar is about where data
lives and who can read it, and a control plane does not move that bar.
Managed containers are a real option and were rejected for now on two
grounds — request-scoped containers fit Celery beat badly, and they foreclose
the residency question in the other direction, since a managed platform
exists only where its provider has a region. **The cost is stated rather than
glossed: this topology has no redundancy and a reboot is an outage.** That is
defensible here *specifically because P0-2 built the client to work through
one* — a doctor keeps recording into IndexedDB and the queue drains later. The
system degrades to "notes are delayed", not "the consultation is lost".

**Exactly one thing is bought: Postgres.** The checklist asks for "automated
backups and PITR", and those are not the same difficulty. `pg_dump` on a cron
is an afternoon's work and the backup runbook already documents it, drill and
all. PITR is continuous WAL archiving plus — the hard part — a restore path
that has been exercised. Two things make that gap unacceptable rather than
untidy: a day of lost consultations is not an acceptable RPO for a clinical
record, and under the Data Privacy Act unrecoverable loss of patient records
is a *reportable availability incident*, not an outage. So Postgres is bought
and everything else stays on the VM.

**Redis is self-hosted, and the data-loss window is written out in numbers
rather than waved at.** What Redis holds here is the Celery broker and
nothing else: no PHI cache, no sessions, and — because decision 0008 put login
rate limiting in Postgres — no rate-limit counters. Task arguments are
encounter *ids*. What is lost on a restart is up to ~1 s of enqueued task
messages under `appendfsync everysec`.

**Why that is acceptable is the interesting part, and it is not "it's only a
queue."** *The compensating control already exists, and it was built for this
exact case by someone who was not thinking about Redis hosting.*
`sweep-stuck-encounters` runs every 300 s and re-kicks any encounter left in a
non-terminal `pipeline_status` past the 30-minute threshold, and its own
comment in `celery_app.py` says it exists to catch "the task that never ran at
all — the broker down, or the worker pool at zero, at the moment
`run_pipeline` fired." A lost enqueue is therefore a **delayed** encounter
bounded at 35 minutes, not a lost one. Managed Redis would shorten that delay
without removing the failure mode, at the price of another processor to name
in the Data Privacy Act disclosure and a fourth residency question. The
argument is explicitly scoped to Redis living on the same host: `REDIS_URL` is
`redis://` because there is no network segment for TLS to protect, and the
moment Redis moves off the VM the scheme becomes `rediss://` and the whole
argument needs re-reading.

## What was built

**The edge, and the Phase 4.1 debt it discharges.** `docs/runbooks/key-rotation.md`
§"What Phase 5 still owes" lists five items. Four are now in
`infra/caddy/Caddyfile`: TLS termination with automatic ACME renewal, an
http→https redirect that **proxies nothing** (an http listener that could
reach the API is a path on which PHI travels in the clear), an explicit
`protocols tls1.2 tls1.3` floor, and `X-Forwarded-Proto` set authoritatively.
The fifth — TLS to Postgres, Redis and object storage — is in the connection
strings rather than at the edge, and lives in
`infra/env/production.env.example`.

Caddy rather than nginx precisely because those first three are its
*defaults*: with nginx each is explicit config plus a certbot timer nobody
notices has stopped until a certificate expires.

**One origin for the client and the API.** There was no web Dockerfile;
`apps/web/Dockerfile` now builds the PWA and bakes it into the Caddy image.
That is a security decision, not a packaging one. Decision 0024 put the
refresh token in an httpOnly cookie; split origins would make it cross-site
and force `SameSite=None`, a strictly weaker cookie — `config.py`'s own
comment says "paired with samesite=none only if the API and client are
cross-site", and this topology is what keeps `lax` correct. It also makes
CORS non-load-bearing, which removes the failure `main.py` calls out as
silent. And it is what `vite.config.ts`'s existing
`navigateFallbackDenylist: [/^\/api\//]` was always assuming: on split
origins the service worker could never intercept API calls and that rule
would be decorative.

**Migrations as a service with a profile.** `migrate` carries
`profiles: ["deploy"]`, so `docker compose up -d` — the command someone
actually types at 2 a.m. — cannot start it. It exists only when
`--profile deploy` names it, which `infra/deploy.sh` does once, as its own
step, whose exit code gates whether the long-running services start at all.
The failure this prevents is specific: three long-lived services start from
the same image, so a migration in an entrypoint means three processes racing
for the same Alembic lock on every restart, and a container that OOM-restarts
at 3 a.m. quietly applying a schema change nobody triggered.

**Exactly one Beat, enforced by a name.** Two Beat schedules now exist and one
of them deletes PHI. Celery's default scheduler holds no distributed lock, so
two beat processes are not deduplicated — they are two concurrent passes over
the same deletion candidates, racing, against rows that are gone afterwards.
The guard is a fixed `container_name`: Docker will not create two containers
with one name, so Compose refuses to scale the service. One line, and it makes
the wrong thing impossible rather than discouraged. Scaling `worker` stays
free and is the right knob if uploads queue.

**Liveness and readiness, as two endpoints with opposite consequences.**
`/health` was defined inline in `main.py` and checked nothing but its own
existence. The fix is *not* "add a database check to `/health`" — that is the
trap, and the wrong version looks more thorough. **Liveness failing restarts
the container; readiness failing removes it from traffic.** A liveness probe
that touches Postgres restarts a healthy application because the database
blinked, and restarts every replica at once because they share the
dependency — turning a 30-second dependency outage into a crash loop that
outlives its cause.

So `app/api/routes/health.py` has `/health` checking nothing external (payload
unchanged, because a probe path that shifts under a refactor un-monitors a
deployment quietly) and `/ready` doing a `SELECT 1` **through the
application's own pooled session** — a healthy Postgres reached through an
exhausted pool is an instance that cannot serve traffic, and a probe that
opened its own connection would report ready throughout — plus a Redis `PING`
with a bounded timeout.

**Object storage is deliberately excluded from readiness**, and that is a
decision rather than an omission. Gating on it would convert a partial outage
into a total one: with the bucket down, uploads and playback fail, but consent
capture, worklists, patient matching, review and signing all still work, and
P0-2's offline queue exists so a doctor keeps recording through it. It is also
a slow remote call wrapped in botocore's retry, so paying it every ten seconds
risks causing that same total outage *by accident*. And a `HeadBucket` proves
little next to the presigned round trip the deploy's own smoke step runs.

**Neither probe body says anything but `ok` and `error` per check.** They are
unauthenticated by necessity, and `psycopg` and `redis-py` both put the
connection target into their error strings. Phase 4 already found the sharper
version of this: `_extract_tool_input` interpolated a whole model response,
PHI included, into an exception message that was then written to a plain
column.

### ⚠️ What was not run, stated plainly

- **Nothing has been deployed.** No VM, no domain, no certificate, no managed
  Postgres, no object-storage account. `infra/deploy.sh` has never run end to
  end.
- **No TLS handshake has ever happened.** The Caddyfile parses; Caddy has
  never served a request with it or obtained a certificate, and the cipher
  list has never been negotiated with a browser.
- **`sops` was not run** and no age key exists.
- **PITR is a specification, not a tested recovery path.** The only tested RPO
  on this project remains "whenever the last dump ran".
- **The forwarded-header behaviour was reasoned from Caddy's and uvicorn
  0.30.6's source and validated as config — not observed on the wire.**
- **`apps/web/Dockerfile` was not built.** The Vite build inside it was run
  directly on the host, which proves the build and the base-URL behaviour but
  not the Dockerfile.

## Notable bugs and findings, none of them in this phase's own code

**`COPY . .` was baking `apps/api/.env` into the image.** The Dockerfile had
no `.dockerignore`, and `.env` is a real, working file on every developer
machine. Proven rather than asserted: built without one, the image contains
`/app/.env` carrying a working `PHI_ENCRYPTION_KEY` — and on this machine that
key is **not** one of the published dev secrets, so Phase 4.1's boot guard
would not have caught it. A layer is immutable, so removing the value from the
environment later does not remove it from the image, and anyone who can
`docker save` or pull it has the key. The secrets runbook's rule that no
`.env` reaches a server was being defeated before the deploy started. Also
`.venv` — hundreds of megabytes of Windows binaries, wrong for the container's
platform.

**The per-IP login rate limit would have become a per-clinic one, silently.**
`auth.py:_client_ip` returns `request.client.host`, and that value keys both
the rate limit and the lockout counter. Behind a reverse proxy every request
appears to come from the proxy, so `LOGIN_RATE_LIMIT_PER_IP_PER_MINUTE = 10`
becomes ten attempts per minute *for the whole clinic* — a self-inflicted
outage the moment two doctors mistype a password in the same minute. Nothing
in the checklist or the 4.1 runbook flagged this; it only exists once there is
a proxy, which is this phase.

**And the obvious fix for it is worse than the bug.** Reading uvicorn 0.30.6's
`ProxyHeadersMiddleware` rather than trusting the flag: with
`--forwarded-allow-ips=*` it returns `x_forwarded_for_hosts[0]` — the
**leftmost**, entirely client-supplied entry. A wildcard would hand an
attacker a fresh apparent IP per login attempt and delete the rate limiter
outright. With a *specific* trusted address it scans from the right for the
first untrusted hop, which is correct — so the edge container gets a static IP
on a fixed subnet and that literal address is what uvicorn trusts (uvicorn
does not accept CIDR at this version). Caddy is separately told
`header_up X-Forwarded-For {remote_host}`, which replaces the header outright.

**A Caddy hardening that would have removed the header entirely.** The obvious
way to write "drop whatever the client sent, then state the truth" is
`header_up -X-Forwarded-Proto` followed by `header_up X-Forwarded-Proto https`.
Caddy applies header operations in the order add, set, **delete** — so the
delete runs last and the app would see no evidence of TLS at all. A plain
`header_up NAME value` compiles to a Set, which already replaces every client
value. Written into the Caddyfile as a "do not do this" so the next person to
harden it does not.

**`caddy validate` warns about the `X-Forwarded-For` line and the warning is
wrong here.** It emits "Unnecessary header_up X-Forwarded-For: the reverse
proxy's default behavior is to pass headers to the upstream". The lint is about
*forwarding*; that line is about *replacing*. Documented in place so nobody
deletes a security control to silence a linter.

**The `X-Forwarded-Proto` hole is narrower than the 4.1 runbook implies, and
worth saying so.** `SecurityHeadersMiddleware` emits HSTS when
`over_tls or settings.is_production`, so **in production a client cannot
suppress HSTS by sending `X-Forwarded-Proto: http`** — the second clause
covers it. The real exposure is a non-production environment served over TLS,
and, more importantly, anything added later that trusts the header (URL
building, redirects, logging) inheriting a client-controlled value. The proxy
still sets it authoritatively; the runbook now records what the actual risk is
rather than restating the general warning.

**A measurement that reframed the probe budget.** With Postgres stopped the
readiness probe answers in 4.1 s — and that is *not* a timeout expiring. The
port is closed, so the connection is refused fast; `localhost` resolves to both
`::1` and `127.0.0.1` and libpq pays ~2.0 s on each in turn. Against
`127.0.0.1` alone the same probe answers in 2.04 s. So **the probe budget is
`connect_timeout` × the number of addresses the hostname resolves to**, which a
managed endpoint with both an A and a AAAA record doubles silently. And
`connect_timeout` did not shorten any of it — libpq floors it at 2 s and a
refusal was already faster than the floor. It is set in the URL anyway, because
the case it bounds is the one a stopped container cannot reproduce: a host that
accepts the SYN and never completes the handshake. Caddy's `health_timeout` is
10 s against the measured worst case rather than the 5 s that looks tidier.

**The first probe of an outage is faster than the steady state** (2.10 s vs
4.10 s), because `pool_pre_ping` fails on an already-open pooled connection
before a fresh connect is attempted. Tuning a timeout against the first sample
would set it too low by half.

## Open follow-ups

- **⚠️ The provider and jurisdiction are still unchosen, and that is the one
  thing blocking a real deploy.** Decision 0036 lists the four questions for
  Legal. Nothing should be provisioned before they are answered — a managed
  Postgres in the wrong region holding real PHI is not fixable by migrating
  later, because the data was already there.
- **No graceful drain.** On `SIGTERM` the API stops immediately rather than
  failing readiness first and letting Caddy drain it, so a deploy drops
  whatever was in flight. Caddy retries, so it is a rough edge and not an
  outage. The fix is a lifespan hook in `app/main.py` flipping a
  `shutting_down` flag that `/ready` honours — deliberately not done here,
  since `main.py` is another agent's file this round and the brief asked for a
  minimal diff.
- **No staging environment.** Every post-deploy check in the runbook's §7
  would be run for the first time against the clinic's own deployment. The
  compose file is parameterised for a second environment; nothing else is.
- **Nobody is alerted when readiness goes red.** Phase 5.2's. On a
  single-instance deployment, Caddy taking the only instance out of rotation
  is an outage with no alarm.
- **The abort-incomplete-multipart lifecycle action has still never been
  verified against anything** (decision 0014, carried since Phase 1.1). It
  needs a real bucket, and the runbook's §4 says exactly how to test it.
- **Image provenance.** Images are built on the deploy host from a clean git
  checkout, which is honest but unsigned and unscanned. A registry with signed
  images and a vulnerability scan is the natural next step, and it is a
  registry decision, so it is downstream of the provider choice too.
- **`--forwarded-allow-ips` pins a literal IP** because uvicorn 0.30.6 does not
  accept CIDR. A uvicorn upgrade that adds CIDR support would let the fixed
  subnet in the compose file replace the static container address, which is one
  fewer thing to keep in sync.
