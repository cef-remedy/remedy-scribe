# Phase 0.5 — Close the test-vs-production divergence

**Status:** done · **Date:** 2026-08-25
**Related decisions:** [0012](../decisions/0012-postgres-test-path-testcontainers-and-subprocess-migrations.md)

## Why this was next

The full test suite ran on SQLite via `Base.metadata.create_all()` —
which builds tables straight from the ORM models and never touches a
migration file. The consent ledger's append-only trigger (Phase 0.1) and
the three `CHECK` constraints (Phase 0.4) both live in Alembic migrations
as raw SQL. Migrations had never run in the test suite, so neither
guarantee had ever been exercised by a single automated test — only
verified once, by hand, with `psql`. This phase closes that gap for real,
not by asserting it's closed.

## What changed

- **`requirements-dev.txt`** — added `testcontainers[postgres]==4.8.2`.
- **`pytest.ini`** — registered a `postgres` marker (documents what it
  needs and that it skips rather than fails without Docker).
- **New `tests/test_postgres_specific.py`** — 5 tests, all running against
  a real, disposable `postgres:16-alpine` container:
  - `test_consent_ledger_rejects_update`, `test_consent_ledger_rejects_delete`
    — the checklist's explicit ask. Both assert not just that *some* error
    is raised, but that the trigger's own message ("append-only") is in it
    — proof it's specifically this guarantee firing, not an unrelated
    failure.
  - Three bonus tests re-verifying 0.4's `CHECK` constraints
    (`pipeline_status`, `event`, `status`) against real Postgres — those
    were only ever proven on SQLite before this phase.
  - A `postgres_engine` fixture that starts the container, runs the real
    `alembic upgrade head` as a subprocess against it, and skips
    (`pytest.skip`, not a failure) the whole module if Docker isn't
    reachable — verified both directions: real pass with Docker up, clean
    skip with `DOCKER_HOST` pointed at nothing.

## How the pieces connect

```
tests/conftest.py (root)                tests/test_postgres_specific.py
  DATABASE_URL = sqlite:///...            postgres_engine fixture
  → app.core.config.get_settings()          │
    permanently cached to SQLite            ├─ testcontainers starts a
    for this whole pytest process            │  real postgres:16-alpine
        │                                    │
        ▼                                    ├─ subprocess: `alembic
  tests/test_*.py (45 tests)                 │  upgrade head`, with
  fast, no Docker needed                     │  DATABASE_URL overridden
                                              │  in that child process's
                                              │  own env — sidesteps the
                                              │  cached settings entirely
                                              │
                                              └─ tests run against the
                                                 real, migrated schema —
                                                 including the trigger
                                                 and CHECK constraints
                                                 create_all() never sees
```

The reason migrations run as a **subprocess** rather than an in-process
Alembic call: `alembic/env.py` always re-derives its DB URL from
`get_settings()`, and that singleton is permanently pointed at SQLite the
moment `tests/conftest.py` is first imported for the whole pytest
session. A subprocess gets a completely fresh Python process with its own
env vars, so it reads `DATABASE_URL` fresh rather than inheriting the
already-cached value — and as a side effect, it's also a more honest
test, since it's the literal command a real deploy runs (Phase 5.1),
not an approximation of it.

## Tests

5 new tests, all in `tests/test_postgres_specific.py`. Full suite: 50
tests, ~108 seconds total (the Postgres module accounts for most of
that — container pull/start + a real migration run). Verified both
outcomes directly: full pass with Docker running, and a clean 5-skipped
(not failed) run with `DOCKER_HOST` pointed at an unreachable address.

## Notable bugs / findings caught (by running against real Postgres, not by reading)

**The append-only trigger and the `event` CHECK constraint interact in a
way that isn't obvious from reading either migration in isolation.** The
first version of `test_consent_event_check_constraint` tried to prove the
`CHECK` constraint by `UPDATE`-ing an existing row's `event` to an invalid
value — and it failed, but not the way expected: the trigger (`BEFORE
UPDATE OR DELETE`) intercepts the statement before the `CHECK` constraint
ever evaluates the new value, so the error was "append-only," not a
constraint violation. This is actually correct system behavior — the
trigger's job is to block all mutation regardless of what's being
mutated to — but it meant the *test* was checking the wrong operation.
Fixed by testing the `event` constraint via `INSERT` instead, which the
trigger doesn't cover at all. Documented inline in the test itself so the
next person doesn't rediscover this by hitting the same failure.

## Notable follow-ups

- Phase 5.3 ("CI: ... test on Postgres (see 0.5)") can now literally point
  CI at `pytest -m postgres` (or just `pytest`, since these tests already
  skip cleanly without Docker) — the mechanism this phase built is what
  that phase wires in.
- Decision 0012 flags that if the Postgres module's ~30-60s startup cost
  becomes a real friction point as more Postgres-only tests accumulate,
  move to a session-scoped shared container rather than one per module —
  not done preemptively.
