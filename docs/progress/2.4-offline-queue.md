# Phase 2.4 — Offline upload queue (P0-2)

**Status:** done · **Date:** 2026-08-27
**Related decisions:** [0028](../decisions/0028-upload-queue-design.md)
(what "confirmed" means, offline ≠ failure, the two status bugs),
[0026](../decisions/0026-recorder-design.md) §3 (chunk vs part granularity),
[0013](../decisions/0013-presigned-multipart-upload-design.md) (S3 as part-state truth)

**This closes the loop.** Audio recorded on a laptop now reaches S3, the
Phase 1 pipeline runs on it for real, and the local copy is deleted only once
that has happened. Phase 1's server-side work has had no real input until now.

## What changed

### Backend (one endpoint)

**`GET /api/v1/encounters/{encounter_id}`** — the queue polls this to know
when the pipeline actually started. It comes with a **route-order regression
test**: FastAPI matches in registration order, so a path parameter declared
before `/loose` or `/failed` would swallow both — `/encounters/loose` would
resolve as `encounter_id="loose"` and 404, emptying the worklist silently.
Easy to reintroduce by tidying the file, so it is asserted rather than left
to convention.

### The queue (`apps/web/src/lib/queue/`)

- **`store.ts`** — durable entries in IndexedDB, at schema **v2** (the
  `uploads` store lives beside the audio chunks; one database, one version,
  one guarded additive upgrade handler so a laptop mid-pilot upgrades without
  losing chunks). Plus the backoff function.
- **`uploader.ts`** — `planParts` (pure, unit-tested) assembles recorder
  chunks into S3-sized parts; `uploadSession` runs init → presigned PUTs →
  complete, skipping parts S3 already has; `pipelineHasStarted` reads the
  encounter status.
- **`queue.ts`** — the runner: an 8-state machine, exponential jittered
  backoff, crash recovery, storage health, and the deletion rule.
- **`useQueue.ts` / `QueueStatus.tsx`** — the visible, persistent status
  P0-2 requires, on both the recording screen and the worklist.

### The state machine, and why deletion sits where it does

```
 recording ──► pending ──► uploading ──► uploaded ──► confirmed ──► done
     │            ▲            │             │            │
     │            └── backoff ─┘             │            └─ local audio
     │                                       │               deleted HERE
     └─ crash ─► (stale >30s) ─► pending     │
                                             ▼
   withdrawal ──► abandoned        terminal server failure ──► failed
                                        (local audio KEPT)
```

`uploaded` means the bytes arrived. `confirmed` means the server's pipeline
*ran*. Deleting at `uploaded` would destroy the only copy of a consultation
whose processing never started — the exact scenario Phase 1.5's stuck-sweep
exists for. Decision 0028 §1 has the full reasoning.

### The write-ahead invariant, concretely

The queue entry — carrying the idempotency key — is written when recording
**starts**, before any audio exists. The end-to-end test asserts exactly
that: at t+0.9s the entry exists in state `recording` with its key persisted,
and zero chunks are on disk. That ordering is the whole point of the phase.

## Verification

**API: 146 passing** (up from 143 — 3 new, including the route-order guard),
`ruff` and `mypy` clean.

**Web unit: 42 passing** (up from 18 — 24 new), `tsc` clean, build fine.
Covering the things that fail while looking fine: part-planning arithmetic
(every part but the last meets S3's minimum; no chunk dropped or duplicated),
backoff growth/cap/jitter, entry durability across connections, idempotent
re-enqueue keeping the original key, and `patchEntry` not clobbering
concurrent field updates.

**End-to-end: 18/18** against the **real stack** — Postgres, Redis, MinIO, a
Celery worker, and a real Chromium:

| | |
|---|---|
| Queue entry written at recording start, before any audio | pass |
| Idempotency key already persisted at that point | pass |
| A normally-stopped recording is **not** labelled interrupted | pass |
| Queue panel renders the recording | pass |
| **Real upload to MinIO** — 48,774 bytes | pass |
| Progress never exceeds the total (48774 of 48774) | pass |
| Server pipeline actually ran (`note_generated`, not merely `uploaded`) | pass |
| Local audio deleted **only** after pipeline start — 3 chunks → 0 | pass |
| A forced retry of a finished upload neither loops nor resurrects audio | pass |

The vendors are stubbed in the worker (no Groq/Anthropic keys here), so the
pipeline advances for real without those calls. The upload path itself —
presigned PUTs to a real S3-compatible endpoint — is genuinely exercised,
which is the part no mock could establish.

## Two bugs the test's own output exposed

Both passed the original assertions while being visibly wrong in the log.
Neither broke the upload; both would have undermined the one thing P0-2 asks
the UI to do.

**1. "Recording was interrupted" on a normal stop.** `recoverInterrupted()`
ran every tick and promoted any `recording` entry to `pending`. It could not
tell *the app crashed mid-recording* from *recording is happening right now*
— so a normally-stopped 14-second recording was labelled interrupted, and the
upload was queued **while capture was still running**, risking chunks written
after the upload being deleted unsent. Fixed with a 5s heartbeat and a 30s
staleness requirement. A timestamp rather than an in-memory flag, because it
has to survive the process dying, which is the case being detected.

**2. Progress over 100%: "56 KB of 37 KB".** `bytesTotal` came from React
state captured *before* `stop()` flushed MediaRecorder's final chunk, so it
was short by exactly one chunk. `markReadyToUpload` now derives it from the
chunk store — the only thing that knows what is on disk. The caller no longer
gets to pass it at all.

Both now have explicit regression assertions.

**A third, smaller one:** adding `queue.test.ts` broke the typecheck for
`api/client.ts`, because a test importing app code transitively compiles it
in the *test* project — which lacked `vite/client` types for
`import.meta.env`. Fixed by adding them there. Worth noting as a shape:
adding a test can break the build for a file the test never touched.

## Open follow-ups

- **Audio gaps still do not reach the note generator.** The gap total now
  travels *with the queue entry* (so it survives to upload time, which it
  did not before), but nothing sends it to the server. Phase 1.4 already
  suppresses content over low-confidence windows, and a known gap is better
  evidence than low ASR confidence. Needs a field on the upload-complete
  call or the encounter; deliberately not invented here.
- **`uploadId` is stored on the entry but never used.** S3's own `ListParts`
  is the resume mechanism (decision 0013), so the field is redundant. Left
  in rather than removed because 2.4's resume path has not been tested
  against a *mid-upload* interruption — only against a completed one — and
  that test may want it.
- **Resume is inferred, not proven.** The uploader skips parts `GET
  /upload/parts` reports, and that code path runs, but no test kills an
  upload halfway and restarts it. The single-part reality of a typical
  consult means multi-part resume is currently exercised only by unit tests
  on `planParts`.
- **Storage thresholds (15/60 minutes) are first guesses**, not derived from
  a real laptop's quota. Chrome typically grants a large fraction of free
  disk, so in practice the browser quota is unlikely to be the binding limit
  before the disk itself is — worth measuring on the clinic hardware.
- **No cap on total queued recordings.** A laptop offline for a week would
  accumulate until quota. The storage check catches it at the boundary, but
  an explicit "you have N unsent consultations, oldest is 6 days old" warning
  would surface it far earlier.
