**Runbook:** [key-rotation.md](../runbooks/key-rotation.md)

Phase 4.1 came with a 🧠 and a ⚠️ that pointed at the same thing from two
directions: the PHI encryption approach had never been *decided*, and the
key it depended on had no rotation story. Losing `PHI_ENCRYPTION_KEY` meant
losing every patient name, every note and every transcript, permanently.

That is now a procedure with a measured cost, rehearsed end to end against a
real database.

## The 🧠, and what is deliberately not resolved here

`docs/tech-stack.md` specified `pgcrypto`; the implementation used app-layer
Fernet because it works identically on SQLite, which the fast test suite
needs. Decision 0031 keeps Fernet, on grounds that are not "it was already
there":

- **`pgcrypto` puts the key in the SQL statement** — and therefore in
  `pg_stat_statements`, the slow-query log, and any statement log a DBA
  turns on for an afternoon. It also **does not solve rotation**: no key id
  in its output either, so re-keying is still an `UPDATE` of every row. Its
  one real advantage, keeping the key out of the app process, is delivered
  far better by KMS.
- **KMS envelope encryption is the right long-term answer** and is not being
  built now, for one honest reason: the thing it buys — cheap rotation —
  costs **three minutes** at this pilot's measured scale.
- **Fernet keeps the test suite testing the real code path**, and does not
  block the KMS move: the column contract is "opaque ciphertext in a text
  column" either way, and migrating is a re-encryption pass — which is
  precisely the script this phase built.

**The final call belongs to Remedy's DPO, and 0031 says so explicitly.**
Three things engineering judgment cannot substitute for: keys in an HSM/KMS
so no process ever holds them; key custody split from deploy access (today
anyone who can deploy can read all PHI); and a required rotation cadence.
The checklist says to ask before wider rollout because retrofitting is
worse — the answer to that is now cheaper to act on, because the rewrite
tooling exists and its runtime is a known number instead of a fear.

## What was built

**Rotation is possible at all.** `PHI_ENCRYPTION_KEY` encrypts;
`PHI_ENCRYPTION_KEY_PREVIOUS` is a comma-separated decrypt-only list. The
app reads a database holding a mix of both, so the rewrite is an online
operation and an *interrupted* rewrite is a non-event rather than an
incident. `MultiFernet` is the mechanism, verified against cryptography
43.0.1's own source rather than assumed.

**`scripts/rotate_phi_key.py`** rewrites every encrypted value. Two
properties, both of them ways the obvious version silently destroys data:

- **Columns are discovered by type, never listed.** A hand-written list goes
  stale the first time someone adds a model, and a column a rotation misses
  is unreadable forever once the old key is gone. A test asserts the
  discovered set *exactly*, so adding an encrypted column fails loudly.
- **Verification is a separate pass under the new key alone.** A run that
  raised no error is not evidence every row moved; only a read the old key
  cannot satisfy is. `--verify-only` gates the one irreversible step.

It pages by primary key rather than `OFFSET` (an `OFFSET` scan over a table
being updated as it is read can skip rows, and a skipped row is a row left
under the retired key), commits per batch, prints **fingerprints and never
key material**, and exits non-zero naming the row when no key can decrypt a
value.

**Environment separation, enforced rather than aspirational.** A Fernet key
is 32 random bytes; no inspection distinguishes a production one from a
local one. So the problem is inverted — **the development key is published
on purpose** in `.env.example` and denied by fingerprint. A production
process refuses to start holding it, the default `JWT_SECRET`, the published
object-store secret, a non-`Secure` refresh cookie, or a CORS allow-list
still naming localhost. All problems reported in one message, at import.

Publishing the dev key also removes the *motive* for the banned behaviour:
nobody needs a real key to get a working laptop.

The refusal is at boot, not first use, because a lazily-validated key lets a
process start, pass its health check, take traffic, and die on the first
patient — with whatever it wrote first already committed under the wrong key.

**Security headers.** A raw ASGI middleware (not `BaseHTTPMiddleware` — it
runs on every request and would add an anyio task pair to each) sets HSTS,
`default-src 'none'` CSP, `nosniff`, `DENY`, `no-referrer`, and `no-store`
on every PHI response. Interactive docs are off in production.

Two details that are easy to get subtly wrong, both tested:

- **HSTS is not sent over plain-http localhost.** A browser that receives it
  pins localhost to https for the full max-age across *every port*, breaking
  every other local project on the machine, with no practical undo. It is
  emitted on `X-Forwarded-Proto: https` or in production.
- **Swagger UI is exempt from the API CSP**, which would otherwise render it
  blank — and it is served only outside production anyway.

**`phi_cipher()` is now cached** (`lru_cache`), where it was previously
rebuilt on every single encrypted column read and write. Decision 0029
measured one patient search decrypting the entire directory; a fresh key
schedule per value there was pure overhead.

## The rehearsal, and what it measured

Not an estimate. Run end to end against a real Postgres 16 (Docker,
`alembic upgrade head`, application and database on the same host), seeded
with **17,500 rows holding 35,000 encrypted values and 1.73 GB of
ciphertext** — about six months of a clinic running 40 consultations a day.

**Full rotation: 181.0 s (3 min 02 s).** Then **35,000 of 35,000 values
verified under the new key alone, and 0 of 35,000 readable under the old** —
the assertion that actually proves the rewrite happened.

| table | rows | values | ciphertext | rotate |
|---|---|---|---|---|
| `patients` | 5,000 | 5,000 | 0.6 MB | 5.1 s |
| `notes` | 5,000 | 20,000 | 13.5 MB | 7.5 s |
| `note_revisions` | 2,500 | 5,000 | 2.3 MB | 3.6 s |
| **`transcripts`** | **5,000** | **5,000** | **1,714 MB** | **164.8 s** |
| **total** | **17,500** | **35,000** | **1,731 MB** | **181.0 s** |

### Two findings that changed how this is framed

**Rotation cost is bytes, not rows.** Transcripts are 14% of the values and
91% of the time. So the checklist's "re-encrypt every row" is not the
O(patients) problem it sounds like — it is O(recorded minutes retained), and
it grows with the retention window rather than the practice. **Phase 4.4's
retention deletion is therefore also a rotation-cost control:** an expired
transcript is a row that never has to be rewritten again.

**Crypto is not the bottleneck — again.** The same scan, three ways over the
same data:

| what ran | time |
|---|---|
| read + decrypt every value (`--verify-only`) | 16.5 s |
| read + decrypt + re-encrypt, no writes (`--dry-run`) | 26.7 s |
| read + decrypt + re-encrypt + `UPDATE` (full run) | **181.0 s** |

Fernet is **27 s of 181 s (15%)**; the other 85% is Postgres rewriting
TOAST-ed text. This is the second time a measurement here has moved the
blame off decryption (0029 found ORM hydration dominating patient search),
and it settles part of the 🧠 directly: **neither `pgcrypto` nor a KMS would
make a rotation meaningfully faster**, because none of them reduce the bytes
Postgres has to write.

*Extrapolated, and labelled as such:* the rewrite ran at ~10 MB/s of
transcript ciphertext and is linear, so a year of the same clinic is roughly
six minutes. Rotation stops being comfortable around 18 GB of retained
transcript — the trigger 0031 names for reconsidering KMS.

## Verification

**API: 324 passing, 0 failing** — 33 of them new here (20 in
`test_key_rotation.py`, 13 in `test_security_headers.py`); the rest of the
growth from 206 is Phases 4.2–4.4 landing alongside. `ruff check .` and
`mypy app` clean.

A note on how that number was obtained, because the first attempts were
misleading. `tests/conftest.py` pins the test database to one SQLite file
per checkout, and `_fresh_schema` drops and recreates every table before
each test — so two concurrent runs make each other fail with "no such
table" in entirely unrelated files. With four phases being built in
parallel there were six `pytest` processes against that one file, producing
37 failures that had nothing to do with any of the code. `conftest.py` now
reads an optional `TEST_DB_PATH`; the default is unchanged, and the run
above used its own file.

The production-boot refusals are asserted **in a real subprocess**, not by
constructing a `Settings` object — importing `app.main` with a production
environment and a development key, and checking the process exits non-zero
with the reason on stderr. `cwd` is a temp directory, because `Settings`
reads a relative `.env` and a developer's own file must not decide the
outcome:

| | |
|---|---|
| development starts on the published key, docs on | pass |
| production refuses the published development PHI key | pass |
| production refuses a repository key hiding in `PHI_ENCRYPTION_KEY_PREVIOUS` | pass |
| production refuses to start with no PHI key at all | pass |
| production refuses the default `JWT_SECRET` | pass |
| production refuses a non-`Secure` refresh cookie | pass |
| production refuses a CORS allow-list naming localhost | pass |
| production serves no interactive docs | pass |
| a malformed key is rejected at boot, not at the first patient | pass |
| the same key as both current and previous is rejected | pass |
| **a correctly configured production process does start** | pass |

Rotation itself is tested against a real database end to end: every one of
the 8 columns rewritten, plaintext byte-identical afterwards, readable under
the new key and **not** under the old, idempotent across repeated runs,
`--dry-run` writing nothing, `--verify-only` catching a row the rotation
never reached, an undecryptable value failing the run rather than being
skipped, and no key material in the output.

## Notable bugs caught

- **The rotation script leaked its database connection.** It creates its own
  engine, and without disposing it the pooled connection outlived `main()`.
  On Postgres that is a lock the next tool waits on; on SQLite it blocked
  the test suite's `drop_all` outright, which surfaced as a cascade of
  unrelated "no such table: notes" failures in later tests. Fixed with a
  `try/finally` dispose — correct for any script that opens an engine.
- **`Fernet` was being reconstructed for every encrypted value.** Not a bug
  that produces wrong answers, which is why it survived four phases: every
  read and write of every PHI column rebuilt the key schedule from base64.
  Now cached, with an explicit reset for the tests that swap keys.

## Open follow-ups

- **The DPO question is open by design.** 0031 records the implementation
  choice and names the three things only Remedy's DPO can settle: HSM/KMS
  key custody, splitting key access from deploy access, and a rotation
  cadence. Ask before wider rollout.
- **Anyone who can deploy can read all PHI.** The key is an environment
  variable in the same deployment the app lives in. No amount of rotation
  discipline fixes that; only a KMS does.
- **Rotation issues one `UPDATE` per row.** 17,500 round trips, and the
  reason 85% of the runtime is the write. Batching would help, but three
  minutes is not a problem worth the added failure modes today.
- **`--batch-size` defaults to 500**, which holds up to ~170 MB of
  transcript ciphertext in memory per batch. Fine on a workstation; the
  runbook says to lower it on a small instance. It could adapt to column
  width instead of being a flat row count.
- **Phase 5 owes the transit half.** TLS termination, http→https redirect,
  a TLS 1.2 floor with modern ciphers, `X-Forwarded-Proto` set by the proxy
  and settable by nobody else, and TLS to Postgres/Redis/object storage.
  None of it is assertable from inside the app; the runbook lists it
  explicitly rather than letting the app's green headers imply it is done.
- **`Clinician.mfa_secret` is still not encrypted.** Deliberate (it is a
  credential, not PHI, per its own comment) but it is the one secret at rest
  that the rotation script does not cover, and worth naming alongside the
  KMS question.
- **HSTS preload is off.** Turning it on is close to irreversible and is
  Remedy's call once the domain is settled.
