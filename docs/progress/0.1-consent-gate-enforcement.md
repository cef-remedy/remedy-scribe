# Phase 0.1 — Enforce the consent gate server-side

**Status:** done · **Date:** 2026-08-25 · **Commit:** `966bfda`
**Related decisions:** [0001](../decisions/0001-consent-ledger-read-model.md),
[0002](../decisions/0002-consent-violation-is-terminal-not-retried.md),
[0003](../decisions/0003-mid-visit-reconsent-detection.md) (open)

## Why this was first

Nothing server-side stopped an encounter from being uploaded and
transcribed with **zero** consent records — that rule lived only in the
mobile client's UI, which is exactly where a legal/compliance control must
not live, since the client is the part a bug or an attacker controls. This
closes that gap before anything else gets built on top of it.

## What changed

- **New `app/services/consent.py`** — `assert_consent_valid(db, encounter_id)`.
  The single place that answers "is it currently legal to touch this
  encounter's audio?" Reads every `ConsentLedgerEntry` row for the
  encounter in chronological order and folds over it (`given` → true,
  `declined`/`withdrawn` → false) rather than querying for "the latest
  `given` with no later `withdrawn`" — avoids a timestamp-tiebreak edge
  case and treats `declined` uniformly with `withdrawn`.
- **`app/api/routes/encounters.py`** — `confirm_upload` calls
  `assert_consent_valid` before setting `audio_object_key`; a
  `ConsentNotValidError` becomes **409** (a state problem, not a
  permissions problem — hence not 403).
- **`app/tasks/pipeline.py`** — `transcribe_encounter` re-checks consent at
  its own head, in a dedicated `except ConsentNotValidError` clause,
  separate from the generic retry-on-any-exception handler. On failure it
  sets `pipeline_status = "blocked_no_consent"` and returns — it does
  **not** retry, because a missing/withdrawn consent won't become valid by
  waiting 30 seconds.
- **`tests/test_consent_gate.py`** — 9 tests: the ledger-fold logic in
  isolation, the `confirm_upload` HTTP boundary (409 vs 200, with
  `run_pipeline` monkeypatched so the test doesn't need a live Celery
  broker), and the task-level defense-in-depth (including a "withdrawn
  mid-flight" race).

## How the pieces connect

```
ConsentLedgerEntry (Postgres, append-only, trigger-enforced)
        │  read by
        ▼
assert_consent_valid()  ←── shared by both enforcement points below
        │                          │
        ▼                          ▼
confirm_upload (HTTP)       transcribe_encounter (Celery task)
  409 on invalid               terminal "blocked_no_consent" on invalid,
                                not retried
```

The ledger itself was already real and already trigger-protected (Postgres
`BEFORE UPDATE/DELETE` trigger rejects mutation unconditionally, even for
the table's owning role) — what was missing was anything *reading* it
before doing something consequential. There are now two checkpoints
instead of zero: one at upload-confirmation time, one at the moment the
async pipeline actually touches the audio, because consent can be
withdrawn in the gap between those two moments (queue backlog, retry
delay, worker restart).

## Tests

9 new tests in `tests/test_consent_gate.py`; full suite (18 tests at this
point) passing on SQLite.

## Notable follow-ups

- `pipeline_status` gained one more free-form string value
  (`"blocked_no_consent"`) on top of the ones already there — flagged for
  Phase 0.4's enum conversion so it isn't dropped.
- Decision 0003 (mid-visit re-consent: manual flag vs. diarization-based
  detection) is explicitly left open — it's a Phase 2.3 product/UX call,
  not something this phase's code touches.
