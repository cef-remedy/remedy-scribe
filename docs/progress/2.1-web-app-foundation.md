# Phase 2.1 — Web app foundation (client re-platformed)

**Status:** done · **Date:** 2026-08-27
**Related decisions:** [0024](../decisions/0024-web-client-on-laptop-not-mobile.md)
(browser client on a clinic laptop — user + measurement), [0025](../decisions/0025-audio-format-mono-opus-32kbps.md)
(mono Opus at 32 kbps — user), and an **amendment to
[0006](../decisions/0006-mobile-token-storage-and-revocation.md)**: the shape
survives, `expo-secure-store` becomes an httpOnly cookie.

## What changed

### The client is a browser app now

`apps/mobile/` (Expo) is **deleted**; `apps/web/` replaces it. Deleted rather
than kept dormant, consistent with how decisions 0018 and 0021 handled
superseded alternatives — git history is the archive.

This was not a preference. The supervisor answered the PRD's open question
*"What devices do doctors actually carry?"* — laptops — and both reasons
`tech-stack.md` §1 gave for rejecting a web client were phone-specific
("mobile browsers suspend microphone capture"; "a phone app is the framing
throughout the PRD's user stories"). Decision 0024 has the full accounting,
including the 29-minute harness run on real hardware that measured **0.05s of
audio lost across 131s of backgrounding**.

The biggest saving is one that does not appear as a feature: `tech-stack.md`'s
Expo-custom-dev-client decision existed *solely* to host native background-audio
modules. With a laptop that entire branch — Android Studio, foreground services,
`AVAudioSession`, a Mac and a paid Apple account for iOS, and the checklist's
"genuine time sink" warning — does not exist rather than being solved.

### Backend: two things a browser needs that a native client never did

Both fail *silently*, which is why both got tests rather than a manual check.

- **CORS** (`app/main.py`). Without it the preflight is rejected and the
  request never reaches a route, so nothing appears in the API log at all —
  the failure presents as a frontend bug. `allow_credentials=True` is
  required for the refresh cookie to be sent, and per the CORS spec it is
  mutually exclusive with `allow_origins=["*"]`, hence an explicit
  allow-list from settings (`cors_allow_origins`).
- **httpOnly refresh cookie** (`app/api/routes/auth.py`). `/login` sets it,
  `/refresh` reads and rotates it, `/logout` clears it. The refresh token is
  still returned in the response body for non-browser callers and the Phase
  0.3 tests; the web client ignores that field entirely.

### Frontend

- `apps/web/` — Vite + React 19 + TypeScript, React Router, `vite-plugin-pwa`
  for the offline shell (P0-2 requires the app to work with no network).
- **API client generated, not written.** `openapi-typescript` turns the live
  schema (22 paths, 31 components) into 1583 lines of types; `openapi-fetch`
  provides a ~2 KB typed runtime. Regenerate with `npm run api:types`. This
  is the item that survived the re-platform completely untouched, and the
  payoff `tech-stack.md` promised for splitting Python from TypeScript: a
  renamed backend route now fails `tsc`, not a clinic.
- `src/api/client.ts` — the only module that talks to the API, and the only
  one that holds the access token (a module variable, never React state,
  never `localStorage`).
- `src/lib/auth.tsx` — auth context tracking *whether* there is a session,
  never the credential.
- `src/lib/audio-config.ts` — decision 0025's constants, plus
  `assertAudioSettings()`, ready for 2.2.
- `src/components/Banner.tsx`, `ErrorBoundary.tsx`, `src/lib/offline.ts` —
  the error/offline primitives. Persistent banners rather than toasts: a
  toast that vanishes in three seconds *is* silent failure for a doctor who
  was looking at a patient at the time.

### Tests

- `apps/api/tests/test_web_client_support.py` — 10 tests: CORS preflight
  granted for an allowed origin, not granted for an unknown one, never a
  wildcard; the cookie set httpOnly and path-scoped; the access token *not*
  in a cookie; refresh working from the cookie alone with an empty body;
  body-token precedence asserted directly; logout and rejected-refresh both
  clearing the cookie.
- `apps/web/smoke/auth-flow.cjs` — a 17-check end-to-end run through a real
  browser against the live API, with a hand-rolled RFC 6238 TOTP generator
  so it can produce live codes without adding a dependency.

## How the pieces connect

```
                    ┌──────────────── apps/web (Vite/React) ───────────────┐
                    │                                                      │
  docs/api/         │  src/api/schema.d.ts   <-- generated, never edited   │
  openapi.json ─────┼─>  (npm run api:types)                               │
  (exported from    │            │                                         │
   the live app)    │            v                                         │
                    │  src/api/client.ts                                   │
                    │    - access token: module variable, in memory only   │
                    │    - authedFetch: adds Bearer, credentials:"include" │
                    │    - on 401 -> single-flight refresh -> retry once   │
                    │            │                                         │
                    │            v                                         │
                    │  src/lib/auth.tsx  ->  App.tsx route gate            │
                    └────────────┼─────────────────────────────────────────┘
                                 │  CORS + credentials
                                 v
        ┌──────────────── apps/api (FastAPI) ─────────────────┐
        │  CORSMiddleware(allow_credentials=True, allow-list) │
        │  POST /auth/login    -> body: access_token          │
        │                         Set-Cookie: httpOnly refresh│
        │  POST /auth/refresh  -> reads cookie, ROTATES it    │
        │  POST /auth/logout   -> revokes + clears cookie     │
        └─────────────────────────────────────────────────────┘
```

The session-resume path is worth tracing explicitly, because it is the whole
reason the token model works:

1. Doctor reloads the page. The access token was in memory — it is gone.
2. `AuthProvider` mounts in state `checking` (not `signed-out`: showing the
   login screen here would flash a sign-in prompt at an already-signed-in
   doctor on every reload).
3. `restoreSession()` → `POST /auth/refresh` with an **empty body** and
   `credentials: "include"`.
4. The *server* reads the httpOnly cookie, rotates it, returns a fresh
   access token.
5. State becomes `signed-in`. No credential was ever readable by JS.

## Bugs caught by running it

**1. Refresh-token precedence was backwards.** My first version preferred the
cookie over an explicitly-presented body token. `TestClient` keeps a cookie
jar, so four Phase 0.3 tests broke — and not cosmetically: a caller naming a
deliberately-stale token got the *valid cookie* rotated instead, returning
200 where reuse detection required 401. Worse in production terms,
single-session logout would revoke whichever session the cookie happened to
hold rather than the one named. Body-first is now the rule, documented at the
precedence site and asserted by its own test. Body-first costs nothing in the
browser: httpOnly guarantees XSS cannot *read* the cookie, which precedence
does not affect.

**2. Cookie-clearing on the error path never reached the browser.** Mutating
the injected `response` and then raising `HTTPException` silently discards
the mutation — FastAPI builds a fresh response for the exception. So the
"clear the dead cookie" logic did nothing, and a rejected refresh would leave
a dead cookie guaranteeing every subsequent silent renewal failed
identically instead of falling through to a real login. Fixed by carrying the
header on the exception, serialized via Starlette's own `delete_cookie`
rather than hand-rolled. The logout test passed throughout, precisely because
logout returns normally — which is what made this easy to miss.

**3. A 422 was indistinguishable from wrong credentials.** Both rendered as
"Could not sign in. Please try again.", which sends a doctor to re-check
their password when the real problem is the email address. Reachable by a
real user, not only a buggy client: `a@b.test` passes the browser's own
`type="email"` validation, but pydantic `EmailStr` rejects RFC 2606 reserved
TLDs. Found because my own smoke fixture used `doc@remedy.test` and got a
422 — the fixture was my bug, the unhelpful message was the app's.

## Deliberately deferred, not dropped

**Biometric unlock on resume.** The checklist item assumed a personal phone.
On a *shared* clinic laptop, WebAuthn (Windows Hello / Touch ID)
authenticates the machine's logged-in user — so if several doctors share one
Windows session, a biometric prompt proves nothing about which doctor is
signing. That is arguably worse than having none, because it looks like proof
of identity. It needs an answer to "do doctors share a Windows login?" first,
and it interacts with signing (2.6), where "who signed this note" is a
medico-legal question rather than a UX one. Recorded as a 🧠 in checklist 2.1.

## Open follow-ups

- **Cookie flags are dev-safe, not prod-safe.** `refresh_cookie_secure`
  defaults to `false` for local `http://`. It **must** be `true` anywhere
  real, and `samesite=none` is only correct if the API and client end up
  cross-site. Phase 5.1 owns this; flagged here so it is not discovered by a
  security review.
- **`assertAudioSettings()` is written but nothing calls it yet** — 2.2 wires
  it in. Named here so it is not mistaken for dead code.
- **The service worker precaches assets but caches no API responses,** by
  design: every API response is PHI or auth-bearing, and a service-worker
  cache is readable by anyone with the device. Offline *data* is Phase 2.4's
  IndexedDB queue with a real retention clock, not opportunistic caching.
- **The smoke test needs a seeded clinician and both servers running**, so it
  is not part of `pytest`. Commands are in the file's header comment. Worth
  wiring into CI (Phase 5.3) once there is a staging environment to point it
  at.
