**Runbook:** [observability](../runbooks/observability.md)

Every request, task and sweep now carries a correlation ID, every stage
reports its own latency and cost, and seven alert rules run every five
minutes. But the phase is really about one property, and the checklist
puts it in a ⚠️ rather than a bullet:

> **A log line or an error report cannot carry PHI by accident.**

## Two corrections to the checklist's wording

5.2 says "correlation IDs threaded from **mobile** request" and "error
tracking on both API and **mobile**." There is no mobile client. Decision
[0024](../decisions/0024-web-client-on-laptop-not-mobile.md) re-platformed
this to a browser web app on a clinic laptop, and the correlation ID is
threaded from the **browser** request. The web half of error tracking is
`apps/web/src/lib/telemetry.ts`, not an EAS build.

## The rule that drove every decision

**A rule that lives in a comment is enforced by memory, and memory is not
a control.**

That is not an abstraction here. This codebase has leaked PHI into a log
path twice, and both times the author had thought about PHI:

- `_extract_tool_input` interpolated an entire model response into an
  exception message, which `_mark_stage_failure` wrote to
  `Encounter.last_pipeline_error` — an **unencrypted** `String(500)`.
  Generated clinical prose, in the clear (docs/progress/4.0).
- That column's own comment argued it was safe because pipeline exceptions
  are "never something built from transcript or note content." True when
  written. False a phase later. Nothing noticed.

So the scrubbing here is **mechanical, not a convention** — with one gap,
named below, that is closed by a test rather than by a scrubber.

## What was built

### Backend

**`app/core/observability.py`** — three enforcement boundaries a careless
call site passes through whether it wants to or not:

- **`logging.setLogRecordFactory`** (`configure_logging`). There is exactly
  one record factory per process and `Logger.makeRecord` always calls it,
  so there is no handler configuration and no third-party library that can
  route around it. It rebuilds each record from its **template** rather
  than its interpolated message: with `%`-style args — how every existing
  log call in this repo is written — `record.msg` is a source literal and
  only `record.args` vary, so scrubbing the args and interpolating
  afterwards preserves every existing line while making its values safe. It
  also pre-renders a scrubbed traceback into `record.exc_text`, which
  `logging.Formatter` prefers and never re-formats.
- **`PHISafeJSONFormatter`** *assembles* the line from `LOGGABLE_FIELDS`
  rather than filtering a denylist. `extra={"transcript": ...}` emits the
  field's **name** in `dropped_fields` and nothing else. No allow-listed
  field can hold free text — they are opaque IDs, measurements and enum
  values — which is what makes `log_event` PHI-free by construction.
- **`_before_send`** — the Sentry transport, configured *before* a DSN
  exists. Strips `request` (bodies, cookies, headers), all breadcrumbs,
  non-allow-listed `extra`, and every stack frame's `vars`.

Plus `sensitive_scope` / `register_sensitive` for the leak shape no
scrubber can recognise by shape (see below), `safe_exception_summary` for
the unencrypted column, `stage_timer`, and `CorrelationIdMiddleware`.

**`app/core/metrics.py`** — the snapshot, the seven alert rules, the cost
model, and `python -m app.core.metrics`, a terminal dashboard. Samples live
in Redis (already in the stack as the broker), keyed by encounter so a
redelivered task cannot double-count — the same idempotency the pipeline
itself has.

**`app/tasks/pipeline.py`** — correlation threaded explicitly into both
task signatures, per-stage timing, the per-consult cost estimate, the
scrubbed write to `last_pipeline_error`, and `monitor_pipeline_health`:
the job that watches the two jobs that exist because nothing was watching.

**`app/main.py`** — `configure_logging` at import (before anything can log),
`init_error_tracking` in `lifespan`, and `CorrelationIdMiddleware` added
**outermost**, so it sees the responses `CORSMiddleware` short-circuits.
That ordering is the point: Phase 2.1's own note was "the preflight is
rejected and the request never reaches a route, so nothing appears in the
API log at all", and a request logger mounted inside CORS reproduces
exactly that blind spot.

### Frontend

**`apps/web/src/lib/telemetry.ts`** — dependency-free, because
`package.json` is not this phase's to change and because `@sentry/react`'s
defaults are precisely what the backend spends its effort switching off. It
wraps `window.fetch` to stamp `x-correlation-id` on API requests (and only
API requests — a presigned S3 `PUT` goes to a different origin, where an
unexpected header breaks the signature), remembers the ID the server
echoes, and installs `error` / `unhandledrejection` handlers. Reports carry
error class, a scrubbed message, stack **frame lines only**, the
correlation ID and the route path.

Wrapping `fetch` rather than editing the API client is the same argument as
putting the scrubber in the record factory: a header added at one call site
is a convention every future call site can forget; a header added at the
transport is a property of the program.

## How the pieces connect

A doctor taps **Finish**. The browser mints `web-4f2a…` and sends it on the
upload-confirm request. The API adopts it (after checking it against
`[A-Za-z0-9_.:-]{1,64}` — an inbound header is attacker-controlled text
headed for a log line, and log injection is how someone edits the record of
their own visit), binds it for the request, and echoes it back.
`run_pipeline` reads it from the ambient context and writes it into **both**
Celery signatures, because a `ContextVar` does not survive serialisation
into Redis. Twenty minutes later `generate_note` runs in a different
process and logs under the same ID.

**What correlation means for the two Beat sweeps.** Neither has an inbound
request, and leaving the field blank would make the one part of the
pipeline nobody triggered also the one part nobody can trace. Each mints a
**run ID** — `sweep-stuck-…`, `sweep-retention-…`, `monitor-…` — covering
everything that run touches, and every encounter a sweep re-kicks inherits
it. That answers a question a request ID cannot: *what else did this same
run touch?* A burst of failures sharing one `sweep-` ID is a broker or
worker problem; the same failures spread across many IDs is a per-encounter
problem. A re-kicked encounter deliberately does **not** adopt its original
upload's request ID — a run identifier and a request identifier are
different things, and merging them would let one sweep of 200 encounters
claim 200 unrelated requests.

## The gap, stated plainly

A **short, unregistered** piece of free text — `logger.info(f"patient
{name}")` — is shape-indistinguishable from `"Connection refused"`. No
scrubber can separate them. Anything that claims to is a denylist.

Two things address it, and neither is a scrubber:

- **`sensitive_scope`** recognises PHI by *identity* rather than shape: the
  process is holding the exact string, so it can be replaced. Each pipeline
  task opens a scope **outside** its `try` — deliberately, so the `except`
  that writes `last_pipeline_error` is inside it — and registers transcript
  segments and generated note sections the moment they exist. Scoped, not
  global: a process-wide registry of PHI strings *is* a PHI store.
- **`test_no_source_file_logs_an_f_string`** scans `app/**/*.py` and fails
  the build on any `logger.*(f"…")`. Ruff's `G004` is not in this repo's
  narrow selected rule set, so the ban lives in the suite — where a rule
  that only lived in a style guide is exactly the kind Phase 4.0 showed
  nobody remembers.

**So: mechanical, with one honest exception.** Structured fields cannot
leak. Prose over 200 characters is replaced by its length and digest — not
truncated, because the first 200 characters of a generated Assessment is
still a generated Assessment. Registered values are replaced wherever they
appear. Short unregistered free text outside a sensitive scope would still
be emitted, and its only defence is that the construct producing it fails
the build.

**Frame locals are the one worth naming twice.** `include_local_variables`
defaults to **True** in sentry-sdk. A frame inside `generate_note` holds
`transcript` — every segment of a verbatim consultation — and a frame
inside `_build_section` holds the generated note. Nothing about the failing
code has to be PHI-related for that to fire: an unrelated `AttributeError`
anywhere down that call stack ships the whole consultation to a third
party, in a field nobody looks at, from code that never mentions logging.
It cannot be fixed by being careful with exception messages. It is off at
`init`, and the test asserts the kwarg rather than trusting the docs.

### The cost finding

Real numbers from `estimate_consult_cost`, against the PRD's <$0.10:

| consultation | ASR | note gen | total |
|---|---|---|---|
| 10 min | $0.0185 | $0.0013 | **$0.020** |
| 30 min | $0.0555 | $0.0028 | **$0.058** |
| 45 min | $0.0833 | $0.0039 | **$0.087** |
| 60 min | $0.1110 | $0.0050 | **$0.116** |

**Break-even is 51.7 minutes of audio.** ASR is 15–23× note generation
across the whole range, because Groq bills Whisper per *audio-hour* and
`gpt-oss-120b` per *token*. So the PRD's cost target is really a
**duration** budget, and no amount of prompt tuning moves it — generation
is 5% of the bill. A typical 20–30 minute consultation lands at $0.04–$0.06,
comfortably inside target; an hour-long one is not, and nothing in the
product currently tells anyone that.

### What could not be run here, stated plainly

- **No live Sentry DSN exists** — nobody has provisioned an account. The
  init options and the scrubbing hook are tested against a fake SDK, which
  proves *what this codebase passes and strips*; it does not prove Sentry
  behaves as documented on receipt. The runbook's step 4 is that check.
- **The web envelope transport has never reached a real DSN.** It is a
  direct implementation of Sentry's envelope protocol with no npm
  dependency; if it silently drops events, that is the first thing to
  suspect.
- **The cost figures are estimates, not measurements.** Token counts are
  inferred from character counts because neither Groq client reads the
  `usage` block the vendor already returns.
- **No web test exists for `telemetry.ts`.** `apps/web/src/lib/telemetry.test.ts`
  is the file that should hold one; it was outside this phase's lease.

## Notable bugs caught

- **The latency series would have been silently empty.** The first version
  read `timing["duration_ms"]` from inside each task's own `finally` to
  record a metric sample. A task's `finally` runs *before* the enclosing
  context manager's `__exit__`, so `stage_timer` had not computed the
  duration yet and every sample would have been skipped — with no error,
  no failing test, and a dashboard reporting "no samples" forever. Fixed
  with an explicit `on_finish(duration_ms, status)` hook, which also keeps
  `observability.py` from importing `metrics.py` (that import is circular:
  metrics logs through observability).
- **`sensitive_scope()` with no values leaked registrations across tasks.**
  It returned early without setting a `ContextVar` token, so a later
  `register_sensitive` mutated the *caller's* context instead. In a Celery
  prefork worker — thousands of tasks, one process, one context — one
  patient's transcript would have stayed registered while the next
  patient's task ran. Harmless in effect (over-redaction), but an unbounded
  in-memory PHI store, which is worse than the problem the scope exists to
  solve. The scope now always establishes a boundary; a test asserts it.
- **A naive digit-redaction rule ate encounter IDs.** `\d{7,}` matches a
  UUID's twelve-digit trailing group, so every `550e8400-…-446655440000` in
  a log line would have been mangled — destroying the exact identifier this
  phase exists to correlate on, in the name of catching phone numbers.
  Fixed with lookarounds that exclude hyphenated hex; a test asserts a UUID
  survives a call that also redacts prose.
- **The allow-list filter and the formatter disagreed about "dropped".**
  The filter blanked non-allow-listed fields to `None` and the formatter
  skipped `None`, so a dropped field vanished without ever being reported —
  safe, but it would have left a developer believing their field arrived.
  The filter now *removes* the attribute (so Sentry's `record.__dict__`
  harvesting cannot find the value either) and carries the **names** for
  the formatter to report.
- **`_QUIET_PATHS` was guessed, then checked.** It initially listed
  `/health/live` and `/health/ready`; the health router registers `/health`
  and `/ready`. Confirmed against the live router rather than left as a
  plausible-looking constant that would have logged every readiness probe.

## Open follow-ups

- **Nobody has provisioned Sentry.** Until a DSN exists, a `critical` alert
  is an ERROR line in a log file on a VM and nothing reads that file. This
  is the single largest gap in the phase and it is an account, not code.
  `sentry-sdk==2.35.0` is the requirements line when someone does.
- **The monitor runs inside the beat process it watches.** It catches beat
  alive with a wedged sweep — the common case — and not beat being dead.
  Closing that needs an external check (a supervisor restart policy or an
  uptime ping alerting on silence), which belongs to the deployment
  runbook.
- **Real token counts are two small changes away.** Read `usage` from the
  Groq ASR and note responses, persist `tokens_in` / `tokens_out` /
  `audio_seconds` on `Note` (a column and a migration), and
  `estimate_consult_cost` becomes `consult_cost`. Both files and the model
  were outside this phase's lease.
- **Cost and latency history lives in Redis, which is not durable here.** A
  `FLUSHALL` or a container rebuild loses it. The durable version is the
  same column as above.
- **Per-stage success/failure is inferred from terminal status.** An
  encounter that failed transcription three times, was retried by a human
  and then succeeded counts purely as a success, so the snapshot
  *understates* the failure rate. The per-attempt truth is emitted as
  `pipeline.stage.*` events; joining the two needs the log pipeline that
  does not exist yet.
- **`COST_CHARS_PER_TOKEN = 4.0` is the weakest number in the model**, and
  wrong in the optimistic direction for this product specifically: Taglish
  tokenises worse than English on a vocabulary trained mostly on English.
  One real Groq response with a `usage` block settles it.
- **Registering PHI at decryption would close the last gap.** Doing it in
  `EncryptedString.process_result_value` would cover every read of every
  PHI column with no call-site discipline at all. It puts a substring scan
  on the hot path of every PHI read, so it belongs behind a measurement —
  and behind evidence that the f-string ban is not already sufficient.
