**Status:** done · **Date:** 2026-08-25 · **Commit:** `a3f1cd6`
**Related decisions:** [0006](../decisions/0006-mobile-token-storage-and-revocation.md)

## Why this was next

`ACCESS_TOKEN_EXPIRE_MINUTES=30` with no refresh path meant a doctor got
logged out mid-consultation roughly twice per clinic session. The TOTP
secret could only be created by a seed script — no self-service
enrollment. `POST /auth/login` had no rate limiting or lockout at all.

## The 🧠 decision (user's call)

**Where does the token live on the device?** Decided: `expo-secure-store`
(Keychain/Keystore) for the refresh token, in-memory only for the access
token, with server-side revocation for the lost-phone case rather than
"wait for expiry." Access token TTL: **15 minutes** (down from 30), refresh
token TTL: **12 hours**. Reasoning in full: decision 0006 (the call) and
0007 (the specific numbers).

## What changed

- **`app/models/refresh_token.py` + `app/services/refresh_tokens.py`** —
  refresh tokens are opaque random values (`secrets.token_urlsafe(32)`),
  stored only as a SHA-256 hash (never the raw value — same principle as
  password hashing, minus the deliberate slowness since this is a
  high-entropy value, not a guessable password). Rotate on every use:
  each refresh both retires the presented token and issues a new one.
- **Reuse detection, with a specific distinction that mattered:** presenting
  a token that already has a successor (`replaced_by_id` set) revokes
  **every** live session for that clinician — a legitimate client never
  replays a token it already exchanged, so this is treated as theft.
  Presenting a token that's merely revoked-with-no-successor (a clean
  logout, an admin's revoke-all) is just rejected, with no cascade. See
  "Notable bugs caught" below for why this distinction exists.
- **New routes on `app/api/routes/auth.py`:**
  - `POST /auth/refresh` — silent renewal, no password/MFA, no
    Authorization header (the access token being renewed may already be
    expired — that's the point).
  - `POST /auth/logout` — revokes exactly the one refresh token presented.
  - `POST /auth/clinicians/{id}/revoke-sessions` — **admin-only**; the
    lost-phone path. Kills every refresh token for that clinician
    immediately. Already-issued access tokens still work until they
    naturally expire (≤15 min) — there's no access-token blacklist.
  - `POST /auth/mfa/enroll` + `POST /auth/mfa/enroll/confirm` — two-step
    enrollment: step 1 verifies password and writes a *pending* secret
    (`Clinician.mfa_secret_pending`, new column) and returns its
    `otpauth://` provisioning URI; step 2 requires one valid code against
    the pending secret before it's promoted to the real `mfa_secret` that
    login actually checks. Blocked entirely if `mfa_secret` is already
    set — re-enrollment is not self-service (decision 0009).
- **`app/services/auth_rate_limit.py` + `app/models/login_attempt.py`** —
  every login attempt (success or failure) is appended to a
  `login_attempts` table. Two independent checks fold over time-windowed
  slices of it: per-IP rate limit (10/minute, catches flooding/spraying
  across accounts) and per-email lockout (5 failures/15 minutes, catches
  distributed guessing against one account). Both checks run **before**
  any password/MFA verification, so a request that's going to be
  rejected never touches credential checking.
- **`app/core/config.py`** — new settings:
  `access_token_expire_minutes` (30→15), `refresh_token_expire_hours` (12),
  `login_rate_limit_per_ip_per_minute` (10), `login_lockout_threshold` (5),
  `login_lockout_window_minutes` (15).
- **Alembic migration** `c3d4e5f6a7b8_auth_hardening.py` — `refresh_tokens`,
  `login_attempts` tables; `clinicians.mfa_secret_pending` column.
- **`tests/test_auth_hardening.py`** — 13 tests.

## How the pieces connect

```
POST /auth/login (password + TOTP, rate-limited + lockout-checked first)
        │
        ├── access_token  (JWT, 15 min, stateless — never in a DB row)
        └── refresh_token (opaque string, 12 hr)
                  │  hash stored in
                  ▼
            refresh_tokens table ── revocable, unlike the JWT
                  │
        ┌─────────┼──────────────────────┐
        ▼         ▼                      ▼
  POST /refresh  POST /logout    POST /clinicians/{id}/revoke-sessions
  (rotate: old    (revoke just    (admin-only — lost-phone path: every
   → new, old      this session)   session for this clinician, dead now)
   flagged
   revoked)
```

The access/refresh split is the whole mechanism: a JWT is self-verifying
and nothing server-side can reach into a device and delete it, but it's
cheap to check on every request. The refresh token is the opposite
trade — a DB row, checked only on renewal, but revocable on command. Each
token type is used for the property it's actually good at.

## Notable bugs caught (both by the test suite, not by inspection)

1. **Reuse-detection over-triggering.** The first version nuked every
   session for a clinician whenever *any* revoked token was presented —
   which meant logging out device A killed device B's session too, since
   logout also sets `revoked_at`. `test_logout_revokes_only_that_session`
   failed immediately. Fix: only cascade when `replaced_by_id` is set —
   that field is *only* ever written by rotation, so it's the one signal
   that actually distinguishes "this token was already exchanged and
   someone's replaying the stale copy" from "this token was retired on
   purpose."
2. **SQLite tz-naive vs. tz-aware datetime comparison.** SQLite hands back
   naive `datetime`s even from a `DateTime(timezone=True)` column (it has
   no real `timestamptz` type — SQLAlchemy's tz-awareness there is
   write-only). Comparing a naive `expires_at` against
   `datetime.now(timezone.utc)` raised `TypeError` in tests, though it
   would have silently worked against Postgres. This is a live instance
   of the exact test-vs-production divergence Phase 0.5 is written to
   catch — found here by running the tests, not by reading the code.

## Notable follow-ups

- **MFA re-enrollment has no self-service path** (decision 0009) — a lost
  authenticator app currently has no fix short of direct DB access. This
  needs an admin-triggered reset endpoint (clear `mfa_secret`, force
  first-time enrollment again, audit-logged) before pilot — natural to
  build alongside `revoke-sessions` since it's the same "doctor lost their
  phone" support moment.
- Access-token revocation has an inherent ≤15-minute lag (no blacklist) —
  accepted deliberately, documented in decision 0007.
