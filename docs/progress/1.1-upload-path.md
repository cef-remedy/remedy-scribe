# Phase 1.1 — Upload path

**Status:** done · **Date:** 2026-08-25
**Related decisions:** [0013](../decisions/0013-presigned-multipart-upload-design.md)
(protocol — user's call), [0014](../decisions/0014-bucket-lifecycle-rule-shape-and-minio-limitation.md),
[0015](../decisions/0015-startup-bucket-provisioning-off-in-tests.md) (both bugs found empirically)

## The 🧠 decision (user's call)

**Build the upload protocol or adopt one?** Decided: **S3 multipart with
presigned part URLs** — the device PUTs audio bytes straight to S3/MinIO;
the API only mints URLs and metadata, never touches the bytes themselves.

## Why this was next

`boto3` was a declared dependency, imported nowhere. There was no upload
endpoint at all — the old `confirm_upload` assumed the audio was already
sitting in a bucket somewhere and just took the client's word for the
object key. Phase 1 can't start ("audio recorded on a device ends up as a
structured note, with no human in the loop") without a real upload path.

## What changed

- **New `app/services/storage.py`** — every boto3 call the upload routes
  need: `create_multipart_upload`, `presign_part_upload`,
  `list_uploaded_parts` (paginated), `complete_multipart_upload` (re-derives
  the parts list from S3 rather than trusting a client-reported one),
  `abort_multipart_upload`, `head_object`, and `ensure_bucket_configured`
  (idempotent create-if-missing + default encryption + a combined
  retention/orphan-abort lifecycle rule).
- **New `app/api/routes/uploads.py`** — `POST .../upload/init`,
  `POST .../upload/parts/{n}`, `GET .../upload/parts`,
  `POST .../upload/complete`. Supersedes and removes the old
  `POST /encounters/{id}/confirm-upload`.
- **`Encounter.audio_upload_id`** (new column + migration) — the S3
  multipart UploadId, set at `init`, cleared at `complete`. Its
  presence/absence is what makes both endpoints idempotent.
- **`app/main.py`** — migrated `@app.on_event("startup")` (deprecated) to
  a `lifespan` context manager; calls `ensure_bucket_configured()` there,
  gated by a new `S3_PROVISION_BUCKET_ON_STARTUP` setting (off in tests).
- **Removed**: `confirm_upload` route, `ConfirmUploadRequest` schema — the
  client-supplied `audio_object_key` they relied on is exactly what 1.1
  replaces (see decision 0013).
- **Tests:** `tests/test_upload_flow.py` (15 tests, storage mocked — fast,
  Docker-free: idempotency, RBAC, 404/409/502 paths) and
  `tests/test_storage_specific.py` (5 tests, real MinIO via testcontainers:
  an actual presigned URL PUT round-trip, abort, bucket lifecycle). Updated
  `test_consent_gate.py`'s two enforcement-point tests to target
  `upload/complete` instead of the removed `confirm_upload`; removed one
  test in `test_schema_constraints.py` that had no remaining route to test.

## How the pieces connect

```
POST /upload/init          -> server generates object_key, calls S3
                               CreateMultipartUpload, stores both on
                               the Encounter row (idempotent: retry
                               returns the same session)
        │
POST /upload/parts/{n}     -> presigned PUT URL (pure computation,
        │                      no network call) — device PUTs bytes
        │                      to S3/MinIO directly, never through
        │                      this API
        ▼
   [device uploads N chunks straight to object storage]
        │
GET  /upload/parts         -> S3's own ListParts — what's already
        │                      landed, for a resuming client to diff
        │                      against (no Postgres mirror table)
        ▼
POST /upload/complete      -> consent check FIRST (before touching S3 —
                               an invalid-consent upload is left
                               incomplete for the lifecycle rule to
                               reap, not finalized)
                            -> re-derive parts from ListParts, call
                               CompleteMultipartUpload
                            -> verify via HeadObject
                            -> retention clock, pipeline_status=UPLOADED,
                               clear audio_upload_id, kick run_pipeline
```

The load-bearing design point: **the server never trusts a client's
account of what happened.** The old flow trusted a client-supplied object
key outright. The new flow generates the key itself, and at completion
time re-reads S3's own `ListParts` rather than accepting a client-reported
`{PartNumber, ETag}` list — a party that never saw a part's PUT response
can't cause the server to finalize wrong.

## Tests

20 new tests (15 route-level + 5 real-MinIO); full suite: 69 passing
(44 SQLite + 5 Postgres + 15 upload-flow + 5 storage-specific — some
renumbering from replacing/removing the 3 obsolete confirm-upload tests).

## Notable bugs caught (all found by running things, not by reading)

1. **A lifecycle rule with only `AbortIncompleteMultipartUpload` is
   rejected by MinIO's schema validator.** The first version split
   retention-expiration and orphan-upload-abort into two separate rules;
   the second one raised `InvalidRequest`, caught only by
   `app/main.py`'s startup handler swallowing it into a log warning — a
   test asserting the rule actually landed is what caught this, not the
   absence of an exception. Fixed by combining both actions into one
   rule (empirically verified MinIO accepts that combination). See
   decision 0014.
2. **Even fixed, this MinIO version silently drops
   `AbortIncompleteMultipartUpload` from what it reports back** —
   confirmed by reading the raw `GetBucketLifecycleConfiguration`
   response directly. The `PUT` not raising is not proof of enforcement.
   Documented as an explicit, known gap rather than asserted around.
3. **A synchronous request-handling API must not use boto3's default
   timeouts.** Running `ensure_bucket_configured()` on every test's
   `TestClient` startup, against nothing listening, hung two full test
   runs past their 180-second limit before this was diagnosed. Fixed with
   short explicit timeouts on the shared client config *and* an explicit
   settings flag to skip bucket provisioning in tests entirely (decision
   0015) — the two fixes address different failure modes (a slow-but-real
   dependency vs. no dependency at all) and both were needed.

## Notable follow-ups

- Decision 0014's gap (MinIO abort-enforcement unverified) should be
  closed with a real check — either against actual AWS S3, or a newer
  MinIO image — before relying on the orphan-upload reaper in a real
  pilot.
- `abort_multipart_upload` exists in `storage.py` but isn't wired to a
  route — no "cancel this upload" button was asked for by 1.1. Cheap to
  add later if a real product need shows up.
- The heads-up about local audio only being safe to delete after both
  receipt *and* pipeline start: `upload/complete`'s response only returns
  after `run_pipeline()` has enqueued the Celery chain, which is a
  reasonable interpretation of "note generation has begun" at MVP
  fidelity — it does not wait for the task to actually start executing.
  Revisit if that distinction matters once Phase 1.5's failure handling
  exists.
