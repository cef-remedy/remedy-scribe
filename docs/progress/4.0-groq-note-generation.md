# Note generation moves from Anthropic Haiku to Groq

**Status:** done · **Date:** 2026-08-28
**Related decisions:** [0035](../decisions/0035-groq-note-generation.md) (the
swap, the model, and why the stated reason for it doesn't hold),
[0018](../decisions/0018-groq-whisper-instead-of-elevenlabs-scribe.md) (Groq already receives the
audio), [0021](../decisions/0021-haiku-only-luna-dropped.md) (the
"dead weight, not a safety net" principle this partly reverses),
[0030](../decisions/0030-grounding-is-withheld-not-approximated.md) (the
span invariant this had to preserve)

Requested as a cost change — Groq offers a free tier — and it is the right
change, but **not for that reason.** Both halves are covered below, because
acting on the stated rationale without checking it would have set up a
failure during the pilot instead of now.

## The premise, checked

**Groq's free tier cannot carry this workload.** It allows roughly **8,000
tokens per minute** on the candidate models. A 20–40 minute consultation
transcript is comfortably **10,000–20,000 tokens**, and note generation
sends the whole thing in one fused call — so a single real consultation
exceeds the per-minute allowance outright. Short visits would work. A
clinic day would not, and it would fail as intermittent errors rather than
an obvious quota wall.

**And the free tier is the tier with no data-protection undertaking.**
Groq's BAA covers "Covered Cloud Services", a definition that explicitly
excludes services *"provided for free or at no additional charge"* as well
as anything in preview status. For a system handling PHI under the Data
Privacy Act that is not a cost trade-off, it is a disqualifier.

So: **make the change, on a paid plan.** The recommendation is not "don't",
it is "budget for the Developer tier."

## The reason it's right anyway

Phase 1.3 already sends every consultation's **audio** to Groq for
transcription. Groq therefore already holds the most sensitive artifact in
the system. Generating the note there discloses **nothing new**, and it
collapses two AI processors into one: one DPA instead of two, one entry in
the processor disclosure, one vendor in the breach-response runbook (which
Phase 4.3 is writing right now), one outage mode instead of two.

Verified rather than assumed, from Groq's Services Agreement: *"Groq is not
permitted to use Inputs or Outputs for training or fine-tuning any AI Model
Services or other models"*, and by default it *"does not retain customer
data for inference requests"*, with Zero Data Retention available. That is
a stronger written position than the absence of one — and it already
applies to the transcript being sent today.

## What changed

**`note_generation/shared.py` (new)** — the prompt body, the JSON schema,
the mechanical `[INAUDIBLE]` substitution, server-side offset assignment
and citation verification, now used identically by both providers.

**`note_generation/groq.py` (new)** — Groq's OpenAI-compatible chat
completions endpoint with `response_format: json_schema, strict: true`.

**`note_generation/haiku.py`** — refactored onto the shared module,
demoted to configured fallback, and one security fix (below).

**`get_note_generator()`** — the swap point that decision 0021 kept "as a
function, not inlined... so a second provider is still a new class and one
`if`". That turned out to be exactly right; this change is a new class and
one `if`.

### The mechanism had to change, not just the model ID

Haiku pins the response shape with a forced tool call. Groq's docs are
explicit that **"Streaming and tool use are not currently supported with
Structured Outputs"** — the two are mutually exclusive there, so the naive
port (send `tools` *and* `response_format`) does not work.

Forced to choose, strict structured output is the **stronger** option:
constrained decoding means the model *cannot* emit a token sequence that
violates the schema, where a forced tool call still asks a model to fill a
schema correctly and hopes. For the one output the entire grounding feature
depends on, that is an upgrade.

Two costs, both handled. Arguments now arrive as a **JSON string** to
parse, so a response truncated at `max_tokens` returns HTTP 200 carrying
invalid JSON — named as `GroqNoteParseError` rather than left to surface as
a mystery 500. And strict mode rejects schemas missing
`additionalProperties: false` or an incomplete `required` list, which only
fails against a live key, so a test asserts the schema's shape recursively
instead.

### Why the sharing is a correctness requirement, not a tidy-up

`build_section` joins sentences with a single space and records each one's
offsets. Phase 3's `grounding.spans_fit_text` re-derives *exactly* that
invariant — it slices a note by its stored spans, re-joins with a single
space, and expects the original text back.

A provider that assembled sections even slightly differently would generate
notes whose grounding **never lines up, from birth**: every section
rendering "source links no longer line up with the text", on one vendor
only, with nothing raising and every existing test passing. A Phase 4
vendor swap silently breaking a Phase 3 feature.

Two tests now pin it: one asserts generated output satisfies
`spans_fit_text` end-to-end, and one asserts both providers build sections
through the identical function object.

### Haiku kept — deliberately contradicting two earlier decisions

Decisions 0021 and 0018 deleted alternatives on the principle that *"an
unused alternative with no real distinguishing capability left is dead
weight, not a safety net."* That clause is a test, and Haiku now passes it:
no 8,000 TPM ceiling, and a commercial agreement without the free-tier
carve-out. Until Groq is on a paid plan, `NOTE_GENERATOR_PROVIDER=haiku` is
one environment variable between a blocked pilot and a working one.

## The bug found while porting

`_extract_tool_input` raised `RuntimeError(f"...: {response_json!r}")` —
interpolating the **entire** Anthropic response into the exception message.

`pipeline.py:_mark_stage_failure` writes `str(exc)[:500]` into
`Encounter.last_pipeline_error`, a plain **unencrypted** `String(500)`
column whose own comment argues it is safe because "every exception raised
from these two tasks is an infrastructure/vendor error... never something
built from transcript or note content, so this can never leak PHI."

On this path that was false. A response missing the tool block — the exact
case being handled — typically contains the model's prose *about the
consultation*, so generated clinical content would have been written to an
unencrypted database column and kept there indefinitely.

Both providers now report the **structure** of a bad response (stop/finish
reason, block types, parse offset) and never its content. Two tests plant a
patient name in a malformed response and assert it cannot reach the
exception message. Invisible until an audit; found by porting, not by any
test.

## Verification

**35 tests passing** in the two generator suites — 19 new for Groq, and the
**16 existing Haiku tests passing unchanged**, which is the useful part:
they were written against the old implementation and now exercise the
shared one, so they are a regression guard proving the extraction changed
no behaviour. `ruff check` and `mypy` clean across 60 source files.

| | |
|---|---|
| the schema satisfies strict mode's requirements, recursively | pass |
| the request sends `json_schema`, never `tools`/`tool_choice` | pass |
| temperature is 0 — same transcript, same note | pass |
| low-confidence words never reach the model | pass |
| adjacent inaudible words collapse to one gap | pass |
| no API call at all for an empty transcript | pass |
| a hallucinated citation is dropped, not stored | pass |
| suppression wins over content the model supplied anyway | pass |
| a missing section yields an empty one, not a lost note | pass |
| **generated spans satisfy Phase 3's grounding invariant** | pass |
| **both providers build sections through the same function** | pass |
| **malformed JSON is reported without the model's output** | pass |
| **the Anthropic path also stopped leaking model output** | pass |
| a refusal, an empty body and a JSON array are distinct errors | pass |
| Groq is the default; Haiku stays selectable | pass |

**Not verified, and it is the real risk:** no call has been made against a
live Groq key — none is provisioned in this environment — so the *quality*
of the output is untested. Specifically, **Taglish comprehension is
unmeasured**. Groq publishes no multilingual benchmarks for `gpt-oss`,
while P0-3 requires Filipino preserved verbatim and P0-4 requires hedged
clinical language. Neither is a given on a model picked from a capability
table.

## Open follow-ups

- **Run a head-to-head on real Taglish transcripts before the pilot.** This
  is the single largest unverified risk in the swap. `prompt_version` is
  stored per note (`groq-v1` vs `haiku-v1`) precisely so the comparison is
  reconstructable from the data rather than from memory.
- **A paid Groq plan is a prerequisite for real PHI**, both for throughput
  and because the BAA excludes free-tier use. Worth raising with whoever
  owns vendor contracts at the same time as the RA 4200 consent script.
- **`MAX_TOKENS = 8192` is a guess, not a measurement.** gpt-oss models
  spend tokens reasoning before answering, and that spend counts against
  the cap; a truncated response is now a named error rather than a silent
  corruption, but the right ceiling should come from observing real notes.
- **A long consultation may exceed even paid per-minute limits.** Nothing
  currently chunks or summarises the transcript before generation. The
  131,072-token context window is not the binding constraint; throughput is.
