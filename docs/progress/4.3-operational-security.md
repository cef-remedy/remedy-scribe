The five bullets in 4.3 look unrelated. They share one property, and the
checklist names it in exactly one of them — *"An untested backup is a
hope."* It is true of all five: a control you have not executed is a
belief about your system, not a property of it. So the rule for this phase
was **execute what can be executed, and name what cannot** rather than
writing prose that reads as though it had been.

Which means the first thing this document owes the reader is the honest
split.

## What was built

**CI — the repository's first.** `.github/workflows/ci.yml`, four jobs:
`api` (ruff, mypy, pytest), `api-audit` (pip-audit), `web` (typecheck,
build, vitest), `web-audit` (npm audit). On push, on PR, on
`workflow_dispatch`, **and on a weekly schedule** — a new advisory lands
against code that did not change, so an audit that only fires on push is
silent exactly on the weeks that matter. The API job needs **no secrets at
all**: `tests/conftest.py` generates its own PHI key. A CI job holding a
real one would be the largest single-secret exposure in the system.

On GitHub's ubuntu runners the `postgres`- and `s3`-marked tests will
actually run rather than skip, because those runners have a Docker daemon
where a developer laptop often does not. That is the point: the raw-SQL
migrations — the consent ledger's append-only trigger, 0.4's CHECK
constraints — are invisible to the SQLite test path.

**A ruff config, `apps/api/ruff.toml`.** The repo had none, so ruff's
defaults were the standard by accident. `line-length = 120`, and the lint
set (`E4`, `E7`, `E9`, `F`) is stated rather than inherited so a ruff
upgrade that changes the defaults shows up as a diff instead of a surprise
CI failure on unrelated code. `E501` is deliberately **not** enabled: the
lint gate is for defects, and turning a width preference into a build
failure would mean either a mass edit or a sprinkle of `noqa`.

**Dependency bumps** in `requirements.txt` / `requirements-dev.txt`, each
with the advisory that motivated it written next to it — a version number
with no reason attached is the thing nobody dares to move later.

**Three runbooks**, in `docs/runbooks/`: `backup-restore.md` (with a drill
log), `breach-response.md`, `secrets-management.md`.

## The real audit findings

`pip-audit` had never been run against this project.

**Before: 30 advisories across 6 packages.** `npm audit` on `apps/web`:
**0 vulnerabilities** — the checklist's note that "the mobile scaffold
already reports vulnerabilities" is stale, since decision 0024 retired the
mobile client. `apps/web/package.json` therefore needed no change.

| Package | Findings | Reachable **in this app**? |
|---|---|---|
| `starlette` 0.38.6 (via fastapi) | 8 | **No.** No `StaticFiles` mount, no `HTTPEndpoint`, nothing reads `request.url`, no form parsing |
| `python-multipart` 0.0.9 | 7 | **No.** No route declares `Form`/`File`/`UploadFile`, so Starlette never invokes the parser — uploads are presigned direct-to-S3 (0013) |
| `cryptography` 43.0.1 | 7 | **No.** Fernet and HMAC only; no certificate chains validated, no EC public keys parsed |
| `python-jose` 3.3.0 | 5 | **No.** `decode_access_token` passes an explicit `algorithms=` allow-list (the documented mitigation for CVE-2024-33663); nothing calls `jwe` |
| `pytest` 8.3.3 | 1 | Dev-only; a predictable `/tmp/pytest-of-<user>` path on Unix |
| `ecdsa` 0.19.2 | 1 | **No.** HS256 only, so no ECDSA path is entered |

Reachability was checked per finding, not assumed. It would have been easy
to write "audited, no action required" — and wrong, because *every one of
those properties is a fact about today's code and none of them is
enforced.* One `Form(...)` parameter makes seven advisories live.

**After: 1.** `ecdsa` CVE-2024-23342 (Minerva timing attack on P-256).
There is no fix and there will not be one — python-ecdsa considers side
channels out of scope — and it arrives as a hard dependency of
python-jose. It is in an **explicit `--ignore-vuln` list in the CI job with
its reasoning in a comment**, rather than the job being soft-failed.
`continue-on-error` on an audit produces a red check everyone learns to
scroll past; an ignore list produces a short, named, re-examinable set of
accepted risks.

## The bcrypt pin, and what testing it found

The pin carried a comment explaining itself, which is more than most pins
do. It is also **wrong about where the breakage starts**, which took ten
minutes in throwaway environments to establish:

| passlib 1.7.4 + | Result |
|---|---|
| bcrypt 4.0.1 | works silently |
| bcrypt 4.1.1 | works, after logging a traceback (`module 'bcrypt' has no attribute '__about__'`) |
| bcrypt 4.3.0 | same |
| bcrypt 5.0.0 | **hard failure** — `ValueError: password cannot be longer than 72 bytes`, raised out of passlib's start-up self-test; hashing and verification never run |

So the project was pinned three minor versions behind the actual break, on
the strength of a log line. And passlib 1.7.4 shipped in October 2020 and
has had no release since, so every future bcrypt release is a coin flip.

**Decision 0034: argon2id via `argon2-cffi`, bcrypt kept verify-only.**
Verified end to end in an isolated environment — hashes produced by the
old stack (passlib 1.7.4 + bcrypt 4.0.1) verify under the new code, wrong
passwords are still rejected, and the truncation footgun goes away:

```
legacy bcrypt hash, 100-char password : verifies
   wrong password sharing the first 72 bytes : ALSO verifies
new argon2id hash, 100-char password  : verifies
   wrong password sharing the first 72 bytes : rejected
```

`app/core/security.py` is owned by another phase, so this is a hand-off
(below), not an applied change.

## Backup and restore — actually executed

Against the running local Postgres 16, 2026-08-28. Full log in
[the runbook](../runbooks/backup-restore.md) §5. Summary: a 70,012-byte
custom-format dump restored into a fresh database with `--exit-on-error
--single-transaction`, then five verifications.

The decision worth carrying forward is what "verify" had to mean, because
row counts alone are nearly worthless here:

- **The append-only trigger was tested by trying to break it.** A real
  `DELETE` and a real `UPDATE` against the restored consent ledger, both
  required to fail. Both did, with the P0-1 message. `pg_dump` carries
  triggers — but a `--data-only` restore, a schema rebuilt by
  `Base.metadata.create_all()`, or `--disable-triggers` would each produce
  a ledger that *looks* right and silently accepts mutation.
- **PHI was decrypted, not merely counted.** All 12 `patients.full_name`
  and all 8 `transcripts.segments` blobs decrypted under the live key.
  A restore whose ciphertext was written under a key you no longer hold is
  an archive, not a recovery.

That check is what forces the **two-artifact rule** into the runbook: the
dump and the `PHI_ENCRYPTION_KEY` must never rest or travel together.

**What was not tested is listed by name in the runbook's §6** — no
production-scale data, no off-host copy, no encryption of the dump, no
PITR, no object-storage restore, no `audit_logs` trigger check (the 4.2
migration had not reached the drilled database), and nobody but the author
has run it.

### One bug this phase introduced and caught

The first draft of `requirements.txt` used an em dash and a `⚠️` in its
comments. `pip-audit` refused to read it:

```
UnicodeDecodeError: 'charmap' codec can't decode byte 0x8f ...
decoding with 'cp1252' codec failed
```

pip's requirements parser decodes with the platform preferred encoding,
which on Windows is cp1252. Every other file in this repo can be UTF-8;
`requirements*.txt` cannot. Caught by running the tool rather than by
reading the file, which is the entire thesis of this phase in miniature.

## Hand-offs — these are blocking

**1. `app/core/security.py` needs the argon2 diff applied, in the same
commit as `requirements.txt`.** They are one change: `requirements.txt` no
longer installs `passlib`, and the current `security.py` imports it. Either
lands alone and a fresh `pip install -r requirements.txt` produces a broken
app. The existing `.venv` is unaffected either way, which is exactly why
this is easy to miss.

a change that must land with another one should not depend on someone
remembering a conversation. Its anchors — the

**2. `app/api/routes/auth.py` should adopt `password_needs_rehash`.**
Without it, argon2 applies to *new* credentials only and existing bcrypt
hashes stay bcrypt forever. The sketch, at the successful-login site:

```python
if verify_password(payload.password, clinician.hashed_password) and password_needs_rehash(
    clinician.hashed_password
):
    clinician.hashed_password = hash_password(payload.password)
```

Not folded into `verify_password` on purpose: the plaintext exists only
for that instant, `security.py` has no session, and a function named
`verify` should not silently write a row.

## Open follow-ups

- **Replace `python-jose` with `PyJWT`.** This removes `ecdsa` from the
  tree entirely and with it the one remaining unfixable advisory, and it
  drops a JWT library that is barely maintained. Needs `security.py`, so
  it was out of scope here. When it lands, **delete the `--ignore-vuln`
  entry** rather than inheriting it.
- **Pin GitHub Actions to commit SHAs, not major tags.** SHA-pinning is
  the stronger supply-chain posture. It was not done because the SHAs
  could not be verified from this environment, and a pin nobody checked is
  worse than an honest tag.
- **The repo is not `ruff format`-clean, and that is untouched on
  purpose.** `ruff format --check` reports 44 of 98 files would be
  rewritten at 120 columns (57 at ruff's default 88). Making it clean is a
  mechanical, reviewable commit of its own; doing it here would have
  buried a security phase under a 44-file reformat while three other
  phases were editing those same files. Recommended as a separate change,
  and until then `ruff format` should not be run casually — it silently
  reformats whatever it touches.
- **`starlette` deprecates `httpx` in its TestClient** ("install `httpx2`
  instead"). Harmless today, a warning in every CI run, and a real
  migration when it becomes an error.
- **`pytest` 9 and `pytest-asyncio` 1.4** are a major bump each, taken
  together for one dev-only advisory. Verified green here, but they are
  the two bumps most likely to be the cause if the suite behaves oddly.
- **No detection exists, and that is what actually limits breach
  compliance.** The NPC's 72 hours run from *reasonable belief*, not
  confirmation, so detection — not notification — is the binding
  constraint. Phase 5.2 (error tracking, alerting) is where that gets
  fixed; the breach runbook states the gap rather than writing around it.
- **The breach runbook's roles table is empty**, deliberately. The DPA
  requires a designated DPO and NPC Circular 16-03 requires a breach
  response team; neither exists. This is the cheapest item in the phase
  and the one that most determines whether any of the rest happens.
- **Backup retention vs. the retention promise.** Phase 4.4 deletes
  expired PHI from the live system; backups are outside its reach, so
  backup retention is an upper bound on what the clinic can honestly
  promise a patient. **Owner: DPO/Legal.**
- **Object storage has no backup story at all.** Audio lives in MinIO/S3
  and nothing covers it — Phase 5.1.
- **Nobody but the author has run the restore drill.** A runbook only its
  writer can execute has not been tested for the case it exists for.
  Schedule a two-person drill before the pilot.
- **Index entries are not written.** `docs/decisions/README.md`,
  `docs/progress/README.md` and `docs/implementation-checklist.md` are all
  outside this phase's ownership, so decision 0034, this document, and the
  three new runbooks are unlisted in them. `docs/runbooks/` is also a new
  directory with no index of its own.
