# Phase 4.4 — Retention enforcement

**Status:** done · **Date:** 2026-08-28
**Related decisions:**
[0033](../decisions/0033-retention-is-enforced-in-two-layers.md) (two

[0027](../decisions/0027-consent-flow-ordering-and-withdrawal.md) (what a

[0030](../decisions/0030-grounding-is-withheld-not-approximated.md) (the

Retention stops being a column and becomes a policy. Since Phase 1.1,
`Encounter.audio_retention_expires_at` has been computed and stored on every
encounter; since Phase 1.2, `Transcript.retention_expires_at` has been stored
on every transcript. Nothing read either one. The Compliance story — "audio
retention duration is a configurable value" — was half true: the value was
configurable, and nothing acted on it.

## The 🧠, resolved at implementation level

The checklist asks the user to choose between **Celery Beat, cron, and bucket
lifecycle rules**, and then reasons its way to "most likely you want both."
That resolution is adopted, and recorded in decision 0033 explicitly as an
implementation-level answer to a question flagged for the user, because the
part that genuinely is theirs — *how long* retention lasts — is untouched.
`audio_retention_days` is still the one knob, still 90, still owned by
Legal/Compliance.

| layer | deletes | runs |
|---|---|---|
| bucket lifecycle rule (already shipped, Phase 1.1) | the audio objects | inside object storage, always |
| `retention.sweep_expired_retention` (Beat, hourly) | transcripts, note revisions, the `audio_deleted_at` write-back | in the app |

Lifecycle-only cannot reach Postgres, and the transcript — verbatim, including
what the doctor chose not to write down — lives entirely in a Postgres row.
Job-only makes a compliance control depend on a container being scheduled and
healthy, and fail *silently* when it is not. So the raw recording gets the
guarantee that does not depend on us, and the derived rows get the only
mechanism that can reach them.

Not cron: the app already runs a Beat process for `sweep-stuck-encounters`,
so a second periodic task costs one dictionary entry rather than a new
container, environment, and answer to "did it run last night?"

**Hourly**, bracketed by two facts: `audio_retention_days` gives the policy day
granularity, so a tighter interval buys nothing against a 90-day clock; but the
job is also the backstop for a withdrawal whose immediate delete failed, and
P0-1 says "without undue delay," so a nightly cron would make a patient's
withdrawal an up-to-24-hour wait for the derived rows.

## The bug this could have been

`grounding.py` derives `edited_since_generation` from a `NoteRevision` merely
*existing* for a section. Deleting revisions while the transcript survives
would flip a section the doctor rewrote back to reporting **"these are the
model's words"** — with real transcript passages still there for the UI to
highlight as its source. A confidently wrong answer about provenance, on the
one screen whose entire job is proof.

So: **revisions are only ever removed in the same purge that removes (or has
already removed) the transcript.** At that point grounding reports
`TranscriptState.EXPIRED`, returns no segments, and has nothing left to
mis-attribute. Two tests hold it, one of them walking a single note through
both states and asserting the grounding output at each.

The audio signal survives untouched for a different reason: `_audio_state`
distinguishes `WITHDRAWN` from `EXPIRED` by asking the consent ledger, not by
anything this job writes. Stamping `audio_deleted_at` is therefore
reason-neutral — asserted on two encounters driven into identical observable
states by different causes.

## The boundary

A **signed `Note` is a permanent medical record.** Nothing in this module
touches the `notes` table, in any code path, forced or not. A note signed 400
days ago survives a purge that removes its audio, its transcript and its
revisions, with its signature and text intact — asserted directly, not implied.
`NoteRevision` rows are the drafting history, not the record, and they expire.
The consent ledger is never touched: it is append-only at the DB level, it is
the legal record of the withdrawal that may have triggered the deletion, and
it is what grounding reads to explain *why* the audio is gone.

## What was built

- **`app/tasks/retention.py`** — one deletion primitive, `purge_encounter`,
  which the scheduled sweep and the withdrawal path both go through, so there
  is one definition of what gets deleted and in what order rather than two
  that can drift. Audio first (the most sensitive artifact and the only one
  outside the database), derived rows after — the same "a later failure
  cannot undo an earlier step" ordering `handle_withdrawal` uses.
- **`run_retention_sweep`** — takes an explicit `Session` so it is callable
  from a test (and later a management command) without a broker; batched at
  500 encounters per run, re-entrant, so a backlog drains over the following
  hours rather than in one very long transaction.
- **`purge_withdrawn_encounter`** — the immediate path for P0-1. **Wraps**
  `handle_withdrawal` rather than reimplementing it: the ledger handling, the
  retention-clock stamp and the `WithdrawalOutcome` the API reports back to
  the doctor stay where they are, and the derived-data purge is added around
  them. Returns the same `WithdrawalOutcome`, so the consent route adopts it
  by changing which function it calls and nothing else.
- **The sweep also treats a withdrawn encounter as due**, keyed off the
  consent ledger rather than the transcript's own 90-day clock — so a
  withdrawal's derived rows are collected within the hour even before the
  route adopts the immediate path. That ledger read goes through
  `current_consent_state`, so **re-consent after a withdrawal deletes
  nothing**: the ledger is a fold, not a latch.
- **Audit (P0-8)** — one row per artifact class:
  `encounter.audio.delete`, `encounter.transcript.delete`,
  `note.revisions.delete`. Each carries the reason
  (`retention_expired` / `consent_withdrawn`) and nothing else: no object key
  (a direct pointer at PHI bytes, and an audit row outlives the retention
  window of what it points at — 0030's reasoning restated for deletions), no
  note or transcript text. `audit.record` is called with the deletion still
  pending in the session, so the deletion and the record of it commit
  together. The scheduled sweep writes a NULL actor; nobody triggered it.
- **`app/tasks/celery_app.py`** — `sweep-expired-retention` at 3600.0s
  alongside the existing 5-minute stuck-encounter sweep, and
  `app.tasks.retention` added to `include` so the worker registers it.
  Verified: `import_default_modules()` registers all four tasks and the beat
  schedule carries both entries.

**No schema change, and no new setting.** `audio_retention_days` already
existed and was already the clock for both columns.

## Details that are deliberate

- **A failed storage delete does not stamp `audio_deleted_at`.** Stamping on
  failure would make grounding report EXPIRED for a recording still in the
  bucket, and the row would drop out of the due-query so no later sweep would
  retry it. Tested both halves: the failure is a no-op with no audit row, and
  the next sweep picks it up once storage is back.
- **A NULL retention clock is never expired** — "no clock was ever set", not
  "expired long ago".
- **`_is_expired` normalises naive datetimes to UTC.** These columns are
  `DateTime(timezone=True)`, which Postgres honours and SQLite does not, so
  the same row reads back aware in production and naive under the test suite —
  and comparing the two raises `TypeError` rather than returning a wrong
  answer. Values are only ever written as UTC, so reading a naive one back as
  UTC is a restatement, not an assumption.
- **Nothing binds a callable at module scope.** Phase 1.5's dispatch-dict bug
  (a `{status: function}` map built at import time, which captured function
  identities and made `monkeypatch.setattr` silently ineffective — the real
  task ran and opened a live Redis connection) is the reason `PurgeReason` is
  a string enum and `purge_encounter` is called by bare name from the sweep
  body. The test that exercises the Beat task through its own `SessionLocal`
  is precisely the one that would hang if this were got wrong.
- **Revisions are bulk-deleted, never loaded.** `previous_text`/`new_text` are
  `EncryptedString`; loading them would decrypt every historical version of a
  note into process memory purely to discard it.

## Open follow-ups

- **The consent route still calls `handle_withdrawal` directly**, so the
  transcript and revisions of a withdrawal are collected by the hourly sweep
  rather than in the same request. `app/api/routes/consent.py` is owned
  elsewhere this phase; the one-line adoption is to call
  `retention.purge_withdrawn_encounter(db, encounter_id, actor_clinician_id=clinician.id)`
  in place of `handle_withdrawal`, which returns the identical
  `WithdrawalOutcome`. Until then the behaviour is correct but up to an hour
  slower, and the audio half is still immediate.
- **`TranscriptState` has no `WITHDRAWN` rung.** `AudioState` distinguishes
  "deleted at the patient's request" from "the retention period elapsed";
  the transcript ladder cannot, so a withdrawn encounter's transcript is
  described to the doctor as expired. Not a wrong signal from this job — it is
  a gap in what the grounding UI can express — but it is the first thing worth
  fixing in this area.
- **`generate_note` does not re-check consent.** `transcribe_encounter` does
  (Phase 0.1), but a chain that has already passed transcription will still
  generate a note after a withdrawal — and now from an empty transcript, since
  the immediate purge removes it. Pre-existing, and orthogonal to retention,
  but this phase makes the shape of it more visible.
- **A withdrawn encounter whose transcript was already time-expired but whose
  revisions were not** would not be collected by the sweep's withdrawn branch
  on the *audio* clock alone; it is covered by the `NoteRevision` existence
  check in the due-query, but that path is reachable only through an ordering
  (transcript expiring before revisions) the current single-clock policy never
  produces. Worth re-checking if per-artifact retention periods ever diverge.
- **Nothing observes the sweep yet.** It returns a count dict and logs one
  INFO line when it purges something. Phase 5.2 should alert on "the retention
  sweep has not run in N hours" — a compliance control that stops running
  silently is the failure mode decision 0033 pairs it with a lifecycle rule to
  survive.
