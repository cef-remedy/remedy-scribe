# Phase 2.5 + 2.6 — Patient identity, and review / edit / sign

**Status:** done · **Date:** 2026-08-27
**Related decisions:** [0029](../decisions/0029-searchable-encrypted-patient-names.md)
(the searchable-names 🧠, and why the checklist's own preferred option does
not fit), [0004](../decisions/0004-note-read-access-scope.md) (note read scope)

**The whole clinical journey now runs as one flow** — consent → record →
upload → transcribe → generate → link a patient → review → edit → file →
sign. Every earlier phase built one link; this is the first time the chain
is complete and tested end to end.

## Phase 2.5 — Patient identity (P0-6)

### The 🧠, resolved against the requirement rather than the menu

The checklist offers a blind index as the way to search encrypted names.
**It doesn't fit**: P0-6's entry point is a *typed or dictated name* that
must **fuzzy-match**, and an HMAC supports equality only. "Maria Cruz" for
*Maria Santos Dela Cruz*, or "Cruzz" for "Cruz", returns nothing.

So names are decrypted and ranked in Python — and the naive version of that
was **2.1 seconds at 5,000 patients**, which I found by measuring rather
than assuming. The breakdown redirected the fix entirely:

| step | cost at N=5,000 |
|---|---|
| raw `SELECT` of ciphertext | 7.7 ms |
| + decrypting every value | 118 ms |
| **full ORM query** instead | **348 ms** |
| `difflib` over all names | 183 ms |
| **token prefilter, then `difflib`** | **68 ms** |

Decryption is *not* the bottleneck. ORM hydration and unfiltered `difflib`
are. The implementation therefore uses a raw three-column `SELECT` and a
shared-token/prefix prefilter before any similarity work — about **194 ms at
5,000 patients**, roughly 10× the naive path. Decision 0029 records the
scale ceiling as measured numbers and names the token-level blind index as
the correct next step if the directory outgrows it.

### What was built

- **`search_patients_by_name`** — name-only ranked fuzzy search.
- **`GET /api/v1/patients/search`** — doctor-only, and **audited as a PHI
  read** because it decrypts the whole directory. The query string is
  deliberately not logged: a patient name in an audit table with longer
  retention than the record it describes is a leak, not a breadcrumb.
- **`PatientPicker`** — debounced search with the three P0-6 outcomes.
  Exact links silently, but **only when there is exactly one exact hit** —
  two identical names is precisely where silence attaches a note to the
  wrong person.
- **Loose-session linking** on the worklist (P0-6's one-tap action).
  Recording is never blocked on identity; this is where identity catches up.
- **Identity re-confirmed at filing** — a new `PatientIdentityNotConfirmedError`
  in `note_lifecycle`. Filing requires the caller to *name* the patient, and
  the server checks it against the encounter's own `patient_id`. Reading
  `encounter.patient_id` and trusting it would make this a formality; a
  stale client showing the previous patient now disagrees and is rejected.

Search and dedup stay separate on purpose. `search_patients_by_name` takes
no birthdate; `match_patient` still requires both, so "dedup uses name +
birthdate together, not name alone" continues to hold. A test asserts it:
same name + wrong birthdate is a search hit but **not** a dedup match.

## Phase 2.6 — Review, edit, sign (P0-5)

Most of this phase's backend already existed from Phase 0 — the state
machine, `NoteRevision`, and the signing fields. What was missing was the
doctor-facing half, plus one gap the tests exposed.

- **`NoteReview` screen** in **APSO order**, not SOAP. P0-4 specifies it
  because the doctor's own conclusion is what they check first; burying it
  under recounted symptoms is how a wrong assessment gets signed.
- **Edits save on blur**, one section at a time, each creating a
  `NoteRevision`. Not a single Save at the end: the edit-burden metric is the
  pilot's headline target, and a metric computed from one final diff cannot
  distinguish "the draft was nearly right" from "the doctor rewrote it in one
  pass".
- **The signing ceremony is visually and structurally separate** from the
  ordinary "next step" button, requires typing the PRC licence every time,
  and says plainly that it transfers accountability from the model to the
  clinician. It should not look like a Save button.
- **Objective-findings entry** is the Objective textarea, with a hint that
  it is where to put what was observed but never said aloud — the recording
  cannot know it.
- **Prior visit context** — `previous_signed_note` + a route, returning
  assessment and plan only. **Only signed notes count**: presenting an
  unsigned note as "the last visit" would hand the doctor an unreviewed AI
  draft as established history, the opposite of what signing is for. And
  subjective/objective are excluded because last visit's symptoms are not
  today's.

## The gap the test found

Writing the end-to-end test surfaced that **the review screen was
unreachable**. Notes are 1:1 with encounters, but nothing exposed the note
id — so `/notes/{id}` had no route into it from any worklist. The test
literally could not navigate to the screen it existed to exercise.

Fixed by adding `note_id` to `EncounterOut`, resolved on the read paths that
need it. Worth recording as a shape: a feature can be complete, tested at
the unit level, and still be dead code because nothing can reach it.

## Open follow-ups

- **The "minor edit" definition is still undefined**, and it is the pilot's
  headline quality target ("≥70% of signed notes require only minor edits").
  Deliberately deferred rather than guessed: `NoteRevision` stores full
  before/after text per edit, so *any* candidate definition — character
  distance, word distance, clinically-weighted — can be computed
  retrospectively. Phase 6 owns choosing one, and the checklist is right that
  it must be written down before alpha and computed consistently.
- **No patient merge tool.** The checklist flagged this and it remains true:
  a mistyped birthdate creates a duplicate, putting one person's history in
  two records. Nothing here fixes that, and the fuzzy search makes it *more*
  visible (both duplicates appear as candidates) without making it
  resolvable. Unglamorous and genuinely needed.
- **`NoteRevision` volume is unbounded.** Saving on blur is right for the
  metric but means every edit is another encrypted PHI copy, and retention
  does not cover revisions yet (Phase 4.4).
- **Dictation is not implemented.** P0-6 says "typed **or dictated**"; the
  picker accepts typed input only. The Web Speech API would cover it, but
  its accuracy on Taglish names is exactly the sort of thing that needs
  measuring before being trusted with patient identity.
- **The patient picker on the review screen shows an id, not a name.** It
  resolves `patient_id` from the encounter but has no name lookup for a
  single patient — `GET /patients/{id}` does not exist. Cosmetic but
  user-facing.
