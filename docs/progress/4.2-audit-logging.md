**Status:** done · **Date:** 2026-08-28
**Related decisions:**

[0005](../decisions/0005-rbac-role-policy-and-audit-log-endpoint.md) (why a

[0030](../decisions/0030-grounding-is-withheld-not-approximated.md) (why an

[0027](../decisions/0027-consent-flow-ordering-and-withdrawal.md) (why
`created_at` alone is not a stable sort)

Before this phase the system could answer "who changed this note?" and
could not answer "who *looked* at this patient's record?" — which is the
question a breach investigation actually asks. Seven `audit.record` call
sites covered a handful of write paths; sixteen ordinary reads and changes
went unrecorded. It is now twenty-three, the table is append-only for seven
years at the database layer, and there is an endpoint a compliance officer
can point at a patient id.

## The rule, and the one exception

The checklist's ⚠️ says reads are the ones developers forget. True, and not
the hard part. The hard part is that once you accept it, "should this be
logged?" becomes a judgment call you make twenty-three times, and every one
is a chance to decide *this* read is too boring to bother with. So it was
applied as a rule instead:

> **Log every disclosure of, or capability over, PHI. Do not log requests.**

That covers a `POST` that reads (`/patients/match` decrypts and ranks the
directory), a list that touches every record (`/encounters/loose`), and a
URL that grants access to bytes (`/upload/parts/{n}` mints a writable
handle on the recording — the playback URL Phase 3 already audits, pointed
the other way).

The second half of the rule is what keeps it from collapsing into a request
log. **`GET /upload/parts` is the one endpoint touching an encounter that
writes no audit row**: it returns part numbers, sizes and ETags from S3, it
discloses no PHI and grants nothing. That is a decision, not an oversight —
it is commented in the route and there is a test named after it.

## How the pieces connect

A read happens → the route assembles the response → `audit.record` writes
one row, after the fact, so a 404 or a 409 never logs a disclosure that did
not occur → the row is stamped with a retention date at insert → the
database refuses to update or delete it until that date → the review
interface reads it back, filtered, and logs the fact that it did.

Three joins between those pieces are load-bearing:

- **`retention_expires_at` is both the retention policy and the tamper
  boundary.** Phase 4.4's purge job reads it; the trigger keys off it. That
  is only safe because `UPDATE` is refused unconditionally — the date
  cannot be back-dated to bring a row into deletable range, so the sole
  route to a deletable row is to wait seven years. It has its own test.
- **The actor's name is joined live from `clinicians`, never copied in.** A
  report of UUIDs is not "reviewable"; a name copied into an append-only
  table is a permanent record of staff identity and goes stale.
- **The coalescing window is keyed on (actor, action, entity).** That is
  what lets `GET /encounters/{id}` be both a genuine PHI read and a 15-second
  poll without the poll burying the human reads around it.

## Retention

Seven years (2555 days) against `AUDIO_RETENTION_DAYS`'s 90. The ratio is
the decision, not the number: the trail's job is to answer "who looked at
this?" about records that have themselves already been deleted, and a log
expiring with its subject cannot. It is a placeholder with a rationale, not
a legal finding — the PRD's retention question is still Legal's.

**The policy column is defined here; the job that acts on it is 4.4's.**
Nothing in this phase deletes anything.

It is read via `getattr(get_settings(), "audit_log_retention_days",
DEFAULT_AUDIT_LOG_RETENTION_DAYS)` because `app/core/config.py` belonged to
a concurrent phase and could not take a new field. **This is the one thing
this phase needs from someone else** — see follow-ups.

## Notable bugs and gaps caught

- **`TRUNCATE` defeats the consent ledger's append-only trigger.** Row-level
  triggers do not fire on `TRUNCATE`, so `TRUNCATE consent_ledger_entries`
  erases P0-1's immutable ledger while leaving the guarantee technically
  intact. Found by asking what the pattern being copied does *not* cover,
  before copying it. `audit_logs` got a statement-level guard; the consent
  ledger still has the gap (follow-up below — it is P0-1's table, and this
  phase should not quietly widen its own blast radius).
- **`PATCH /notes/{id}` wrote no audit row at all.** The only change to
  clinical content in the API that was invisible to the audit trail. A
  `NoteRevision` was written, but that is not the same thing: it holds the
  before/after PHI text, it dies with the note under retention, and the
  compliance review interface cannot see it. "Access and change logs" means
  both.
- **`POST /patients/match` reads like a write and is a read.** It decrypts
  and ranks the whole directory and, on a hit, discloses an existing
  patient's identity. It had been unlogged since 0.2, plausibly because the
  verb is `POST`.
- **An ISO-8601 UTC timestamp in a query string silently 422s.**
  `?since=2026-08-27T12:00:00+00:00` interpolated into a URL decodes the
  `+` as a space and fails validation. Caught by the time-window test
  failing that way first; the test now passes `params=` and asserts the
  200, and the same trap is waiting for any client that builds the URL by
  hand.
- **The consent ledger records *what* was consented to and never *who*.**
  By design — it is a statement about the patient. But that means the audit
  row added here is the only record of who captured a withdrawal, which is
  the event that triggers deletion of a recording.

## Open follow-ups

- **`audit_log_retention_days` needs to land in `Settings`.**
  `app/core/config.py` was owned by Phase 4.3 this cycle, so the policy is
  a module constant read through a `getattr` bridge. Adding
  `audit_log_retention_days: int = 2555` to `Settings` (and
  `AUDIT_LOG_RETENTION_DAYS` to `.env.example`) makes the bridge a no-op
  with no code change here. **This is the only thing this phase needs from
  another owner.**
- **A denied access is not logged.** `require_role` raises inside a
  dependency, so a 403 never reaches the route body and "who tried to read
  the audit log and was refused?" is unanswerable. The right fix is an
  exception handler in `app/main.py` (another phase's file this cycle), not
  a copy-pasted `try` in every route. There is a test asserting the current
  behaviour so the gap stays visible.
- **The consent ledger is still TRUNCATE-able.** One statement-level trigger,
  in whoever's phase next touches P0-1.
- **Auth routes are deliberately out of scope.** Login, refresh, logout and
  MFA disclose no PHI and already have their own record in `login_attempts`
  (0.3). Worth revisiting only if session events need to appear in the same
  review timeline as clinical access.
- **No review *UI*, by choice.** The requirement is "reviewable", and the
  access report is the query; a compliance screen in `apps/web` is a Phase
  6 sort of thing. `X-Total-Count` is already there for it to page against.
- **Volume is now a function of reads, not writes**, which is a different
  order of magnitude. If it becomes an operational cost, the answer is
  partitioning by month plus 4.4's purge — not logging fewer actions.
- **`prior-visit` logs nothing when there is no prior visit.** Nothing was
  disclosed, which is consistent with the 404 rule, but it does mean "who
  checked whether this patient had a prior visit" is only answerable when
  the answer was yes.
