# Phase 2.2 — Recording

**Status:** done (bar the consent flow it is gated behind, which is 2.3) · **Date:** 2026-08-27
**Related decisions:** [0024](../decisions/0024-web-client-on-laptop-not-mobile.md)
(browser client, and what was measured about backgrounding/sleep),
[0025](../decisions/0025-audio-format-mono-opus-32kbps.md) (mono Opus 32 kbps),
[0026](../decisions/0026-recorder-design.md) (fail-closed consent gate, recorded
gaps, chunk granularity, crypto-shred)

## What changed

### Backend (small, and needed by P0-1)

- **`GET /api/v1/consent/{encounter_id}`** — the client can now ask "may I
  record?". P0-1 requires blocking *before anything is captured*, and the
  existing enforcement points (upload confirmation, transcription) both run
  after capture. Any authenticated clinician may read it, matching the
  reasoning in decision 0004 for note reads.
- **`current_consent_state()`** extracted in `app/services/consent.py`, with
  `assert_consent_valid()` reduced to a thin wrapper over it. The module
  docstring already promised one definition of "valid consent"; this keeps
  that true now that there are three consumers instead of two.

### The recorder (`apps/web/src/lib/recorder/`)

- **`crypto.ts`** — AES-GCM with a **non-extractable** `CryptoKey` in
  IndexedDB. Plaintext audio never reaches disk. `destroyAudioKey()` is the
  crypto-shred path; see decision 0026 for its per-device blast radius.
- **`store.ts`** — the write-ahead chunk log. Session-scoped reads via a
  compound index, per-session delete, and `assembleSession()` for the
  eventual upload path.
- **`session.ts`** — `RecordingSession`, the orchestrator. Everything
  load-bearing here came from the capture harness rather than assumption:
  - **Wake lock re-acquired on every `visibilitychange → visible`.** The
    browser auto-releases on hide and never restores it; in the harness run
    it was lost 35s in and never came back, leaving 28 of 29 minutes
    unguarded.
  - **`audioBitsPerSecond` set explicitly.** Without it the browser picks,
    which is how the harness recorded 129 kbps stereo.
  - **`assertAudioSettings()`** compares requested against actual and
    surfaces mismatches, because the test laptop reported `channelCount: 2`
    while being asked for 1.
  - **Gap detection** via an AudioWorklet sample count, with suspends
    detected from wall-clock jumps and stalls from worklet silence.
  - **`requestData()` before `stop()`** to flush MediaRecorder's partial
    chunk. Without it the final seconds are discarded — and the tail of a
    consultation is often where the plan is stated. Visible in the smoke
    run: the live panel showed 3 chunks, storage held 4.
- **`useRecorder.ts`** — thin React binding. The audio machinery stays out
  of React state so a re-render can never restart a recording.

### The consent gate and UI

- **`lib/consent.ts`** — reads the server, fails closed on every uncertain
  path including offline, and is re-checked at the moment of the tap rather
  than only on mount. Reasoning and the cost of the offline choice: decision
  0026.
- **`components/RecordingIndicator.tsx`** — P0-1's persistent indicator.
  Sticky, undismissable, `role="status"`, and it shows missing audio inline
  rather than hiding it in a details panel. Honours
  `prefers-reduced-motion` by stopping the pulse while keeping the dot
  visible — it is the indicator, not decoration.
- **`routes/Record.tsx`** — the recording screen. The gate is the only path
  to the record button, so until 2.3 exists a doctor genuinely cannot
  record. That is the correct state for a system whose legal basis for
  recording is not yet implemented, rather than a temporarily-open path
  with a TODO.

## How the pieces connect

```
  Doctor opens /encounters/:id/record
        │
        ▼
  checkConsentGate(encounterId)  ──►  GET /api/v1/consent/{id}
        │                                   │
        │                                   ▼
        │                        current_consent_state(): fold the
        │                        append-only ledger  ── the SAME fold
        │                        assert_consent_valid() uses at upload
        │                        confirmation and transcription
        │
        ├─ not given / offline / error ──►  BLOCKED. No record button
        │                                   exists to press. (P0-1)
        │
        └─ given ──► record button ──► re-check gate ──► RecordingSession.start()
                                                             │
        ┌────────────────────────────────────────────────────┘
        ▼
  getUserMedia(mono, 16kHz)      AudioWorklet ──► sample count (ground truth)
        │                              │
        ├──────────────┬───────────────┘
        │              │
        ▼              ▼
  MediaRecorder   monitor() every 500ms
  (32 kbps,         · wall-clock jump  -> "suspend" gap
   5s timeslice)    · worklet silence   -> "stall" gap
        │           · missing = window - captured
        │ ondataavailable (every ~5s)
        ▼
  encryptChunk(AES-GCM, non-extractable key)
        │
        ▼
  appendChunk() -> IndexedDB      [ciphertext only, never plaintext]
        │
        ▼

```

## Verification

**API: 136 passing** (up from 131 — 5 new consent-state tests), `ruff` and
`mypy` clean.

**Web unit tests: 18 passing** (`npm test`, vitest + `fake-indexeddb`).
These cover what fails *silently* if broken: key non-extractability,
plaintext never reaching disk, cross-session leakage, IV freshness,
GCM rejecting tampered and truncated chunks, reassembly order, and container
preservation so Safari's MP4 is not mislabelled as WebM.

`fake-indexeddb` is a real spec-compliant implementation, not a stub —
deliberate, because the store's correctness depends on transaction semantics
and compound-index key ranges that a hand-written fake would let through.

**End-to-end: 22/22** (`smoke/record-flow.cjs`, real Chromium against the
live API):

| | |
|---|---|
| Consent gate blocks with no ledger entry (P0-1) | pass |
| No record button offered while blocked | pass |
| Recording starts once consent exists | pass |
| Persistent indicator visible during, gone after | pass |
| 4 chunks / 65 KB written to IndexedDB | pass |
| Every chunk has a 12-byte IV and ciphertext | pass |
| **Stored bytes are not plaintext audio** (WebM magic absent) | pass |
| Sequence contiguous from 0 | pass |
| 18s elapsed, 17s captured, **0:00 missing** | pass |
| Consent withdrawal re-blocks recording | pass |

The browser-only parts (getUserMedia, MediaRecorder, AudioWorklet, wake
lock) are tested *here* rather than mocked in vitest. A jsdom
`MediaRecorder` would only prove the mock works — the same gap that hid a
real httpx bug in Phase 1.3.

**Decision 0025 confirmed in practice:** 65,218 bytes for 18 seconds is
**~29 kbps**, against a 32 kbps target and the harness's accidental
129 kbps. The explicit `audioBitsPerSecond` is what makes that true.

## Bugs caught by running it

**A real IndexedDB connection leak.** `getAudioKey()` opened a connection
and never closed it when not handed one. Found because a test's
`beforeEach` hook timed out — `deleteDatabase` blocks on open connections.
The production consequence is worse than the test symptom: leaked
connections accumulate one per recording across a clinic day, and an open
connection blocks `onupgradeneeded`, so a future `DB_VERSION` bump would
hang indefinitely for anyone with the tab open. Fixed to close only what it
opened. The fixture was also changed to clear stores rather than delete the
database — useful as a signal once, useless as a fixture.

**An orphaned dev server served stale code.** The smoke run failed on a
selector because port 5173 was held by a Vite process from the Phase 2.1
run. Worth recording as a *good* outcome: `strictPort: true` made it fail
loudly instead of silently moving to another port, which would have broken
CORS and produced a far more confusing failure.

**TS 5.8's generic `Uint8Array`.** `crypto.getRandomValues` returns
`Uint8Array<ArrayBufferLike>`, which is not assignable to `BufferSource`
because the default admits `SharedArrayBuffer`. Pinned to
`Uint8Array<ArrayBuffer>` at the type definition rather than cast at every
crypto call site.

**The generated client caught its own staleness.** Adding the consent
endpoint broke `tsc` in `lib/consent.ts` until `openapi.json` and
`schema.d.ts` were regenerated. Exactly the payoff Phase 2.1 claimed for
generating the client instead of hand-writing it.

## Open follow-ups

- **Gaps are reported to the doctor but not to the note generator.** Phase
  1.4 already suppresses content over low-confidence windows; a *known*
  audio gap is strictly better evidence than low ASR confidence and
  deserves the same treatment. Needs the gap list to travel with the upload,
  which is 2.4's data path.
- **Nothing uploads yet.** Chunks accumulate in IndexedDB and are never
  sent or deleted — that is 2.4 (offline queue), and until it exists a
  clinic laptop would fill up. `deleteSession()` and `assembleSession()`
  are written and tested for it, and are currently uncalled by design, not
  by oversight.
- **`prefers-reduced-motion` is handled; a full a11y pass is not.** The
  indicator is `role="status"` with a live region, but the recording screen
  has not been keyboard- or screen-reader-tested end to end.
- **Battery/thermal over a full clinic day is still unmeasured.** The
  original checklist heads-up assumed a mid-range Android; a plugged-in
  laptop makes it far less pressing, but "far less pressing" is not
  "measured".
- **No pause/resume.** The checklist's "pause/resume on phone call" is N/A
  on a laptop (decision 0024), but a deliberate pause for a mid-visit
  interruption is a real clinical need and belongs with 2.3's re-consent
  flow, which is the thing that makes pausing legally meaningful.
