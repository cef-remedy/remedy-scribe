Orientation

The whole consultation in one paragraph

A doctor signs in on a clinic laptop and taps Start a new consultation. The browser opens an encounter on the server, then records — encrypting every five-second piece of audio before it touches disk, and counting samples to prove no audio went missing. When the visit ends, a durable queue reassembles those pieces into storage-sized parts and uploads them straight to object storage, bypassing the API entirely. The API is told only when the bytes have landed, and it verifies that claim before believing it. Two Celery tasks then run: one sends the audio to Groq's Whisper for a transcript, the other sends the transcript to Groq's language model for an APSO-structured draft whose every sentence cites the transcript segments it came from. The doctor opens the draft, taps any line to see the passage behind it and taps again to hear that exact moment of the recording, edits what needs editing, confirms who the patient is, and signs. Behind that signature, the system freezes a measurement of how much had to change.

That is the happy path, and it is about a third of the code. The rest is what happens when the wifi drops, the laptop lid closes, the vendor times out, the doctor rewrites a line after generation, or the patient asks for the recording to be destroyed. This document walks the path and stops at each of those.

Verified

The numbers here were measured, not remembered. pytest over the API: 473 passed, 19 skipped, 2 failed — both failures are this machine's .env holding real Google Drive service-account credentials that two tests assume are absent (one of them successfully reached Google's token endpoint mid-run). vitest over the browser client: 72 passed. The 19 skips are the Postgres and MinIO suites, which need containers this run did not start. Endpoint and state counts come from docs/api/openapi.json and from the enums themselves. Where a claim below is not covered by a test, it says so.

Read this first

Two things are deliberately outside the app, and were removed from it on this branch. Consent is captured in the room before the microphone opens — the ledger, its API and its withdrawal effects all still exist server-side, but nothing in the client asks for consent and no server check blocks on it any more. And signing no longer collects a PRC licence number; the column survives, nullable and unused. The older phase writeups in docs/progress/ describe both as in-app gates. They were, until commit 4bc6031.

The trace

Twelve files, in the order the consultation touches them

The companion document orders the code by dependency. This one orders it by time — open these in sequence and you are following one recording through the system. It is not a complete reading list; it is the spine, and every section below hangs off one of these steps.

  1. The doctor signs in web/src/lib/auth.tsx → api/app/api/routes/auth.py An access token in memory, a refresh token in an httpOnly cookie. Note what the client is deliberately not allowed to keep.
  2. An encounter is opened web/src/routes/Home.tsx → routes/encounters.py, start_or_resume Get-or-create on a client-supplied idempotency key. The patient is allowed to be unknown, on purpose.
  3. Intent is written before any audio exists web/src/lib/queue/queue.ts, enqueueRecording The write-ahead invariant. A crash mid-consultation is recoverable only because this row landed first.
  4. The microphone opens web/src/lib/recorder/session.ts Wake lock, an AudioWorklet counting samples, mono Opus at an explicitly pinned bitrate.
  5. Each piece is encrypted, then stored web/src/lib/recorder/crypto.ts, recorder/store.ts AES-GCM under a non-extractable key. Plaintext audio never reaches IndexedDB.
  6. The queue reassembles and uploads web/src/lib/queue/uploader.ts, planParts and uploadSession Many small chunks become few large parts, cut on exact byte boundaries. The bytes never pass through the API.
  7. The server accepts the recording api/app/api/routes/uploads.py, complete_upload Finalize, then HEAD the object to check that "complete" was true. The retention clock starts on that line.
  8. Two background tasks run api/app/tasks/pipeline.py A Celery chain; each stage idempotent, each with its own terminal failure state and its own way back out.
  9. Audio becomes a transcript api/app/services/asr/groq_whisper.py Whisper large-v3. There is no diarization here, and the code refuses to fake one.
  10. The transcript becomes a cited draft app/services/note_generation/groq.py, with shared.py The clinically load-bearing half lives in shared.py precisely so it cannot vary by vendor.
  11. The doctor checks it against the recording app/services/grounding.py → web/src/components/GroundedSection.tsx The product's actual differentiator, and the one place the system would rather say nothing than guess.
  12. It is filed, then signed app/services/note_lifecycle.py One step at a time, identity re-confirmed at filing, and the quality measurement frozen at the signature.

Part one

Two state machines, and the handover between them

Everything in this system is tracked by one of two enums, and knowing which is which explains most of the architecture. Encounter.pipeline_status is the machine's progress — did the audio arrive, did transcription run, did generation run. Note.status is the doctor's progress — generated, filed, authenticated, signed. They meet exactly once, at the moment a note row is created, and after that they never touch again.

That separation is why a doctor can be reviewing a note while the pipeline for the next consultation is still running, and why a pipeline failure is a different kind of problem from an unsigned note: one is an operations question with a retry button, the other is a clinical question with a person attached.

StateSet byWhat it means
recordingPOST /encountersAn encounter exists. There may be no audio at all.
uploadedPOST /upload/completeThe object exists in storage and has been verified by a HEAD.
transcribedtranscribe_encounterA transcript row exists, encrypted, with per-word timings.
note_generatedgenerate_noteA note row exists. This is where the machine hands over to the doctor.
transcription_failedretries exhaustedTerminal. Only POST /retry or a human moves it.
generation_failedretries exhaustedTerminal, and cheaper to retry — the transcript already exists.
blocked_no_consentnothing, nowA legacy value. Rows carrying it resume recording rather than pointing at a deleted page.
Why it matters

There is no upload_failed state, and that absence is deliberate (decision 0023). An upload failure is synchronous — the browser's own request gets a 409 or a 502 and can retry immediately, with a human right there. The two states that do exist are the ones that fail inside a Celery task with nobody watching, which is the only situation that needs a state to be discovered later. Adding a third for symmetry would have added a status nothing could ever be found in.

Part two

Signing in, and what the browser is allowed to keep

The consultation starts with a login, and the login is where the client's security model is decided. Two tokens, held in deliberately different places:

TokenLivesWhy there
AccessA module-scoped variable in memoryLost on reload, which is fine — the cookie restores the session. Never localStorage: anything a script can read, an XSS payload can read.
RefreshAn httpOnly cookieThis code cannot read it at all — the one respect in which the browser client is strictly stronger than the mobile app planned first, since expo-secure-store was always readable by app code.

That choice has a visible consequence on the very first frame. App.tsx refuses to render either the login screen or the app while it is still asking the server whether the cookie is valid:

Where the login route is unusually careful

Three things happen server-side that are worth knowing before you read routes/auth.py:

  • Rate limiting is backed by Postgres, not Redis (decision 0008). Redis is already a dependency, so this looks wrong — until you notice Redis here is a job broker whose loss window is quantified and accepted. A lockout counter that evaporates on a broker restart can be cleared by causing a restart.
  • A presented body token beats the cookie. Getting that backwards is a real bug, not a style choice: with cookie-first, a caller naming a specific token cannot use it, which silently broke the reuse-detection tests — they present a deliberately stale token and expect a 401, and the route rotated the valid cookie instead and returned 200.
  • The role in the JWT is a routing hint, never a boundary. It decides whether a compliance login lands on /audit instead of the doctor worklist; every route re-checks with require_role(...) regardless.
The catch

MFA enrollment (/enroll-mfa) is deliberately reachable while signed out, and that looks like a hole until you read why: it exists for a clinician who cannot log in yet because their account requires MFA and has no secret. Both of its routes prove identity themselves with email and password. Before the screen existed, the only way any account got MFA was a seed script writing a secret straight into the database — an ops gap that had been open since Phase 0.3 and was found not by a test but by an audit of which endpoints had no caller.

Part three

Opening a consultation before you know who the patient is

POST /encounters is four lines of behaviour with two requirements packed into them. The first is idempotency: the route is a get-or-create on a client-supplied upload_idempotency_key, backed by a unique constraint on the column. A retried request with the same key returns the existing encounter rather than opening a second one, which is what stops a flaky connection from producing two notes for one consultation.

The second is subtler and is the requirement that shapes the whole worklist: recording is never blocked on identity. Encounter.patient_id is nullable, so a doctor whose patient is already talking can start capturing and sort out the chart afterwards. Encounters with no patient sit in a clinic-wide "loose sessions" tray until someone links them.

Worth noticing

Creating and resuming are audited as different actions — encounter.create and encounter.resume — and the reasoning is one sentence in the route: the idempotency key is client-supplied, so a resume can return an encounter belonging to a different clinician's recording. "Who picked this session back up" is a real access question, and collapsing it into a create would hide it behind an event that did not happen.

Notice also which lists are scoped and which are not. /encounters/recent is filtered to the calling clinician, because it answers "what was I just doing". /encounters/loose and /encounters/failed are clinic-wide, because an unlinked or dead-lettered recording is a backlog anyone may need to clear. All three write an audit row with entity_id = "*" and a result count rather than enumerating the ids — otherwise a polled tray screen would write an audit row proportional to the clinic's backlog every few seconds.

Found by walking, not by testing

/encounters/recent exists because of a hole no unit test could see: after filing a note there was no way back to it. The only lists were loose and failed, so the moment a doctor linked a patient the encounter left the only tray showing it, and the note was reachable only by remembering its URL. Every test addresses an encounter by an id it already holds, so every test passed. The same shape of bug appeared again at Phase 2.6, where the review screen was unreachable because nothing exposed note_id. Both were found by opening a browser and trying to work.

Part four

Capture: what the laptop does while nobody is looking at it

This is the stage with the most defensive code in the system, for a simple reason — it is the only stage whose failure destroys something irreplaceable. A failed upload retries. A failed transcription retries. A consultation that was not captured is gone, and the patient has left.

The order of operations at the tap

Three things happen before getUserMedia is even called, and each one is in that position deliberately:

  1. The device-full check. Free space is checked at the tap, not discovered mid-consultation. An IndexedDB write that fails with QuotaExceededError halfway through loses the rest of the recording and there is no graceful recovery in the moment. If space is critical, the screen refuses to start and says how many minutes remain — minutes, not a percentage, because "12% free" does not answer the question a doctor is actually asking.
  2. The write-ahead queue entry. The record of intent, including the idempotency key, reaches durable storage before any audio exists. A crash mid-recording then leaves both the chunks and the intent on disk, so the queue recovers the recording on next launch instead of orphaning it.
  3. Only then, the microphone.

Four things learned from measurement, not assumed

Everything load-bearing in session.ts came out of a capture harness run rather than from documentation, and decision 0024 records the numbers.

WhatWhat the harness actually showed
The wake lock must be re-acquired on every return to visibleAcquired at 0.0s, dropped at 35.1s on the first backgrounding, never restored by the browser. Idle sleep went unguarded for 28 of 29 minutes, and a suspend duly followed at 122.8s.
An explicit audioBitsPerSecond is mandatoryWithout it the browser picks: 129 kbps stereo, 26.7 MB over 29 minutes, despite mono being requested.
A requested constraint is not an achieved settingThe device reported channelCount: 2 while being asked for 1. Mismatches are surfaced to the doctor rather than assumed away.
Gaps must be detected, not hoped againstClosing the lid cost 6.5s of real audio. No client architecture prevents that, so the honest response is to record that a gap happened and carry the fact forward.

Gap detection is the interesting one. An AudioWorklet counts samples as they pass through the audio graph and posts the running total four times a second. Wall-clock elapsed time minus captured audio time is, by construction, audio that does not exist — and the count only falls behind if the graph genuinely stalled. The recording screen shows all three numbers live, and the "missing" one turns red past a second.

Why it matters

A truncated recording presented as complete is the failure mode the PRD explicitly rejects, and it is worse than an obviously broken one. If six seconds of a consultation are missing and nothing says so, the transcript reads as continuous, the model drafts a note from it as if nothing were absent, and the grounding UI will happily show a doctor the passage on either side of the hole. The gap total travels with the queue entry precisely so that fact does not live only on a screen the doctor has already navigated away from.

Encryption, and the limitation stated out loud

Each chunk is AES-GCM encrypted before it reaches IndexedDB, under a key held with extractable: false. Two properties matter: the raw key bytes cannot be read back out of the browser at all — not by this code, not by an XSS payload — and GCM is authenticated, so a tampered chunk fails to decrypt rather than decrypting to garbage that then gets transcribed as if it were speech.

The honest limit

A browser cannot seal this key in hardware the way iOS Keychain or Android Keystore could. extractable: false is enforced by the browser, not by a secure element: someone with the device, the OS user session and local code execution can still use the key. The file says so in its own docstring rather than leaving it to be discovered. If Legal requires hardware-sealed custody for on-device PHI, that requirement — not a performance or preference argument — is what would force the Electron option from decision 0024.

Telling a crash apart from a recording in progress

While capturing, the screen writes a heartbeat to the queue entry every five seconds. Without it the recovery logic cannot distinguish a crashed recording from one happening right now in this very tab — and it got that wrong once: a 14-second recording was labelled "interrupted" and pushed into the upload queue while still capturing, which both showed the doctor a false fault and risked uploading before the last chunks existed. A timestamp is the right signal rather than an in-memory flag, because it survives the process dying, which is exactly the case being detected.

Part five

Getting the bytes off the laptop

A four-endpoint protocol in which the audio never touches the API: the server mints presigned URLs and tracks metadata, and the browser PUTs bytes straight to object storage. Decision 0013, replacing an earlier route that accepted a client-supplied object key on faith with no proof it pointed at anything real.

CallWhat it doesWhat makes it safe to retry
POST …/upload/initServer generates the object key, opens a multipart sessionIf a session is already open, returns the same one rather than orphaning a second in storage
POST …/upload/parts/{n}Mints one presigned PUTStateless; minting again is free
GET …/upload/partsReports what has already landedStorage is the source of truth, not a Postgres table this app would have to keep in sync with it
POST …/upload/completeFinalizes, verifies, starts the clock, kicks the pipelineReturns the encounter unchanged if it is no longer recording

The granularity that must not be conflated

Two different sizes are in play, and getting them backwards breaks the upload for every part but the last.

Found live

planParts used to group whole recorder chunks until their running total first reached the minimum. S3 only requires "at least", so that was correct there and silently wrong on Google Drive, which persists a resumable upload in 256 KiB increments and reports progress as a byte offset. Real ~5s Opus chunks are ~17 KB and never sum to exactly 256 KiB, so part 1 overshot, Drive kept only the aligned prefix and answered 308, and part 2 then announced a range starting at a byte Drive had never reached. The symptom was a 1:35 consultation stuck on "Part 2 upload failed (HTTP 503)" through all eight attempts — deterministic, not flaky, because every retry re-derived the same wrong offset from the same ragged plan. Decision 0041.

Two verifications on the way in

complete_upload does not take the client's word for anything. It finalizes the multipart upload, and then does something that looks redundant and is not:

When local audio is allowed to be deleted

Not when upload/complete succeeds. The queue polls GET /encounters/{id} and waits for pipeline_status to show the pipeline actually started, and only then deletes the encrypted chunks from the laptop. The distinction is the checklist's own sharpening of P0-2: the confirmation the device waits for should be about the pipeline, not the bytes. upload/complete confirms bytes and enqueues work; only the status says whether that work ran.

Worth noticing

That poll is the one place in the API that needed a coalescing valve on the audit log. Reading an encounter is a genuine disclosure — it reveals the patient linkage, the pipeline state and the note id — so it must be logged. But a 20-minute transcription polled every 15 seconds would write around 80 identical rows for one recording and bury the human reads on either side of them. A 60-second window keeps the first access and the shape of the polling session, and drops only the repeat count (decision 0032).

Offline is handled as a normal state rather than a fault. The recorder does not need the network at all; the queue backs off and retries; the record screen says so plainly ("Recording still works — audio is saved on this laptop and uploads later") rather than showing an error the doctor cannot act on.

Part six

The asynchronous half: two tasks, three ways of failing

complete_upload ends by calling run_pipeline, which builds a Celery chain of exactly two tasks — transcribe_encounter | generate_note — and returns. Everything after that point happens with no browser attached and nobody watching, which is what all the machinery below is for.

Idempotency is enforced twice, at different altitudes. Upstream, at the encounter row: the idempotency key resolves to a single encounter, so a retried upload never enqueues a second chain. Downstream, inside each task: transcribe_encounter no-ops if the status is already transcribed or beyond, and generate_note no-ops if a note row already exists. You want both, because they defend against different things — the first against a retrying client, the second against Celery redelivering a message under task_acks_late.

Failure modeWhat catches itWhy the other one can't
The task ran and raised, repeatedlyDead-lettering — after max_retries, the encounter moves to a terminal *_failed statusThe sweep looks for encounters that stopped progressing; a dead-lettered one has, by design, and re-kicking it would defeat the point of a dead letter
The task never ran at all — broker down, worker pool at zerosweep_stuck_encounters, on Celery Beat every five minutesDead-lettering lives inside an except block. A task that never started never reaches one
Beat itself is wedged, or a sweep is failing silentlymonitor_pipeline_health, which reads a snapshot, evaluates alert rules and emits breaches at ERRORNeither sweep watches itself. Both run in one Beat process, and if it dies the app keeps serving while expired PHI quietly stops being deleted
Known gap

The monitor runs in the same Beat process as the jobs it watches, and the code says so rather than pretending otherwise: if Beat dies, the monitor dies with the sweeps. What it does catch is the far more common case — Beat alive, a sweep failing or wedged on a query. The honest fix is an external check, and it is written up as such in the observability runbook. Separately, ERROR-level alerts only reach a human when SENTRY_DSN is set; without one, every alert rule in the system is a line in a log file. That is stated in the task's own docstring.

The one line that looks trivial

A ContextVar does not survive serialisation into Redis. So the ID is read from the ambient context here — where an HTTP request has already bound one — and written into both task signatures, which is what lets a browser request, a transcription and a note generation minutes later all carry the same ID with no changes to either route that calls this.

The sweep does something deliberately different: with no inbound request there is nothing to inherit, so it mints its own sweep-… ID and every encounter it re-kicks inherits that. This answers a question a request ID cannot — which sweep run rescued this encounter, and what else did that run touch? A burst of failures sharing one sweep ID is a broker or worker problem; the same failures spread across many IDs is a per-encounter problem.

Worth noticing

Both tasks wrap their whole body in sensitive_scope(), and it is opened outside the try — so the except blocks are inside it. That is where _mark_stage_failure writes an exception summary to an unencrypted column, and it is the exact spot where Phase 4.0 found a real leak: a helper had interpolated an entire model response into an error message, writing generated clinical prose into last_pipeline_error. Truncating to 500 characters was never a control — the first 500 characters of a note are still a note. Routing the write through the scrubber fixes the class rather than the instance.

POST /encounters/{id}/retry is the doctor-facing way out of a dead letter, and it re-runs only the failed stage onward. A generation_failed encounter already has a real transcript, so retrying it calls run_note_generation rather than paying for a second ASR call that would produce the transcript the first one already got right. One button covers both failure states, because from the doctor's side they are the same problem at different depths.

Part seven

From audio to a draft that cites its sources

Both vendor calls go to Groq, and that consolidation is the decision worth understanding (0035). The audio and its verbatim transcript are already processed there for ASR, so moving note generation to the same vendor means one processor to contract with, audit and disclose under the Data Privacy Act instead of two — and the note is derived from a transcript Groq has already seen, so it discloses nothing new.

What the ASR step cannot do, said plainly

Whisper large-v3 is a transcription model, not a diarization one. There is no per-speaker label anywhere in its output, on Groq or anywhere else it is hosted. So every segment is labelled speaker_unknown — deliberately not shaped like the speaker_0/speaker_1 labels a real diarizing vendor would emit, so nothing downstream can mistake it for "one speaker successfully identified out of several." The PRD named ElevenLabs Scribe v2, which does diarize; decision 0018 traded that away and the code refuses to paper over the loss.

The parts that must be identical across vendors

note_generation/shared.py exists for a correctness reason, not a DRY one. Two things in it are load-bearing for features built in entirely different phases, and a provider that reimplemented either slightly differently would break those features silently:

  • The span convention. build_section joins sentences with a single space and records each sentence's character offsets as it goes. The grounding UI re-derives exactly that invariant to decide whether a note's stored offsets still fit its text. If one provider joined with a newline, every note it generated would report "source links no longer line up" from the moment it was created — a feature failing quietly, on one vendor only, with nothing raising.
  • Citation verification. Cited segment IDs are checked against the segments actually sent, and dropped when they do not match. A hallucinated citation is worse than an uncited sentence, because it looks like evidence.

The [INAUDIBLE] substitution lives there for the same reason. P0-4's suppression requirement is enforced mechanically — by never showing the model the unreliable words — rather than by asking it nicely in a prompt. That guarantee is only as strong as its least careful provider.

Groq's structured output is used rather than forced tool use, and not by preference: Groq's own docs state that streaming and tool use are not supported with structured outputs, so the two are mutually exclusive there. Given the choice, response_format: json_schema with strict: true is the stronger one — the schema is enforced by constrained decoding, so the model cannot emit a violating token sequence, whereas a forced tool call still asks a model to fill a schema correctly. The cost is that arguments arrive as a JSON string to parse, which adds a failure mode.

Blocked, not broken

Groq's free tier allows roughly 8,000 tokens per minute on this model, and a 20–40 minute consultation transcript is comfortably 10k–20k tokens. Short visits work; a real clinic day does not. Separately, Groq's BAA covers "Covered Cloud Services", which excludes both preview-stage models and services provided free of charge — so PHI needs a paid plan and a Production-status model. This is not a code gap. It is a purchase order.

One more thing happens in generate_note and nowhere else: the per-consultation cost estimate. This is the only place that knows both numbers it needs — audio duration, taken from the transcript's own last word timestamp, and text volume — and knows them without an extra query or a byte of PHI leaving the function. It also never raises: a failure to measure a note must not fail the note.

Part eight

Grounding: the hard part, and the four places it refuses to guess

This is the product's trust mechanism and the genuinely difficult piece of the system. The doctor's rational response to "an AI wrote this" is prove it, and this is the proof. Everything upstream exists to make it honest: segment IDs assigned at persist time, the model citing those IDs rather than inventing offsets, and citations verified against the segments actually sent.

Why the offsets are re-derived rather than trusted

text_start and text_end are offsets into the text as generated. A doctor's edit shifts every offset after it, so highlighting by stored offsets after an edit highlights the wrong words. spans_fit_text checks the invariant instead of assuming it: slice the current text by the spans, re-join with a single space, and the result must be the original text back. Any insertion, deletion or reordering breaks it. A same-length in-sentence substitution does not — correctly, because the offsets genuinely still delimit that sentence, and whether its content is still the model's is the separate question edited_since_generation answers.

Why it matters

These two flags are separate because they fail differently. Broken offsets are a rendering problem — the UI would underline the wrong words. A same-length rewrite is a provenance problem — the offsets are fine, and presenting a transcript passage as "the source of this line" would simply be false, because the line is now the doctor's sentence. Collapsing them into one boolean would mean either withholding grounding from notes that still have it, or attributing a doctor's words to the model.

The degradation ladder

Notes outlive audio. So both audio_state and transcript_state are five-valued, and the UI says which rung it is on in words rather than showing a play button that does nothing:

StateWhat the doctor is told
availablePlay it.
never_recordedThere was no recording for this encounter.
withdrawnDeleted at the patient's request — legally and clinically a different fact from time passing.
expiredThe retention period elapsed.
unreachableStorage did not answer. Deliberately not folded into expired: "we could not check" and "it is gone" warrant different words, and guessing the harsher one is still a guess.

The transcript ladder gained its own withdrawn rung for exactly this reason. Retention deletes a withdrawn encounter's transcript too — correctly, since it is verbatim PHI derived from a recording someone asked to have destroyed — and with only expired available, that deletion was being described to the doctor as "the retention period elapsed," which is the wrong reason.

In the browser: two taps, and a window rather than a file

Each section renders as clickable lines first and swaps to a textarea only when the doctor chooses to edit. That ordering is the point rather than a workaround: the first pass over an AI draft should be verification, and the default gesture should be the one the doctor is accountable for. Tap a line to highlight its source passage; tap again to hear it — two taps rather than one, because playing audio aloud in a consultation room is not something to trigger by accident.

Playback stops at the cited passage's end_ms plus a 250 ms tail rather than running on into the rest of the consultation. The doctor asked to hear one line's source; continuing past it discloses more of the recording than they asked for, and does it without them noticing. The presigned URL is minted on the click that justifies it, carries Cache-Control: no-store, and is re-fetched rather than held across a long review session.

The catch

On the Google Drive backend none of that byte-path reasoning holds, and the code says so instead of quietly degrading. Drive has no presigned GET, so presign_audio_playback raises UnsupportedByBackendError and the route falls back to streaming the audio through the API — honouring Range requests so one cited passage does not pull the whole consultation, and setting no-store by hand, since on the S3 path that header was signed into the URL. This gives up exactly the property decision 0013 was written to protect: PHI bytes crossing the application server. It is a limitation of Drive at every tier, not of the free plan.

Part nine

Filing and signing: four states, one step at a time

note_lifecycle.transition() is the only code path allowed to write Note.status. Routes must call it rather than assigning the field, so "no state skippable" is enforced in one place instead of trusted to every caller. The allowed moves are a dictionary of exactly three entries: generated → filed → authenticated → signed.

Two of those steps do more than move a value.

Filing re-confirms who the patient is

Filing is the point the note becomes part of a patient's record, so it is the last moment a mis-linked recording can be caught cheaply — after that, the note is in the wrong person's history. The route therefore requires the caller to name the patient rather than reading encounter.patient_id and trusting it:

Found live, with a screenshot

This check produced a bug that is worth the space. A doctor picked and confirmed a patient right there on the review screen — the banner said "Linked to …, born …. Filing will confirm this." — and filing rejected it every time. The picker component never calls the server on its own by design; the two screens using it are each supposed to. Home's loose-session tray did. The review screen's handler was pure React state, so the banner was true only in that component's memory, while the column the transition actually checks had never been touched. The fix was one call to linkEncounterToPatient() before setting local state. The lesson: a confirmation step can only confirm something that already exists, and "confirm" and "create" reading identically in the UI is what let the gap survive.

Signing captures identity, and freezes the measurement

Signing writes signed_by_clinician_id and signed_at, and the route audits it. Then, after the commit and deliberately unable to raise, it captures the edit-burden metric. Retention will delete the note's revisions long before the pilot is assessed, so a metric computed later would quietly become uncomputable — and a bug in a similarity ratio must never refuse a doctor's signature or roll one back. The measurement is recomputable; a refused signature in a consultation room is not.

Why it matters

The definition behind that measurement is the last engineering decision the project made, and the obvious version of it was unsafe. The PRD's headline target is "≥70% of signed notes require only minor edits". Under a plain distance threshold, 500mg → 5000mg is a one-character edit — maximally minor, and a tenfold overdose; no chest pain → chest pain is a three-character deletion that inverts a finding. So an edit is minor only if it is small and clinically inert, with the clinical check acting as a veto rather than a weighting. Under the naive definition the metric would have reported the model as most trustworthy precisely where it was most dangerous — in the number being used to justify skipping vendor validation for two vendors (decision 0039).

The measurement compares generated text to signed text, not the sum of the revisions — a doctor who types a word, deletes it and retypes it produces three revisions and zero net change. Recovering the generated text is done structurally rather than by timestamp: it is the previous_text that never appears as any new_text for that section. Edits form a chain A→B→C and only A is never anyone's output, which is ordering-independent and needs no new column. The one genuine ambiguity — an edit followed by a revert makes every value both an input and an output — is detected and reported as ambiguous rather than guessed at.

Part ten

After the signature: what is kept, what is destroyed, who can tell

The consultation is over, but three subsystems keep acting on it for months.

Retention, in two layers that cannot substitute for each other

The bucket's own lifecycle rule expires the audio objects. It runs inside object storage, so it holds whether or not this application is running, deployed, or even correct — that is the backstop, and it matters most because the raw recording is the most sensitive artifact. A Celery Beat job handles everything the bucket cannot see: the Postgres rows derived from that audio — transcript, drafting history — plus the write-back that keeps the encounter row honest about what has already gone. A lifecycle rule cannot reach Postgres; an application job cannot be trusted to have run.

ArtifactFate
Audio objectDeleted by the lifecycle rule, and by the purge job, whichever gets there first
TranscriptDeleted by the purge job on its own clock, or immediately on withdrawal
NoteRevision rowsDeleted with the transcript, never separately
The signed noteNever. No code path in the retention module touches the notes table, for any reason
The consent ledgerNever. It is append-only at the database level and is the legal record of the withdrawal that may have triggered the deletion
Audit rowsTheir own retention period, deliberately longer than the PHI they describe
Why revisions die with the transcript

Grounding derives edited_since_generation from a revision merely existing for a section. Delete revisions while the transcript survives and a doctor-rewritten section flips back to "these are the model's words," and the UI will highlight transcript passages as the source of prose the model never wrote — exactly the confidently-wrong answer the whole grounding design exists to prevent. So they are only ever removed in the same purge that removes the transcript, at which point grounding reports expired, returns no segments, and has nothing left to mis-attribute.

On the Google Drive backend the first layer does not exist: Drive has no lifecycle rules, so expired audio is deleted only by the Celery purge, which runs only while the worker machine is up. That is one of the three costs decision 0040 names rather than absorbs, and no paid Google tier removes it.

The audit trail, and the rule that replaced twenty-three judgment calls

Every disclosure of, or capability over, PHI is logged — and requests are never logged. That single rule is why GET /upload/parts writes no row (it discloses part numbers and ETags, no PHI, and grants nothing) while POST /upload/parts/{n} does (a presigned PUT is a live, writable handle on a recording). The vocabulary is <entity>.<verb>, with a .read segment wherever the event is a disclosure rather than a change — because an access log that only records writes answers "who changed this?" and cannot answer "who looked at this?", which is the question a breach investigation actually asks.

The log is append-only at the database level, plus a TRUNCATE guard — added because Phase 4.2 found that append-only triggers do not fire on a truncate, so the table could be emptied in one statement by anything holding the privilege. The same phase found that PATCH /notes, the one endpoint in the whole API that changes clinical content, was writing no audit row at all.

Measurement

Beyond edit burden, the pipeline emits per-stage latency and a per-consultation cost estimate, and the pilot report exposes coverage so silent loss of a measurement is visible rather than assumed away. Two numbers are worth carrying: the PRD's <$0.10 per consult target breaks even at about 51.7 minutes of audio, because ASR costs 15–23× note generation — it is really a duration budget, not a cost one. And the ≥70% minor-edit target is now measurable but not yet meaningful, because nobody has seen the distribution it will be judged against.

Part eleven

What the tests pin down, and what they structurally cannot

Measured this session: 473 passed, 19 skipped, 2 failed across 494 collected API tests, in 2m 48s; 72 passed in the browser client's vitest suite, in 2.4s. The two failures are environmental — this machine's .env supplies real Google Drive service-account credentials, and two tests assert the behaviour of their absence. One of them reached Google's live token endpoint mid-run and got a 200, which is a decent illustration of why they fail here and pass in CI.

The 19 skips are not neglect; they are the suites that require containers. test_postgres_specific.py and test_storage_specific.py spin up real Postgres and MinIO via testcontainers and skip — loudly, with the Docker error in the message — when the daemon is not there. The reasoning is in the file: the interesting kind of bug is in exactly the mechanics a mock skips.

The catch

The most instructive bugs in this project's history were invisible to the suite by construction, and the pattern repeats: every test addresses an entity by an id it already holds. That is why "there is no navigation path to this screen" shipped twice behind a green suite, why 419 passing tests hid a seed script that made every account unloginnable, and why a real browser recording had — probably — never once transcribed successfully while every ASR test passed. Synthetic test audio produced a content type simple enough to dodge the bug, and then failed for being fake, which is what kept the real failure hidden.

Part twelve

The edges: deploy, CI, and the things that only fail in production

What a green check is allowed to mean

The CI question that shaped Phase 5.3 was not "which linters should run" but what is a passing build actually evidence of? The suite builds its schema with create_all() against SQLite, so it is structurally incapable of noticing that a model has no migration. Add a column, everything goes green, alembic upgrade head succeeds at deploy because there is nothing to apply, and the first query against the new column raises UndefinedColumn at a clinic. Green, green, green, outage — a passing check asserting something it never looked at, which is worse than no check, because a green badge is what stops anyone looking.

The rule the phase worked to is worth stealing verbatim:

The rule

A gate must be able to fail, must have been seen failing, and must not be able to pass by not running. Hence a migration check built as a snapshot assertion rather than an ignore list — it fails when a divergence disappears too, so nobody can quiet it by deleting an entry — and Postgres suites that cannot silently skip themselves in CI the way they legitimately do on a laptop. It found four real schema divergences nothing had ever compared.

Deployment, as actually configured

The production topology in decision 0036 is one Linux VM on Docker Compose with a bought Postgres. What is deployed today is the free-tier variant, and it is a different shape with different costs:

Three configuration choices in that stack are non-obvious and each came from a failure:

  • CORS was the wrong tool for local-against-Render development. The runbook once told an engineer to add http://localhost:5173 to the deployed origin list, and the production boot guard refused to start — correctly, since it cannot tell a deliberate temporary addition from a dev .env deployed by accident. A conditional Vite dev-server proxy replaced it, deliberately not VITE_-prefixed so it can never leak into the bundle. It also fixed a problem the CORS approach carried silently: cross-origin from a real browser would have made the SameSite=lax refresh cookie unusable mid-recording.
  • Security headers are raw ASGI middleware, added inside the CORS middleware so they still land on the responses CORS short-circuits. A rejected preflight is still a response leaving the API.
Blocked, not broken

What is left on this project is mostly not engineering. Legal has not cleared the RA 4200 consent script; a Data Protection Officer and a breach-response team are both legally required and currently nonexistent; decision 0036's four data-residency questions are unanswered. On the accounts side a real pilot needs a paid Groq plan, a Sentry account, a managed Postgres and a VM. None of those is a code change, and no amount of engineering closes any of them. The repository's own README carries a standing instruction not to record a real patient yet.

Part thirteen

Six things that broke after the code looked finished

Every one of these was found by using the deployed system, not by a test. They are ordered by how much they change the way you would read the codebase.

1 · Every real browser recording had probably never transcribed

Observed: a real recording sat at "waiting for the server to start processing"; worker logs showed a bare Groq 400 on every attempt, with no complaint about content.

Actually: Groq identifies audio format from the filename extension in the multipart upload. Two bugs were stacked. The extension lookup matched on the full MIME string, but MediaRecorder's real value is audio/webm;codecs=opus — with parameters — so it missed every real recording and fell back to a generic .audio. And the audio/webm → .weba mapping it would have used was itself wrong: the same bytes 400 as .weba and 200 as .webm. Only synthetic test audio ever had a content type simple enough to dodge the first bug, and it failed anyway for being fake — which is precisely what kept the real failure invisible.

The generalizable move: when a test fixture is simpler than production input in any dimension, that dimension is untested — and a test that fails for its own separate reason will hide the bug rather than reveal it.

2 · A 500 on upload, from a component the error never named

Observed: the PUT to Drive succeeded, the database correctly advanced to uploaded with a retention timestamp, and then upload/complete returned a bare 500 with no detail. Readiness had been reporting redis:ok the whole time.

Actually: the two Redis clients in the codebase disagree about rediss://. The health probe uses redis.Redis.from_url(), which infers TLS from the scheme. Celery's client, Kombu, refuses a rediss:// connection unless a certificate policy is stated explicitly — and refuses late, at the first real connection, which is chain.apply_async() inside complete_upload, after storage and the database commit had already succeeded.

The generalizable move: two clients for the same dependency is two configurations, and a health check that uses the easier one is not evidence about the harder one.

3 · A confirmation that confirmed nothing

Observed: a doctor confirmed a patient on the review screen, the banner said so, and filing rejected it every time with "This recording is not linked to a patient yet."

Actually: the picker never calls the server itself by design; the two screens using it are each meant to. One did. The review screen's handler was pure React state, so the banner was true only in that component's memory while the column the transition checks had never been written.

The generalizable move: a shared component with a by-design responsibility left to its callers has as many chances to be wrong as it has callers — and "confirm" and "create" looking identical in the UI is what lets one of them go unimplemented.

4 · An upload bug that shipped behind a clean typecheck

Observed: "Cannot access 'init' before initialization" on every upload, on every backend, always.

Actually: a stale tsconfig.app.tsbuildinfo let the typecheck skip uploader.ts entirely; a forced run reported three errors on one line. The part-size plan read init.data on the line above the const init = await … that declares it — a temporal dead zone error, so it does not depend on backend, load, or consultation length.

The generalizable move: an incremental build cache means "the typecheck passed" and "the typechecker looked at this file" are different claims. The follow-up is the more useful half: the forty lines that actually talk to storage had no unit test at all, only an end-to-end smoke test needing Postgres, MinIO, a worker and a real Chromium — a real test, and not one anybody runs while editing a header.

5 · The queue that could not see a fix applied elsewhere

Observed: an encounter that failed at note generation was successfully retried from the worklist and reached note_generated — while the browser's own upload queue card kept showing it as failed, forever, with the same stale error.

Actually: the queue's poll only ever re-checked entries in the uploaded state. Once an entry moved to failed — correctly, the first time — nothing looked at it again, and the doctor's retry went through an entirely separate server-side path the client has no visibility into.

The generalizable move: when two components can both change the same state, a terminal state in one of them has to stay observable, or the two drift apart permanently at exactly the moment the problem gets fixed.

6 · Two mechanisms, each individually correct, in direct conflict

Observed: every seeded account was unloginnable, with 419 tests passing.

Actually: two independent reasons. The seed created clinicians with no MFA secret, while login requires one. And every seeded address was on @staging.remedy.invalid — which email-validator, used by Pydantic's EmailStr, rejects as a special-use TLD, so the request died at the schema with a 422 before any credential was checked. The seed's own production-safety design is what required a non-routable domain.

The generalizable move: two correct rules can be jointly unsatisfiable, and nothing in either rule's own tests will say so. The place to look is wherever two subsystems constrain the same value from opposite directions.

The ratio, again

Five of these six are integration or environment failures rather than logic errors, which is the same ratio the scaffold walkthrough reported at the other end of the project — and the failures got more integration-shaped, not less, as the code matured. All six were found by driving the real deployed system. None of the six was a hard problem to fix; the hard part in every case was seeing that something was wrong at all.
